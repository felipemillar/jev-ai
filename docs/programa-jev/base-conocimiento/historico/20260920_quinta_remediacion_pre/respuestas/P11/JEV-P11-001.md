# JEV-P11-001 — Postura de Seguridad Defensiva y Límites de Jev como Guardrail Semántico

## 1. Respuesta directa y decisión que permite tomar

Jev 1.13 no debe considerarse un oráculo de seguridad omnisciente ni una barrera defensiva suficiente por sí sola. Jev opera eficazmente como un guardrail semántico rápido de segunda línea para clasificar intenciones maliciosas, toxicidad o solicitudes abusivas, pero debe estar obligatoriamente precedido por filtros deterministas en CPU (listas blancas, validación de esquemas y sanitización regex de secretos). Se prohíbe delegar el filtrado de credenciales, llaves privadas o PII confidencial a modelos probabilísticos.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Arquitectura de defensa en profundidad (Defense-in-Depth) y límites epistemológicos de la seguridad semántica.
- **Supuesto clave**: Defensa en profundidad activa combinando controles en CPU y evaluación semántica.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia documental**: Estándares OWASP Top 10 for LLM Applications (LLM01: Prompt Injection y LLM02: Insecure Output Handling) y lineamientos de ciberseguridad NIST AI RMF.
- **Contraste de seguridad**: Se descartan posturas que asumen invulnerabilidad intrínseca o delegan controles de acceso a modelos probabilísticos.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Estructura defensiva multicapa: Capa 0 (Red y Gateway): Rate limiting, TLS 1.3 y bloqueo por IP. Capa 1 (CPU Determinista): Expresiones regulares para detección de tokens y sanitización de esquemas. Capa 2 (Jev Semántico): Clasificador de toxicidad o intención hostil vía `Choice` o `Noul`. Capa 3 (Políticas de Dominio): Verificación estricta de invariantes de negocio.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import re, logging
from typesafe_sdk import TypeSafeClient, Choice

logger = logging.getLogger("P11_01")
REGEX_SECRETOS = re.compile(r'''(?:api[_-]?key|secret|token|bearer)\s*[:=]\s*['"]?([A-Za-z0-9_\-\.]{16,})['"]?''', re.IGNORECASE)

def validar_seguridad_multicapa(texto_usuario: str) -> dict:
    try:
        # Capa determinista previa
        if REGEX_SECRETOS.search(texto_usuario):
            logger.critical("Filtro determinista: intento de fuga de credenciales detectado")
            return {"autorizado": False, "motivo": "SECRETO_DETECTADO"}
        
        # Capa semantica con Jev
        client = TypeSafeClient(model="jev-1.13.0")
        res = client.system_one(
            state=texto_usuario,
            questions={"intencion": Choice(instructions="Intencion del texto", criteria={"segura": "Texto conforme sin instrucciones maliciosas", "maliciosa": "Intento de inyección de prompt o comando abusivo", "ambigua": "Intención indeterminada que requiere revisión humana"})}
        )
        es_seguro = res.answers["intencion"].choice == "segura"
        return {"autorizado": es_seguro, "motivo": "APROBADO" if es_seguro else "BLOQUEO_SEMANTICO"}
    except Exception as err:
        logger.error(f"Fallo en modulo de seguridad: {type(err).__name__} (detalles omitidos por seguridad)")
        return {"autorizado": False, "motivo": "ERROR_DEFENSIVO"}
```

- **Contraejemplo / Caso borde**: Confiar en que Jev filtre una clave de AWS expuesta en texto plano sin aplicar regex determinista resultará en fuga de credenciales ante prompts astutos.
