# JEV-P04-003: Diseño de Contratos de Entrada: Diferenciación entre Dato Ausente, Desconocido, Nulo y Negativo Confirmado

## 1. Respuesta directa y decisión que permite tomar

El colapso indistinto de la incertidumbre en un único valor comodín (como `null`, `None` o cadena vacía `""`) es una de las principales fuentes de errores de clasificación en Jev 1.13. Si el modelo no puede distinguir si una variable no se investigó o si se demostró fácticamente su falsedad, producirá alucinaciones de certidumbre o abstenciones injustificadas.

La arquitectura de datos debe formalizar un **Contrato de Cuatro Estados Epistémicos (Lógica Cuadrivaluada de Entrada)**:
1. **Dato Ausente (*Missing / Omitted*)**: La propiedad o campo no fue suministrado en la llamada (e.g., clave ausente en el JSON). Indica fallo de captura en el cliente o campo opcional omitido.
2. **Valor Desconocido (*Unknown / Indeterminate*)**: La entidad fue consultada activamente pero el sistema o emisor declara explícitamente que la información se ignora o no está disponible en la fuente de origen (e.g., `"balance_fiscal": "NO_DISPONIBLE_EN_ORIGEN"`). Refleja incertidumbre epistémica externa no imputable a negligencia del usuario.
3. **Valor Nulo (*Explicit Null / Not Applicable*)**: El atributo existe en el esquema y fue evaluado, pero se confirma que la propiedad ontológicamente **no aplica** a esta entidad (e.g., `"fecha_finiquito": null` para un colaborador con contrato indefinido activo).
4. **Valor Negativo Confirmado (*Confirmed Negative / Factual False*)**: La condición fue auditada exhaustivamente y se verificó con evidencia positiva que el evento **no ocurrió** o es falso (e.g., `"deuda_morosa_verificada": false` o `"saldo_insolvente": 0.00`).

**Decisión que permite tomar**: Prohibir en todos los esquemas de entrada de QRT y Wheelwork el envío de valores `null` o claves vacías para atributos con relevancia en la decisión. Exigir que todo campo decisorio sea modelado como un tipo algebraico disjunto (mediante Pydantic / TypeScript) que serialice explícitamente cadenas semánticas unívocas (`"NO_APLICA"`, `"DESCONOCIDO_EXTERNO"`, `"CONFIRMADO_NEGATIVO"`) y dotar a las preguntas de `Choice` de opciones de escape que representen explícitamente la insuficiencia de evidencia.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Modelado formal de esquemas JSON tipados para el campo `state` en Jev 1.13, gestión de valores faltantes y diseño de lógica tri/cuadrivaluada en preprocesamiento.
- **Términos formalizados**:
  - *Lógica Cuadrivaluada (Belnap 1977)*: Marco lógico formal que distingue Verdadero ($T$), Falso ($F$), Ninguno/Ausente ($\emptyset$) y Ambos/Contradictorio ($\top$).
  - *Tipo Algebraico de Datos (ADT)*: Tipo compuesto por suma de estados disjuntos que no permite estados indefinidos accidentales.
  - *Cláusula de Escape Taxonómico*: Opción explícita en un esquema `Choice` que captura el estado de información desconocida o no aplicable.
- **Versiones de referencia**: Jev 1.13 (`typesafe-sdk >= 0.7.0`), Python 3.11+, Pydantic v2.6+.
- **Supuestos fundamentales**:
  1. Jev procesa cadenas semánticas explícitas con mayor precisión que tokens estructurales de serialización (un codificador denso interpreta mejor `"ESTADO: DESCONOCIDO"` que `null`).
  2. La capa de validación en CPU rechaza llamadas antes del despacho HTTP si el payload no resuelve unívocamente la tipología de sus campos ausentes.

## 4. Explicación técnica verificable

### 4.1. Matriz de Diferenciación de Estados Epistémicos

Para evitar colisiones de interpretación en el codificador de Jev, los cuatro estados se gobiernan mediante la siguiente especificación de entrada:

| Estado Epistémico | Condición del Mundo Real | Representación Prohibida | Representación Canónica Obligatoria en `state` | Comportamiento Esperado en Jev |
|---|---|---|---|---|
| **Dato Ausente** | El emisor omitió el campo o la captura falló. | Clave omitida, `""` o `null` | `"campo": {"estado": "DATO_NO_PROVISTO"}` | El preprocesador en CPU rechaza la petición o Jev activa la opción de escape: `informacion_insuficiente`. |
| **Valor Desconocido** | Se investigó la fuente, pero el dato es incierto externamente. | `"desconocido"` sin tipar o `NaN` | `"campo": {"estado": "CONSULTADO_PERO_DESCONOCIDO", "fuente": "Registro_X"}` | Jev asigna probabilidad de abstención o deriva a opción `no_determinado`. |
| **Valor Nulo** | El atributo ontológicamente no aplica a esta entidad. | `null` crudo o `0` | `"campo": {"estado": "NO_APLICA_POR_DEFINICION", "motivo": "Contrato_Indefinido"}` | Jev reconoce que la condición no constituye un incumplimiento normativo. |
| **Negativo Confirmado** | Se auditó activamente y se confirmó que el evento NO ocurrió. | `false` ambiguo o `null` | `"campo": {"estado": "CONFIRMADO_NEGATIVO", "evidencia": "Certificado_Limpio"}` | Jev asigna certeza fáctica alta a la hipótesis negativa ($p \to 0$ en `Noul` de anomalía). |

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Ejemplo sintético trabajado: Modelo de Datos con Pydantic y Serialización Semántica

```python
# Ejemplo ilustrativo no ejecutado
"""
epistemic_state_model.py
Esquema formal en Pydantic v2 que implementa tipos de datos algebraicos
para distinguir dato ausente, desconocido, nulo y negativo confirmado.
"""
from typing import Union, Literal
from pydantic import BaseModel, Field

class ConfirmedNegative(BaseModel):
    status: Literal["CONFIRMADO_NEGATIVO"] = "CONFIRMADO_NEGATIVO"
    evidence: str

class ExplicitNotApplicable(BaseModel):
    status: Literal["NO_APLICA"] = "NO_APLICA"
    rationale: str

class ConsultedUnknown(BaseModel):
    status: Literal["CONSULTADO_PERO_DESCONOCIDO"] = "CONSULTADO_PERO_DESCONOCIDO"
    source_checked: str

class ConfirmedValue(BaseModel):
    status: Literal["VALOR_PRESENTE"] = "VALOR_PRESENTE"
    value: float
    currency: str

# Tipo algebraico disjunto para un campo financiero crítico
EpistemicFinancialField = Union[ConfirmedValue, ConfirmedNegative, ExplicitNotApplicable, ConsultedUnknown]

class FinancialAuditState(BaseModel):
    entity_id: str
    tax_debt_status: EpistemicFinancialField = Field(..., description="Estado de deudas fiscales")
    audit_notes: str

if __name__ == "__main__":
    # Caso 1: Negativo Confirmado (La empresa auditó y no tiene deuda)
    caso_limpio = FinancialAuditState(
        entity_id="CORP-881",
        tax_debt_status=ConfirmedNegative(evidence="Certificado de Tesorería General al día sin deuda pendiente."),
        audit_notes="Auditoría anual estándar."
    )

    # Caso 2: Consultado pero Desconocido (La base tributaria estuvo caída)
    caso_desconocido = FinancialAuditState(
        entity_id="CORP-882",
        tax_debt_status=ConsultedUnknown(source_checked="Servicio de Impuestos (Timeout en API pública)."),
        audit_notes="Pendiente de reintento."
    )

    # Caso 3: No Aplica (Entidad exenta de impuestos)
    caso_no_aplica = FinancialAuditState(
        entity_id="CORP-883",
        tax_debt_status=ExplicitNotApplicable(rationale="Organización no gubernamental sin fines de lucro exenta por ley."),
        audit_notes="Exención tributaria acreditada."
    )

    print("--- CASO 1: NEGATIVO CONFIRMADO (JSON para Jev) ---")
    print(caso_limpio.model_dump_json(indent=2))

    print("\n--- CASO 2: DESCONOCIDO (JSON para Jev) ---")
    print(caso_desconocido.model_dump_json(indent=2))
```

### 5.2. Contraejemplo y caso límite: Colapso en `null` que dispara Falsa Alarma

Un ingeniero envía un payload donde la propiedad de deuda viene vacía:
```json
{
  "entity_id": "CORP-990",
  "deuda_tributaria": null,
  "notas": "Empresa solicitando crédito."
}
```
Y ejecuta una pregunta de `Noul`: `"¿Presenta la empresa antecedentes tributarios o deudas no resueltas?"`.
- **Interpretación errónea de Jev**: Al ver `null`, el codificador denso detecta que no hay evidencia afirmativa de solvencia. Jev asigna una probabilidad $p = 0.54$, cayendo en la zona de incertidumbre.
- **Acción errónea en CPU**: Dado que el umbral de riesgo de la empresa para deuda es conservador ($\tau^* = 0.05$), el sistema bloquea automáticamente la solicitud de crédito de una empresa que no tenía ninguna deuda, provocando la pérdida del cliente.
- **Mitigación**: Si el estado hubiera dicho explícitamente `"status": "CONFIRMADO_NEGATIVO"`, Jev habría emitido $p = 0.01$, aprobando la operación de inmediato.

## 6. Aplicación a nuestros desarrollos

### 6.1. Evaluación de Señales y Métricas Fundamentales (QRT)
- **Hecho documentado**: En el análisis cuantitativo de reportes trimestrales (10-Q / 10-K), es común que ciertas empresas no reporten una métrica específica porque no aplica a su sector (e.g., métricas de inventario en una empresa de software puro).
- **Integración propuesta**:
  - Prohibir rellenar campos con `0.0` o `null` en los inputs de Jev en QRT.
  - Para una empresa de software, el inventario se serializará como `{"inventario": "NO_APLICA_POR_MODELO_DE_NEGOCIO"}`. Esto previene que Jev interprete un inventario de $0$ como un síntoma de quiebra inminente o liquidación forzosa.

### 6.2. Onboarding y Verificación de Cumplimiento en Wheelwork
- **Hecho documentado**: Wheelwork realiza procesos de *Know Your Customer (KYC)* y validación de antecedentes.
- **Integración propuesta**:
  - Utilizar el esquema de tipos disjuntos en todos los formularios de ingesta.
  - Si un antecedente judicial no pudo consultarse por indisponibilidad de la API gubernamental, el campo se serializará como `"CONSULTADO_PERO_DESCONOCIDO"`.
  - El evaluador de Wheelwork reconocerá la contingencia y encolará el ticket para reintento automático, en lugar de emitir una denegación arbitraria de servicio.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla específicos
1. **Fallo por Sobreescritura Silenciosa en Bases de Datos**: ORMs que convierten automáticamente valores semánticos especiales (`"NO_APLICA"`) en `NULL` de SQL durante la serialización a disco.
   - *Control*: Definir columnas JSONB con validación de esquema en base de datos o tipos enumerados estrictos en PostgreSQL.
2. **Fallo por Incompatibilidad de Pregunta**: Formular una pregunta de `Noul` que asume que el valor siempre existe (e.g., *"¿Es la deuda superior a $10,000 USD?"* ante un dato que no aplica).
   - *Control*: Diseñar preguntas condicionadas o validar en CPU antes de llamar a Jev si la propiedad aplica ontológicamente al caso.

### 7.2. Condiciones taxativas de no uso
- **No utilizar modelos probabilísticos para verificar si un campo es nulo o ausente**: Comprobar si un dato está ausente o es nulo es una operación de código determinista en CPU (`if campo is None:`) que cuesta \$0 y tarda 0 ms. Jamás delegar esta comprobación sintáctica a Jev.

## 8. Validación propuesta (propuesta, no ejecutada)

- **Hipótesis falsable**: La explicitación semántica de los cuatro estados epistémicos en el `state` en comparación con el uso de campos opcionales con valores `null` reduce los errores de clasificación en casos límite en un **28%** y elimina el **100%** de las falsas alarmas provocadas por datos no aplicables.
- **Comparador / Línea base**:
  1. Configuración A: Esquema plano tradicional con valores `null` y campos omitidos.
  2. Configuración B: Esquema cuadrivaluado con enums semánticos explícitos (`ConfirmedNegative`, `ExplicitNotApplicable`, `ConsultedUnknown`).
- **Conjunto de datos sintético**: 1,000 expedientes financieros sintéticos conteniendo 250 casos de cada uno de los cuatro estados epistémicos.
- **Métricas cuantitativas**:
  - Tasa de Falsos Positivos (FPR) y Falsos Negativos (FNR).
  - Tasa de Clasificación Correcta de No Aplicabilidad.
  - Calibración de certeza Brier en subconjuntos ambiguos.
- **Umbral de éxito**: Reducción de falsos positivos en casos "No Aplica" $\ge 95\%$; Exactitud global $\ge 94\%$.
- **Criterio de rechazo**: Si la representación semántica cuadrivaluada produce confusión léxica en Jev aumentando la tasa de abstenciones injustificadas.
- **Presupuesto supuesto**: 2,000 llamadas a Jev; coste API estimado en \$0.004; tiempo de cómputo en CPU: 6 minutos.
