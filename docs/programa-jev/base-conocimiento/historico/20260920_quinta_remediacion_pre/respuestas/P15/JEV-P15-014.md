# JEV-P15-014 — Evaluación de Señales Textuales con Particiones Temporales Rigurosas

## 1. Respuesta directa y decisión que permite tomar

En finanzas cuantitativas, la validación de cualquier modelo o señal derivada de texto exige particiones temporales estrictas (Time-Series Split / Purged Walk-Forward). Queda terminantemente prohibido utilizar validación cruzada con barajado aleatorio (K-Fold cross-validation con shuffle), ya que mezcla datos del futuro con datos del pasado, generando resultados artificialmente optimistas que colapsan en tiempo real. Los conjuntos de entrenamiento, validación y prueba deben ser cronológicamente contiguos y purgando períodos de solapamiento.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Machine Learning en series temporales financieras, prevención de filtraciones de datos y metodología de validación.
- **Supuesto clave**: Entorno de investigación documental hermético y aislado del motor de trading algorítmico.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia cuantitativa**: Metodología de Marcos López de Prado en 'Advances in Financial Machine Learning' (Capítulo 7: Cross-Validation in Finance).
- **Contraste econométrico**: Se prohíbe deducir rentabilidad o predicción financiera a partir de exactitud de clasificación de texto.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Partición Walk-Forward con Purging y Embargo: Bloque Entrenamiento: Años 2018-2021; Purga: 1 mes; Bloque Validación: 2022; Bloque Fuera de Muestra (OOD): 2023-2024. El conjunto OOD no se consulta hasta el congelamiento final del modelo.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import logging

logger = logging.getLogger("P15_14")

def validar_particion_temporal_continua(anios_entrenamiento: list, anios_prueba: list) -> bool:
    try:
        max_entrenamiento = max(anios_entrenamiento)
        min_prueba = min(anios_prueba)
        if min_prueba <= max_entrenamiento:
            logger.critical("CONTAMINACION TEMPORAL: El conjunto de prueba se solapa con entrenamiento")
            return False
        return True
    except Exception as err:
        logger.error(f"Fallo en validacion temporal: {type(err).__name__} (detalles omitidos por seguridad)")
        return False
```

- **Contraejemplo / Caso borde**: Mezclar aleatoriamente noticias de 2020 y 2023 para entrenar y probar un clasificador financiero garantiza un Sharpe ilusorio en el backtest.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| K-Fold aleatorio en series temporales | Falso descubrimiento de alfas inexistentes | Particiones cronológicas Walk-Forward obligatorias | Purga y embargo temporal entre conjuntos |
| Look-ahead bias por fechas de reporte contable | Resultados de backtest sobreoptimizados | Filtro por publication_timestamp | Bloqueo estricto de eventos con timestamp futuro |
| Conexión accidental de módulos semánticos al broker | Ejecución errónea de órdenes de capital | Reglas de firewall de red (Air-Gap) | Prohibir APIs de FIX en servidores de inferencia |

## 8. Validación propuesta

- **Hipótesis Falsable**: La validación Walk-Forward refleja fielmente el rendimiento real de las señales textuales en producción.
- **Métricas**: Correlación entre el Sharpe de validación Walk-Forward y el Sharpe en producción.
- **Criterio de Rechazo**: Correlación >= 0.70 en pruebas con datos no vistos.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
