# JEV-P04-019: Reglas de Reutilización, Caducidad (TTL) e Invalidación de Contexto en Flujos Largos

## 1. Respuesta directa y decisión que permite tomar

En procesos operativos de larga duración (e.g., una postulación de financiamiento vehicular que dura 10 días en Wheelwork, o una orden de cobertura financiera que permanece latente durante horas en QRT), reutilizar ciegamente el payload `state` recopilado en pasos anteriores introduce el riesgo de **Decisiones sobre Realidades Fantasma (*Stale Context Decisions*)**: dictámenes emitidos por Jev 1.13 basados en saldos de cuenta agotados, tipos de cambio desactualizados, antecedentes crediticios caducados o identidades revocadas.

Para garantizar que toda inferencia en flujos asíncronos y multietapa se ejecute sobre información vigente sin re-extraer innecesariamente datos inmutables, la arquitectura debe implementar una **Política Multicapa de Ciclo de Vida del Contexto (Context Lifecycle & TTL)**:

1. **Estratificación de Variables por Volatilidad Temporal**: Cada campo o bloque dentro del `state` debe asociarse a una clase de caducidad estricta (TTL):
   - *Clase Volátil (Mercado / Transacciones en Tiempo Real)*: TTL de 10 a 60 segundos (e.g., tipo de cambio FX, cotización de un bono, balance disponible en billetera).
   - *Clase Operacional (Saldos y Estados de Gestión)*: TTL de 15 minutos a 4 horas (e.g., estado de una factura en el SII, inventario disponible de vehículos, deuda en mora).
   - *Clase Documental de Negocio (Ingresos y Solvencia)*: TTL de 30 a 60 días (e.g., última liquidación de sueldo, carpeta tributaria anual).
   - *Clase Estática (Identidad y Legal)*: TTL de 180 a 365 días (e.g., escritura de constitución de sociedad, validación biométrica de cédula).
2. **Compuerta de Validación Temporal Pre-Inferencia en CPU (Staleness Gate)**:
   - Antes de llamar a `POST /v1/systemone`, el ensamblador en CPU verifica la condición de frescura para cada variable causal: $t_{\text{actual}} - t_{\text{captura}} \le \text{TTL}_{\text{clase}}$.
   - Si alguna variable causal ha caducado, la inferencia se suspende y el sistema dispara un evento de re-adquisición asíncrona hacia la fuente canónica.
3. **Invalidación Reactiva Basada en Eventos (Event-Driven Invalidation)**:
   - Ciertas transiciones de estado invalidan el contexto de forma instantánea mediante webhooks o colas de mensajería (e.g., `ORDEN_CANCELADA`, `ALERTA_FRAUDE_ACTIVADA`, `RECLAMO_INGRESADO`), eliminando inmediatamente cualquier caché activa sin esperar el vencimiento del TTL.
4. **Firma Criptográfica de Estado con Epoch Canónico**:
   - El hash `state_sha256` (RFC 8785) debe incorporar la versión del snapshot o la marca de tiempo de la actualización. Esto garantiza que la caché de logits de Jev 1.13 no devuelva una respuesta anterior si el contexto ha mutado.

**Decisión que permite tomar**: Prohibir la persistencia estática del payload `state` entre diferentes etapas de un flujo de negocio sin verificación previa de TTL. Establecer un middleware de frescura temporal en CPU que re-valide las variables volátiles antes de cada invocación a Jev.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Gestión del ciclo de vida, almacenamiento en caché, caducidad e invalidación del contexto (`state`) para Jev 1.13 en flujos transaccionales y asíncronos en QRT y Wheelwork.
- **Términos formalizados**:
  - *Stale Context (Contexto Obsoleto)*: Conjunto de datos que representaba fielmente el estado del mundo en el momento $t_0$, pero que en el momento $t_1$ de la inferencia difiere de la realidad operativa.
  - *Time-To-Live (TTL)*: Ventana temporal durante la cual un dato se presume suficientemente fidedigno para permitir decisiones operacionales sin re-consulta.
  - *Event-Driven Invalidation (Invalidación Dirigida por Eventos)*: Purga forzada e inmediata de un estado almacenado ante la ocurrencia de un cambio de negocio crítico.
  - *Staleness Gate (Compuerta de Obsolescencia)*: Verificación algorítmica en CPU que bloquea la inferencia si los datos han superado su vida útil permitida.
- **Versiones de referencia**: Jev 1.13 (`typesafe-sdk >= 0.7.0`), Redis 7.x / Memcached (para capa de caché), Python 3.11+.
- **Supuestos fundamentales**:
  1. El coste de re-consultar una API externa volátil (e.g., tipo de cambio) es órdenes de magnitud menor que el coste de una decisión errónea basada en datos vencidos.
  2. Todos los nodos del sistema sincronizan sus relojes mediante Network Time Protocol (NTP) con una desviación inferior a 100 milisegundos.

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Ejemplo sintético trabajado: Gestor de Contexto con TTL y Frescura Temporal en Python

```python
# Ejemplo ilustrativo no ejecutado
"""
Módulo de Gestión de Ciclo de Vida y Frescura de Contexto para Jev 1.13.
"""
from datetime import datetime, timezone, timedelta
from typing import Dict, Any, Tuple
import hashlib
import json

class ContextLifecycleManager:
    # Definición de TTLs por categoría de datos
    TTL_CONFIG = {
        "fx_mercado": timedelta(seconds=60),
        "saldo_operacional": timedelta(minutes=15),
        "documento_ingreso": timedelta(days=30),
        "identidad_maestra": timedelta(days=180)
    }

    def __init__(self):
        # Almacén de contexto simulado (en producción sería Redis o Postgres)
        self.context_store: Dict[str, Dict[str, Any]] = {}

    def save_feature(self, entity_id: str, feature_key: str, value: Any, category: str):
        now = datetime.now(timezone.utc)
        if entity_id not in self.context_store:
            self.context_store[entity_id] = {}

        self.context_store[entity_id][feature_key] = {
            "value": value,
            "category": category,
            "updated_at": now
        }

    def invalidate_feature(self, entity_id: str, feature_key: str):
        """Invalidación forzada por evento (Webhook)."""
        if entity_id in self.context_store and feature_key in self.context_store[entity_id]:
            del self.context_store[entity_id][feature_key]

    def get_fresh_context(self, entity_id: str) -> Tuple[bool, Dict[str, Any], list]:
        """Comprueba frescura temporal y ensambla el estado si es válido."""
        if entity_id not in self.context_store:
            return False, {}, ["ENTIDAD_NO_ENCONTRADA"]

        now = datetime.now(timezone.utc)
        fresh_state = {}
        stale_keys = []

        for key, item in self.context_store[entity_id].items():
            category = item["category"]
            ttl = self.TTL_CONFIG.get(category, timedelta(minutes=5))
            age = now - item["updated_at"]

            if age > ttl:
                stale_keys.append({"key": key, "category": category, "age_seconds": round(age.total_seconds(), 1)})
            else:
                fresh_state[key] = item["value"]

        if stale_keys:
            return False, {}, stale_keys

        # Añadir metadata de trazabilidad
        fresh_state["_context_metadata"] = {
            "entity_id": entity_id,
            "assembled_at_utc": now.isoformat(),
            "status": "ALL_FEATURES_FRESH"
        }
        return True, fresh_state, []

# Simulación de ejecución
if __name__ == "__main__":
    manager = ContextLifecycleManager()
    entity = "CLI-5544"

    # Ingesta inicial de datos en t0
    manager.save_feature(entity, "tipo_cambio_usd_clp", 950.5, "fx_mercado")
    manager.save_feature(entity, "saldo_disponible_clp", 2500000, "saldo_operacional")
    manager.save_feature(entity, "renta_mensual_clp", 1800000, "documento_ingreso")

    # 1. Consulta inmediata (t0 + 5 seg): Todo fresco
    is_valid, state, errors = manager.get_fresh_context(entity)
    print(f"Estado en t0 + 5s: ¿Válido para Jev? {is_valid}")
    print(f"Campos frescos: {list(state.keys())}")

    # 2. Simulación de obsolescencia: envejecemos artificialmente el tipo de cambio (90 segundos atrás)
    manager.context_store[entity]["tipo_cambio_usd_clp"]["updated_at"] = datetime.now(timezone.utc) - timedelta(seconds=90)

    is_valid_t1, state_t1, errors_t1 = manager.get_fresh_context(entity)
    print(f"\nEstado en t0 + 90s: ¿Válido para Jev? {is_valid_t1}")
    print(f"Alerta de obsolescencia en CPU: {errors_t1}")

    # 3. Invalidación reactiva por Webhook (Alerta de Fraude en Cuenta)
    manager.invalidate_feature(entity, "saldo_disponible_clp")
    print(f"\nDespués de webhook de invalidación: ¿Existe saldo? {'saldo_disponible_clp' in manager.context_store[entity]}")
```

### 5.2. Contraejemplo y Caso Límite: Disputa Cambiaria por Inferencia sobre Caché Latente en QRT

En una operación cuantitativa en QRT, se evalúa una orden de cobertura de divisas por $500,000$ USD:
- En $t_0 = 10:00:00$, el tipo de cambio USD/CLP es $920$ CLP. El sistema ensambla un `state` con este valor.
- La ejecución de la orden sufre una demora técnica en la red y se procesa a las $t_1 = 10:45:00$. Durante ese intervalo, una noticia económica dispara el dólar a $960$ CLP.
- **Falla catastrófica por reutilización de contexto**: Si el microservicio de decisión reutiliza el `state` ensamblado a las 10:00:00 sin compuerta de frescura temporal, Jev aprueba la cobertura asumiendo un costo en moneda local de $460$ millones de CLP, cuando el costo real de mercado es de $480$ millones de CLP, generando una pérdida inmediata de $20$ millones de CLP.
- **Manejo correcto**: Al evaluar $t_{\text{actual}} - t_{\text{captura}} = 45 \text{ min} > \text{TTL}_{\text{FX}} (60 \text{ s})$, la Staleness Gate en CPU aborta la inferencia, refresca la cotización en vivo y re-evalúa el juicio con el dato fáctico real de $960$ CLP.

## 6. Aplicación a nuestros desarrollos

### 6.1. Hechos verificables en proyectos existentes

1. **Wheelwork (Flujos Asíncronos de Arriendo)**:
   - Un cliente inicia una postulación el lunes, sube documentos el miércoles y la resolución final se emite el viernes.
   - *Hecho*: El estado de morosidad en el boletín comercial (DICOM/CMF) puede mutar durante esos 5 días; un postulante limpio el lunes puede haber entrado en mora ejecutiva el jueves.

2. **QRT (Gestión de Órdenes y Liquidación)**:
   - Administra órdenes que esperan condiciones de liquidez o eventos corporativos para ejecutarse.
   - *Hecho*: Las líneas de crédito interbancarias y las garantías colaterales fluctúan intradiariamente en función de la volatilidad del mercado.

### 6.2. Hipótesis de diseño para Jev

- **Hipótesis 1**: La imposición de una compuerta de frescura con TTLs estratificados previene el 100% de decisiones erróneas derivadas de datos financieros vencidos.
- **Hipótesis 2**: El almacenamiento en caché local de variables estáticas (TTL $> 30$ días) reduce el tráfico a bases de datos de clientes en un 65% en flujos multietapa.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla y mitigaciones

| Modo de Falla | Causa Raíz | Detección | Mitigación Arquitectónica |
|---|---|---|---|
| **Desincronización de Relojes (Clock Skew)** | Desviación de NTP en un servidor local que calcula edades de datos negativas o infladas. | Monitor de sincronización NTP con alerta si $|\Delta t_{\text{reloj}}| > 200 \text{ ms}$. | Usar marcas temporales basadas en timestamps monotónicos o servidores centrales de tiempo. |
| **Tormenta de Re-Consultas (Thundering Herd)** | Expiración simultánea del TTL para miles de usuarios activos que satura la base de datos externa. | Monitoreo de picos de conexiones en el microservicio de origen. | Implementar TTL con fluctuación aleatoria (*jitter* probabilístico $\pm 10\%$). |
| **Omisión de Webhook por Pérdida de Red** | Un evento crítico de invalidación no llega al nodo debido a un timeout HTTP. | Registro de eventos no reconocidos en cola de mensajería (Dead Letter Queue). | TTL pasivo como seguro de vida secundario que fuerza el refresco aunque falle el webhook. |

### 7.2. Condiciones de NO uso

- **NO utilizar el mismo TTL para todas las variables de un modelo**: Configurar un TTL universal de 24 horas es un error severo; lo que es fresco para una escritura legal es letal para una cotización bursátil.
- **NO re-evaluar con Jev si la única variable actualizada es puramente cuantitativa**: Si lo único que cambió fue un precio que sobrepasó un límite duro, una regla en CPU debe actuar sin gastar inferencia en Jev.

## 8. Validación propuesta

> **Nota**: Validación técnica propuesta, no ejecutada en producción.

### 8.1. Diseño experimental
- **Hipótesis falsable**: La implementación de la Staleness Gate con política de TTL estratificada evitará el 100% de las decisiones desalineadas por datos obsoletos en un entorno de simulación asíncrono de 1,000 eventos distribuidos a lo largo de 7 días, con un sobrecoste de llamadas de refresco menor al $8\%$.
- **Dataset sintético de prueba**: 1,000 procesos de solicitud con eventos de mutación de estado programados aleatoriamente (e.g., pagos sobrevenidos, alertas de riesgo, variaciones de tasa FX).
- **Métricas y umbrales**:
  - Tasa de Decisiones con Datos Obsoletos: $0.0\%$.
  - Overhead de Latencia por Verificación en CPU: $< 1$ milisegundo.
  - Tasa de Refresco Oportuno ante Webhook: $> 99.9\%$.
- **Criterio de rechazo**: Si una sola inferencia se ejecuta con una variable volátil cuya edad supere el TTL establecido, el sistema de caché se considera inseguro y debe bloquearse el modo persistente.
- **Presupuesto estimado**: 1,000 inferencias API Jev en simulación = $0.50 USD; entorno local de Redis.
