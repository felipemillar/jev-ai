# JEV-P04-012: Representación de Temporalidad, Vigencia y Revisiones: Protocolo de Superación Cronológica

## 1. Respuesta directa y decisión que permite tomar

En modelos de lenguaje estáticos y codificadores densos, los tokens carecen de una flecha del tiempo intrínseca: un hecho ocurrido hace tres años ("el cliente adeuda \$10,000 USD") compite por atención en igualdad de condiciones con un hecho ocurrido hace una hora ("el cliente liquidó la totalidad de su deuda"), arriesgando que Jev otorgue mayor autoridad al dato antiguo por mera prominencia léxica o cercanía gramatical.

Para garantizar que los datos actualizados prevalezcan y que las versiones derogadas pierdan autoridad probatoria sin amputar el historial de auditoría, la arquitectura debe implementar el **Protocolo de Superación Cronológica y Bitemporalidad en JSON (*Temporal Supersession Protocol*)**:
1. **Estandarización Canónica ISO 8601 en UTC**: Toda marca temporal debe formatearse obligatoriamente en UTC canónico (`YYYY-MM-DDTHH:MM:SSZ`), eliminando discrepancias por husos horarios locales o formatos tipográficos ambiguos (`DD/MM` vs `MM/DD`).
2. **Atributos Explícitos de Vigencia y Derogación en CPU**: Cada registro en el `state` debe incluir metadatos calculados previamente en CPU:
   - `effective_date_utc`: Fecha a partir de la cual el hecho produce efectos.
   - `expiration_date_utc`: Fecha de caducidad formal (o cadena `"INDEFINIDO"`).
   - `is_active_version`: Booleano determinista (`true` si `effective_date <= decision_now <= expiration_date`).
   - `superseded_by_id`: Identificador de la versión posterior que anuló o modificó este registro.
3. **Estructura Bipartita en el Estado (`Vigente` vs `Histórico`)**: Separar el `state` en dos claves de primer nivel: `estado_activo_vigente` (que contiene exclusivamente la versión actual) y `trazabilidad_historica` (array con revisiones superadas ordenadas cronológicamente).
4. **Instrucción de Prelación Temporal en Criterios de Jev**: Formular las preguntas indicando explícitamente que la evaluación debe recaer sobre la clave `estado_activo_vigente`, utilizando el historial únicamente si la pregunta indaga sobre reincidencia o evolución.
5. **Aislamiento Estricto de Fuga Temporal (*Lookahead Bias*)**: En backtesting y simulaciones, aplicar una compuerta determinista que purgue cualquier registro cuya fecha de publicación sea posterior al instante de corte de la decisión ($\tau_{\text{corte}}$).

**Decisión que permite tomar**: Prohibir la inyección de historiales documentales desestructurados donde convivan versiones vigentes y obsoletas sin tipado temporal. Exigir la estructura bipartita (`Vigente` vs `Histórico`) con marcas ISO 8601 calculadas en CPU para todos los flujos de QRT y Wheelwork.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Modelado de datos temporales, versionado de políticas y contratos, y prevención de sesgo de anticipación (*lookahead bias*) en Jev 1.13.
- **Términos formalizados**:
  - *Superación Cronológica (Temporal Supersession)*: Regla ontológica donde una versión posterior válida deroga formalmente los efectos de una versión previa.
  - *Tiempo de Evento vs. Tiempo de Ingesta (Bitemporalidad)*: Distinción entre el momento en que ocurrió el hecho en el mundo real (`event_time`) y el momento en que el dato estuvo disponible en la base de datos (`ingestion_time`).
  - *Fuga Temporal (Lookahead Bias)*: Error en el que se suministra al modelo información que no estaba disponible en el momento en que la decisión debía tomarse.
- **Versiones de referencia**: Jev 1.13 (`typesafe-sdk >= 0.7.0`), Python 3.11+, ISO 8601.
- **Supuestos fundamentales**:
  1. El sistema anfitrión dispone de un reloj sincronizado por protocolo NTP con precisión inferior a 10 ms.
  2. Las fuentes documentales proporcionan metadatos explícitos de fecha de emisión y número de revisión.

### 4.1. Estructura del Estado Bitemporal Bipartito en JSON

Para erradicar la ambigüedad de vigencia, el `state` se serializa en dos compartimentos semánticos estancos:

```json

  "entidad_id": "POL-RRHH-2026",
  "instante_evaluacion_utc": "2026-09-19T23:50:00Z",
  "estado_activo_vigente": {
    "version_id": "v3.0.0",
    "effective_date_utc": "2026-01-01T00:00:00Z",
    "expiration_date_utc": "2026-12-31T23:59:59Z",
    "politica_remota": "Trabajo 100% remoto autorizado para ingenieros senior sin requerir presencialidad."
  },
  "trazabilidad_historica_superada": [
    {
      "version_id": "v1.0.0",
      "effective_date_utc": "2024-01-01T00:00:00Z",
      "superseded_at_utc": "2025-12-31T23:59:59Z",
      "politica_remota": "Presencialidad obligatoria 3 días por semana en oficinas corporativas."
    }
  ]
}
```

### 4.2. Inferencia Dirigida en Jev
La pregunta tipada en `Noul` se formula apuntando directamente a la clave de vigencia:
```json
{
  "q_remoto_permitido": {
    "type": "noul",
    "instructions": "¿Autoriza la cláusula descrita en 'estado_activo_vigente' el trabajo 100% remoto para ingenieros senior?"
  }
}
```
Al focalizar el criterio sobre `estado_activo_vigente`, Jev asigna $p = 0.99$ con certidumbre máxima, ignorando por completo la cláusula histórica derogada de presencialidad de 2024.

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Ejemplo sintético trabajado: Motor de Enrutamiento Temporal en Python

```python
# Ejemplo ilustrativo no ejecutado
"""
temporal_router.py
Módulo de resolución temporal y gobierno de vigencia para estados de Jev.
"""
from datetime import datetime, timezone
from dataclasses import dataclass
from typing import List, Dict, Any

@dataclass(frozen=True)
class PolicyVersion:
    version_id: str
    effective_utc: str
    expiration_utc: str
    rule_text: str

class TemporalStateBuilder:
    def __init__(self, current_time_utc: str):
        self.now = datetime.fromisoformat(current_time_utc)

    def compile_bitemporal_state(self, entity_id: str, versions: List[PolicyVersion]) -> Dict[str, Any]:
        active_version = None
        historical_versions = []

        for v in versions:
            eff_dt = datetime.fromisoformat(v.effective_utc)
            exp_dt = datetime.fromisoformat(v.expiration_utc)

            # Comprobar si la versión está vigente en el instante 'now'
            if eff_dt <= self.now <= exp_dt:
                active_version = {
                    "version_id": v.version_id,
                    "effective_date_utc": v.effective_utc,
                    "expiration_date_utc": v.expiration_utc,
                    "contenido": v.rule_text
                }
            elif exp_dt < self.now:
                historical_versions.append({
                    "version_id": v.version_id,
                    "effective_date_utc": v.effective_utc,
                    "expiration_date_utc": v.expiration_utc,
                    "contenido": v.rule_text,
                    "estado": "SUPERADO_HISTORICO"
                })
            else:
                # Versión futura (aún no entra en vigencia) -> Descartar para evitar Lookahead Bias
                print(f"[AUDIT] Descartando versión futura no vigente: {v.version_id} ({v.effective_utc})")

        if not active_version:
            raise ValueError(f"No existe ninguna versión activa vigente para la fecha {self.now.isoformat()}")

        # Ordenar historial cronológicamente ascendente
        historical_versions.sort(key=lambda x: x["effective_date_utc"])

        return {
            "entidad_id": entity_id,
            "instante_corte_utc": self.now.isoformat(),
            "estado_activo_vigente": active_version,
            "trazabilidad_historica": historical_versions
        }

if __name__ == "__main__":
    builder = TemporalStateBuilder(current_time_utc="2026-09-19T23:50:00Z")

    versiones_politica = [
        PolicyVersion(
            version_id="POL-2024",
            effective_utc="2024-01-01T00:00:00Z",
            expiration_utc="2025-12-31T23:59:59Z",
            rule_text="Se prohíbe el uso de herramientas de IA sin aprobación del comité de riesgos."
        ),
        PolicyVersion(
            version_id="POL-2026",
            effective_utc="2026-01-01T00:00:00Z",
            expiration_utc="2026-12-31T23:59:59Z",
            rule_text="Se autoriza el uso de modelos System One tipados (Jev) para evaluación de riesgos en producción."
        ),
        PolicyVersion(
            version_id="POL-FUTURA-2027",
            effective_utc="2027-01-01T00:00:00Z",
            expiration_utc="2027-12-31T23:59:59Z",
            rule_text="Revisión experimental 2027..."
        )
    ]

    estado_compilado = builder.compile_bitemporal_state("POL-IA-01", versiones_politica)

    import json
    print("--- ESTADO BITEMPORAL COMPILADO PARA JEV ---")
    print(json.dumps(estado_compilado, indent=2, ensure_ascii=False))
```

### 5.2. Contraejemplo y caso límite: La Cláusula Derogada que Bloquea el Sistema

Un equipo concatena el texto íntegro de un manual de compras donde en la página 2 figura una política de 2018 que prohibía compras con tarjeta corporativa, y en la página 15 figura una enmienda de 2026 que las autoriza explícitamente:
- **Error**: El desarrollador no separa las secciones ni etiqueta la vigencia temporal.
- **Inferencia en Jev**: Ante la pregunta de `Noul`: *"¿Está autorizado el uso de tarjetas corporativas para este gasto?"*, Jev detecta la prohibición tajante de 2018 y la autorización de 2026 en el mismo contexto. Al ser proposiciones antagónicas, la probabilidad colapsa a $p = 0.51$ con certidumbre nula ($|2p-1| = 0.02$).
- **Consecuencia**: El pago legítimo queda congelado indefinidamente en la mesa de soporte humano.
- **Mitigación**: Al compilar el estado bitemporal, la regla de 2018 pasa a `trazabilidad_historica` y la de 2026 a `estado_activo_vigente`. Jev evalúa la versión vigente y aprueba la operación en $30\text{ ms}$ con $p = 0.99$.

## 6. Aplicación a nuestros desarrollos

### 6.1. Revisiones de Cifras Macroeconómicas en QRT
- **Hecho documentado**: Los datos de nóminas de empleo no agrícola (NFP) o crecimiento del PIB sufren revisiones retroactivas hasta 3 meses después de su primera publicación.
- **Integración propuesta**:
  - En QRT, cada dato económico se registrará con bitemporalidad estricta: `tiempo_referencia_economica` vs `tiempo_publicacion_efectiva`.
  - El evaluador de Jev consumirá exclusivamente la cifra que estaba efectivamente publicada en el instante del trade simulado, eliminando cualquier sesgo retrospectivo en los modelos cuantitativos.

### 6.2. Vigencia de Contratos y Tarifas en Wheelwork
- **Hecho documentado**: Wheelwork automatiza el pago a proveedores basándose en tarifas horarias pactadas por contrato.
- **Integración propuesta**:
  - Las tablas de tarifas se modelarán con `effective_date_utc` y `expiration_date_utc`.
  - Cuando Jev concilia una factura, el `state` inyectará en `estado_activo_vigente` la tarifa que correspondía a la fecha de prestación del servicio, previniendo sobrepagos o rechazos indebidos por aplicar tarifas desactualizadas.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla específicos
1. **Fallo por Desfase de Zona Horaria**: Enviar fechas con desfases locales (e.g. `UTC-4`) sin normalizar a UTC; a las 22:00 horas locales puede ser un día distinto al de UTC, induciendo decisiones desfasadas por un día entero.
   - *Control*: Todo timestamp debe ser parseado con `datetime.fromisoformat()` y convertido obligatoriamente a UTC con zona `Z` en CPU.
2. **Fallo por Ambigüedad en Cláusulas con Retroactividad Jurídica**: Documentos que declaran retroactividad expresa (e.g., *"Esta política rige retroactivamente desde octubre de 2025"*).
   - *Control*: El preprocesador en CPU debe ajustar `effective_date_utc` a la fecha retroactiva declarada, documentando la justificación en el log de auditoría.

### 7.2. Condiciones taxativas de no uso
- **No permitir que Jev intente calcular por sí mismo si una fecha es anterior o posterior a otra mediante deducción textual**: Jev es un estimador semántico con capacidad jagged para aritmética de fechas; la comparación temporal `$now > expiration$` debe ejecutarse siempre en CPU determinista.

## 8. Validación propuesta (propuesta, no ejecutada)

- **Hipótesis falsable**: La estructuración del estado bajo el formato bitemporal bipartito (`estado_activo_vigente` vs `trazabilidad_historica`) elimina el **100%** de las interferencias atencionales causadas por políticas derogadas y mantiene una certidumbre $|2p-1| \ge 0.90$, mientras que la concatenación plana genera una tasa de indecisión/abstención ($p \in [0.40, 0.60]$) en más del **45%** de los casos.
- **Comparador / Línea base**: Concatenación plana desestructurada de versiones vigentes y obsoletas en el mismo párrafo.
- **Conjunto de datos sintético**: 300 pares de políticas sintéticas con derogaciones explícitas de condiciones normativas.
- **Métricas cuantitativas**:
  - Exactitud en la Selección de la Regla Vigente.
  - Tasa de Colapso de Certidumbre ($|2p-1| < 0.20$).
  - Tasa de Decisión Correcta sobre la Versión Activa.
- **Umbral de éxito**: Selección correcta de regla activa $= 100\%$; Tasa de colapso $\le 1\%$ (vs $\ge 45\%$ en línea base).
- **Criterio de rechazo**: Si la estructura bipartita induce al modelo a confundir la clave histórica con la clave vigente.
- **Presupuesto supuesto**: 600 llamadas a endpoints de Jev; coste API estimado en \$0.002; tiempo de cómputo en CPU: 5 minutos.
