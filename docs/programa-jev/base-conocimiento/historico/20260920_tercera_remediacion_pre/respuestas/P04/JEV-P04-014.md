# JEV-P04-014: Delegación de Cálculos a Código y Semántica a Jev: Preparación de Magnitudes, Monedas y Tiempos

## 1. Respuesta directa y decisión que permite tomar

Los modelos discriminativos basados en codificadores densos como Jev 1.13 presentan una **zona de ruptura de capacidad (*Capability Jaggedness*) severa en operaciones aritméticas implícitas**: son incapaces de restar balances flotantes, calcular variaciones porcentuales, convertir divisas a tipos de cambio variables o determinar si una marca horaria cae en fin de semana. Solicitar a Jev que realice cálculos matemáticos en el prompt produce errores aleatorios, colapsa la calibración y genera fallas de lógica en producción.

El principio rector no negociable de la arquitectura establece: **"El código en CPU calcula, normaliza y compara; Jev clasifica, juzga y calibra la semántica; el Sistema 2 delibera y redacta"**.

Para implementar esta división de responsabilidades de forma estricta:
1. **Pre-cálculo Aritmético Completo en CPU**: Toda resta, delta, margen de tolerancia o porcentaje debe calcularse deterministamente en el cliente antes de compilar el `state`. Al modelo no se le pide que reste $B - A$; se le inyectan los valores $A$, $B$, $\Delta$ y un indicador booleano explícito `excede_tolerancia_maxima: true`.
2. **Normalización Monetaria a Moneda Base Común (ISO 4217)**: Si la decisión compara importes en monedas heterogéneas (USD, EUR, CLP), el preprocesador en CPU convierte los importes a una divisa base fija aplicando la tasa de cambio vigente, inyectando tanto el valor original como el valor normalizado.
3. **Estandarización Temporal UTC con Banderas de Negocio Contextuales**: Todos los timestamps se serializan en ISO 8601 UTC. Si la lógica depende del horario local (e.g., horario bancario o sesión de mercado), la CPU evalúa el calendario y adjunta indicadores booleanos precalculados (`es_horario_habil: false`, `sesion_mercado: "AFTER_HOURS"`).
4. **Discretización en Rangos Semánticos**: Cuando la magnitud numérica informa una categoría de riesgo, la CPU discretiza el continuo en rangos ordinales estandarizados.

**Decisión que permite tomar**: Prohibir preguntas a Jev que contengan operadores de cálculo ("cuál es la diferencia", "calcula el total", "aplica el 19% de IVA"). Toda condición aritmética debe resolverse previamente en CPU, delegando a Jev exclusivamente la valoración cualitativa del estado fáctico resultante.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Preparación de datos cuantitativos, monetarios y temporales para el campo `state` en Jev 1.13 en entornos transaccionales (QRT y Wheelwork).
- **Términos formalizados**:
  - *Capability Jaggedness en Aritmética*: Disparidad donde un modelo comprende semántica compleja de textos legales pero falla en operaciones aritméticas básicas de dos dígitos.
  - *Pre-cálculo Determinista*: Resolución de expresiones algebraicas mediante código nativo en CPU antes del ensamblaje del payload.
  - *Moneda Base Común*: Divisa de referencia a la cual se convierten todos los flujos para permitir comparaciones ordinales sin sesgo de tipo de cambio.
- **Versiones de referencia**: Jev 1.13 (`typesafe-sdk >= 0.7.0`), Python 3.11+, ISO 4217, ISO 8601.
- **Supuestos fundamentales**:
  1. La CPU del cliente ejecuta operaciones aritméticas de coma flotante en nanosegundos con coste computacional y monetario de cero.
  2. Las tasas de cambio de divisas provienen de fuentes oficiales auditadas sincronizadas periódicamente.

### 5.1. Ejemplo sintético trabajado: Módulo de Preparación Cuantitativa en Python

```python
# Ejemplo ilustrativo no ejecutado
"""
quantitative_preprocessor.py
Middleware de pre-cálculo aritmético y normalización de magnitudes para Jev.
"""
from datetime import datetime, timezone
from typing import Dict, Any

class QuantitativeStateNormalizer:
    def __init__(self, base_currency: str = "USD", fx_rates_to_usd: Dict[str, float] = None):
        self.base_currency = base_currency
        self.fx_rates = fx_rates_to_usd or {"USD": 1.0, "EUR": 1.08, "CLP": 0.00106}

    def prepare_financial_state(
        self,
        invoice_id: str,
        declared_amount: float,
        declared_currency: str,
        invoiced_amount: float,
        invoiced_currency: str,
        tolerance_pct: float = 2.0
    ) -> Dict[str, Any]:
        # 1. Normalización de Divisas a Moneda Base en CPU
        rate_decl = self.fx_rates[declared_currency.upper()]
        rate_inv = self.fx_rates[invoiced_currency.upper()]

        declared_usd = declared_amount * rate_decl
        invoiced_usd = invoiced_amount * rate_inv

        # 2. Aritmética Determinista en CPU
        delta_usd = invoiced_usd - declared_usd
        delta_pct = (delta_usd / declared_usd) * 100.0 if declared_usd > 0 else 0.0
        exceeds_tolerance = abs(delta_pct) > tolerance_pct

        # 3. Ensamblaje del Estado JSON para Jev
        state = {
            "invoice_id": invoice_id,
            "moneda_base_calculo": self.base_currency,
            "cifras_declaradas": {
                "monto_original": declared_amount,
                "moneda_original": declared_currency.upper(),
                "equivalente_usd": round(declared_usd, 2)
            },
            "cifras_facturadas": {
                "monto_original": invoiced_amount,
                "moneda_original": invoiced_currency.upper(),
                "equivalente_usd": round(invoiced_usd, 2)
            },
            "calculos_deterministas_cpu": {
                "diferencia_neta_usd": round(delta_usd, 2),
                "desviacion_porcentual": round(delta_pct, 2),
                "umbral_tolerancia_pct": tolerance_pct,
                "supera_tolerancia_autorizada": exceeds_tolerance
            }
        }
        return state

if __name__ == "__main__":
    normalizer = QuantitativeStateNormalizer()

    # Factura en Euros comparada contra orden de compra en Dólares
    state_payload = normalizer.prepare_financial_state(
        invoice_id="INV-9902",
        declared_amount=10000.0,
        declared_currency="USD",
        invoiced_amount=9500.0,
        invoiced_currency="EUR",  # 9500 * 1.08 = 10,260 USD (+2.6% de diferencia)
        tolerance_pct=2.0
    )

    import json
    print("--- ESTADO PREPARADO CON CÁLCULOS DETERMINISTAS EN CPU ---")
    print(json.dumps(state_payload, indent=2, ensure_ascii=False))
```

### 5.2. Contraejemplo y caso límite: La Pregunta de Aritmética Implícita que Falla

Un desarrollador envía el texto crudo: `"Orden PO-10: 10,000 USD. Factura: 9,500 EUR (Tasa 1.08 USD por EUR)."`
Y le formula a Jev la siguiente pregunta de `Noul`:
- **Pregunta Prohibida**: `"¿Es el importe facturado en euros convertido a dólares superior al importe de la orden por más de un 2%?"`
- **Fallo de Inferencia**: Jev carece de una unidad aritmético-lógica (ALU) en su pase de codificación directa. El modelo ve el número $9,500$ y lo compara textualmente con $10,000$, concluyendo erróneamente que $9,500 < 10,000$ y emitiendo $p = 0.02$ (Falso Negativo).
- **Consecuencia**: El sobreprecio real (\$260 USD) se aprueba silenciosamente sin revisión.
- **Mitigación**: Con el preprocesamiento en CPU, Jev recibe la clave precalculada `"supera_tolerancia_autorizada": true`. La pregunta se formula: *"¿Informa el estado que la desviación supera la tolerancia autorizada?"*, y Jev responde $p = 0.99$ con certidumbre perfecta.

## 6. Aplicación a nuestros desarrollos

### 6.1. Separación Aritmética en Motores de Trading (QRT)
- **Hecho documentado**: Los cálculos de slippage, volatilidad realizada y valor en riesgo (VaR) se ejecutan en microsegundos en bibliotecas optimizadas de C++ / NumPy.
- **Integración propuesta**:
  - En QRT, se prohíbe formular preguntas semánticas a Jev que involucren umbrales numéricos complejos sin pre-cálculo.
  - La CPU calcula el ratio de Sharpe, la distancia a la banda de Bollinger y el desvío en pips, inyectando estos deltas y sus banderas booleanas en el `state`.
  - Jev evalúa si la justificación textual del comunicado de prensa explica congruentemente dicho desvío cuantitativo.

### 6.2. Conciliación de Gastos y Facturas en Wheelwork
- **Hecho documentado**: Wheelwork concilia comprobantes de compras corporativas donde concurren múltiples divisas y porcentajes de impuestos locales (IVA).
- **Integración propuesta**:
  - El motor de backend ejecutará el desglose aritmético de impuestos y conversión a moneda funcional de la empresa.
  - El estado inyectará las diferencias ya calculadas. Jev se limitará a clasificar la tipología del gasto y su adecuación a las políticas internas.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla específicos
1. **Fallo por Desincronización de Tasas FX**: Utilizar tasas de cambio desactualizadas en el preprocesador de CPU, induciendo errores cuantitativos antes de la llamada a Jev.
   - *Control*: Mantener un servicio local de caché de tipos de cambio con TTL de 5 minutos alimentado por proveedores oficiales.
2. **Fallo por Redondeo Prematuro de Flotantes**: Redondear cantidades intermedias a enteros en CPU, introduciendo errores acumulativos de centavos que disparan falsas alarmas.
   - *Control*: Conservar precisión de doble punto flotante (float64) en todos los cálculos intermedios de CPU y redondear únicamente al serializar a JSON.

### 7.2. Condiciones taxativas de no uso
- **No solicitar jamás a Jev la conversión de husos horarios locales mediante instrucciones del prompt**: La conversión de zonas horarias con horario de verano (DST) es un problema determinista resuelto por librerías como `zoneinfo` en Python; transferir esta tarea a Jev garantiza errores periódicos en los cambios de estación.

## 8. Validación propuesta (propuesta, no ejecutada)

- **Hipótesis falsable**: La resolución previa en CPU de cálculos aritméticos y conversiones de divisa, en comparación con solicitar cálculos aritméticos implícitos en el prompt de Jev, reduce la tasa de errores de decisión en transacciones multidivisa del **42%** a **0%**, manteniendo una reproducibilidad determinista del **100%**.
- **Comparador / Línea base**: Inferencia donde se suministran importes en divisas mixtas y se solicita a Jev que aplique la tasa cambiaria y calcule la desviación en el prompt.
- **Conjunto de datos sintético**: 400 transacciones multidivisa sintéticas (USD, EUR, GBP, CLP) con desviaciones cercanas al umbral de tolerancia ($\pm 1\%$).
- **Métricas cuantitativas**:
  - Tasa de Error Aritmético Inducido en Decisión.
  - Certidumbre media $|2p-1|$ de Jev.
  - Latencia computacional en CPU vs llamada a API.
- **Umbral de éxito**: Tasa de error con pre-cálculo $= 0\%$; Tasa de error en línea base $\ge 35\%$.
- **Criterio de rechazo**: Si la delegación a CPU no muestra ventajas perceptibles en exactitud frente al cálculo implícito en el prompt.
- **Presupuesto supuesto**: 800 llamadas a Jev; coste API estimado en \$0.003; tiempo de cómputo en CPU: 5 minutos.
