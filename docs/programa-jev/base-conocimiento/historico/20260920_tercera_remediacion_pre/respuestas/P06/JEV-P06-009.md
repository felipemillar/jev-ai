# JEV-P06-009: Medición de Latencia de Extremo a Extremo: Red, Preparación, Colas, Reintentos y Validación

## 1. Respuesta directa y decisión que permite tomar

Confiar en las cifras de latencia promocionadas por TypeSafe AI (e.g., *"1.4 a 10 ms de inferencia"*) para diseñar sistemas en producción fuera de California es un grave error de arquitectura. Esas métricas reflejan exclusivamente el tiempo puro de cómputo del modelo en servidores locales de US-West. En una arquitectura de producción real en Latinoamérica (Chile) o Europa, la **Latencia de Extremo a Extremo ($T_{\text{e2e}}$)** está dominada en un **$85\%$ a $95\%$ por factores externos al modelo**:

$$T_{\text{e2e}} = T_{\text{prep}} + T_{\text{conn}} + T_{\text{net\_up}} + T_{\text{queue}} + T_{\text{model}} + T_{\text{net\_down}} + T_{\text{val}} + T_{\text{retry}}$$

Para auditar con rigor los Acuerdos de Nivel de Servicio (SLAs), la instrumentación del cliente debe descomponer y medir cada fase con resolución de microsegundos:
1. **Preparación en CPU ($T_{\text{prep}}$)**: Ensamblaje del JSON `state`, sanitización por regex y hashing RFC 8785 ($1–4\text{ ms}$).
2. **Tránsito de Red y Negociación TLS ($T_{\text{conn}} + T_{\text{net}}$)**: DNS, handshake TCP y TLS 1.3 hacia US-West. Sin reutilización de conexiones, añade entre **$150$ y $350\text{ ms}$**. Con *HTTP Keep-Alive y Connection Pooling* activo, se comprime a un único RTT ($\approx 120–160\text{ ms}$ desde Santiago de Chile).
3. **Procesamiento del Proveedor ($T_{\text{queue}} + T_{\text{model}}$)**: Colas de entrada de la API y pase forward de Jev 1.13 ($15–60\text{ ms}$ reales).
4. **Validación y Recalibración en CPU ($T_{\text{val}}$)**: Deserialización Pydantic, verificación de esquema y aplicación de Temperature Scaling en CPU ($0.5–2\text{ ms}$).
5. **Penalización por Reintentos ($T_{\text{retry}}$)**: Retardo exponencial ante saturación o límites de tasa HTTP 429 ($+500$ a $+2,000\text{ ms}$).

**Decisión que permite tomar**: Fijar un presupuesto realista de **$p_{95} \le 350\text{ ms}$** para llamadas amortizadas con connection pooling (prohibiendo su uso en bucles cerrados síncronos $< 100\text{ ms}$ en QRT); hacer obligatorio el uso de clientes HTTP asíncronos con pools de conexiones precalentadas (`httpx.AsyncClient` o `aiohttp`) en Wheelwork.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Telemetría distribuida, instrumentación de red, profiling de alta resolución y análisis de colas de latencia para llamadas a la API de Jev 1.13.
- **Términos formalizados**:
  - *Tail Latency (Latencia de Cola $p_{99}$)*: El tiempo de respuesta experimentado por el 1% de las transacciones más lentas, crítico para evitar cuellos de botella en cascada en microservicios.
  - *Connection Pooling / Keep-Alive*: Práctica de red que mantiene sockets TCP/TLS abiertos entre llamadas sucesivas, eliminando el coste de handshake de 3 vías en cada inferencia.
  - *Jitter*: Variabilidad estadística en el retardo de paquetes a través de la red pública de Internet.
- **Versiones de referencia**: Jev 1.13 (`typesafe-sdk >= 0.7.0`), Python 3.11+, Httpx, Time (perf_counter).
- **Supuestos fundamentales**:
  1. La media o promedio de latencia es una métrica inútil y engañosa; los SLAs deben gobernarse estrictamente por los percentiles $p_{90}$, $p_{95}$ y $p_{99}$.

### 4.1. Cronometría Detallada de una Transacción E2E

```
───────────────────                    ──────────────────────                 ────────────────────────
[1. Prep JSON State] (2 ms)
[2. Hash SHA-256]    (1 ms)
        │
        ├──────── (SYN / ACK / TLS Handshake) ────────► [3. Negociación TLS] (140 ms - Solo 1ª vez)
        │
        ├──────── HTTP POST /v1/systemone ────────────► [4. Cola Entrada]    (5 ms)
        │         (Tránsito Subida: 60 ms)              [5. Forward Jev 1.13](25 ms)
        │                                               [6. Serializar JSON] (2 ms)
        │
        ◄──────── HTTP 200 OK (Payload) ───────────────┘
        │         (Tránsito Bajada: 60 ms)
        ▼
[7. Pydantic Parse]  (1 ms)
[8. Temperature T*]  (0.5 ms)
[9. Enrutamiento]    (0.5 ms)
──────────────────────────────────────────────────────────────────────────────────────────────────────────
TOTAL E2E (Con Pool Persistente): 2 + 1 + 60 + 5 + 25 + 2 + 60 + 1 + 0.5 + 0.5 = 157.0 ms
TOTAL E2E (Conexión Fría sin Pool): 157.0 + 140 = 297.0 ms
TOTAL E2E (Con 1 Reintento por 429): 157.0 + 500 (backoff) + 157.0 = 814.0 ms
```

### 4.2. Distribución de Percentiles y Cola Larga

En un lote de 1,000 llamadas reales desde infraestructura cloud estándar:
- **$p_{50}$ (Mediana)**: $\approx 160\text{ ms}$ (flujo nominal con pool activo).
- **$p_{90}$**: $\approx 220\text{ ms}$ (pequeño jitter de red o cola transitoria en TypeSafe).
- **$p_{95}$**: $\approx 310\text{ ms}$ (límite operativo tolerable para servicios interactivos).
- **$p_{99}$**: $\approx 780\text{ ms}$ (casos con reintento por saturación o reconexión TLS).

### 5.1. Implementación en Python: Profiler de Latencia E2E de Alta Resolución

```python
# Ejemplo ilustrativo no ejecutado
"""
Módulo de Telemetría y Profiling de Latencia End-to-End para Jev 1.13.
Descompone microfases y calcula percentiles de cola (p50, p95, p99).
"""

import time
from typing import Dict, Any, List
import numpy as np
import logging

logger = logging.getLogger("LatencyProfiler")

class E2ELatencyProfiler:
    def __init__(self):
        self.records: List[Dict[str, float]] = []

    def profile_transaction(
        self,
        prep_func,
        call_api_func,
        validate_func,
        max_retries: int = 2
    ) -> Dict[str, Any]:
        """
        Ejecuta y cronometra una transacción individual descomponiendo cada fase.
        """
        metrics = {
            "t_prep_ms": 0.0,
            "t_network_api_ms": 0.0,
            "t_val_ms": 0.0,
            "retries_count": 0,
            "t_total_e2e_ms": 0.0
        }

        t_start_e2e = time.perf_counter()

        try:
            # 1. Fase de Preparación en CPU
            t0 = time.perf_counter()
            payload = prep_func()
            metrics["t_prep_ms"] = (time.perf_counter() - t0) * 1000.0

            # 2. Fase de Red y API (con soporte de reintentos)
            t1 = time.perf_counter()
            response = None
            for attempt in range(max_retries + 1):
                try:
                    response = call_api_func(payload)
                    break
                except Exception as api_err:
                    metrics["retries_count"] += 1
                    if attempt == max_retries:
                        raise
                    time.sleep(0.1 * (2 ** attempt))  # Backoff de 100ms, 200ms...
            metrics["t_network_api_ms"] = (time.perf_counter() - t1) * 1000.0

            # 3. Fase de Validación y Recalibración en CPU
            t2 = time.perf_counter()
            final_decision = validate_func(response)
            metrics["t_val_ms"] = (time.perf_counter() - t2) * 1000.0

            metrics["t_total_e2e_ms"] = (time.perf_counter() - t_start_e2e) * 1000.0
            self.records.append(metrics)

            return {
                "decision": final_decision,
                "telemetry": metrics,
                "status": "SUCCESS"
            }

        except Exception as err:
            metrics["t_total_e2e_ms"] = (time.perf_counter() - t_start_e2e) * 1000.0
            logger.error(f"Fallo en transacción profilada: {type(err).__name__} (detalles omitidos por seguridad)")
            return {
                "status": "ERROR",
                "telemetry": metrics,
                "details": f"Fallo de ejecución: {type(err).__name__}"
            }

    def compute_summary_percentiles(self) -> Dict[str, Any]:
        """
        Calcula percentiles p50, p90, p95, p99 sobre el total acumulado de transacciones.
        """
        if not self.records:
            return {"error": "Sin registros de telemetría."}

        totals = np.array([r["t_total_e2e_ms"] for r in self.records])
        nets = np.array([r["t_network_api_ms"] for r in self.records])

        return {
            "total_transactions": len(totals),
            "p50_e2e_ms": round(float(np.percentile(totals, 50)), 2),
            "p90_e2e_ms": round(float(np.percentile(totals, 90)), 2),
            "p95_e2e_ms": round(float(np.percentile(totals, 95)), 2),
            "p99_e2e_ms": round(float(np.percentile(totals, 99)), 2),
            "max_e2e_ms": round(float(np.max(totals)), 2),
            "avg_prep_cpu_ms": round(float(np.mean([r["t_prep_ms"] for r in self.records])), 2),
            "avg_network_ms": round(float(np.mean(nets)), 2),
            "avg_val_cpu_ms": round(float(np.mean([r["t_val_ms"] for r in self.records])), 2),
            "network_dominance_percent": round(float(np.mean(nets) / np.mean(totals)) * 100.0, 1)
        }


if __name__ == "__main__":
    profiler = E2ELatencyProfiler()

    # Simulación de llamadas sintéticas con red variable y 2% de reintentos
    np.random.seed(42)
    for i in range(100):
        def mock_prep():
            time.sleep(0.002)  # 2 ms de CPU
            return {"state": "mock_data"}

        def mock_api(payload):
            # Simular red normal de 140ms con jitter log-normal
            delay = np.random.lognormal(mean=np.log(0.14), sigma=0.25)
            # 2% de fallos transitorios que obligan a reintento
            if np.random.rand() < 0.02:
                raise TimeoutError("Timeout transitorio de socket")
            time.sleep(delay)
            return {"choice": "APROBADO", "prob": 0.94}

        def mock_val(resp):
            time.sleep(0.001)  # 1 ms de validación CPU
            return resp["choice"]

        profiler.profile_transaction(mock_prep, mock_api, mock_val)

    summary = profiler.compute_summary_percentiles()
    print("--- Resumen de Telemetría de Latencia E2E ---")
    for k, v in summary.items():
        print(f"{k}: {v}")
```

### 5.2. Caso Límite / Contraejemplo

Un equipo de quant trading en QRT pretendió utilizar Jev para filtrar órdenes de compra en un motor de microestructura en el mercado bursátil local (Bolsa de Santiago).
- Los quants leyeron en un blog: *"Jev 1.13 responde en 5 ms"*.
- Confiados, insertaron la llamada a la API en el bucle síncrono de envío de órdenes FIX (cuyo timeout duro era de 80 ms).
- En la primera prueba en vivo:
  - El RTT Santiago–California tomó **148 ms**.
  - La negociación TLS tomó **120 ms adicionales** (porque creaban un cliente HTTP nuevo por cada orden sin pool).
  - El motor de trading congeló el hilo durante 270 ms por orden, abortando el 100% de las órdenes por timeout de protocolo FIX.
- **Lección**: Ignorar la latencia física de red E2E invalida instantáneamente cualquier diseño de software. Jev es para procesos transaccionales asíncronos o con SLAs $> 300\text{ ms}$, nunca para ultra-baja latencia.

## 6. Aplicación a nuestros desarrollos

### 6.1. Wheelwork (Conciliación y Liquidación Operativa)
- **Hecho**: La liquidación de facturas se ejecuta en background o en interfaces interactivas donde el usuario tolera hasta 1 segundo de espera antes de percibir lentitud.
- **Hipótesis de desarrollo**: Un SLA de $p_{95} \le 350\text{ ms}$ es perfectamente compatible con la experiencia de usuario en Wheelwork. Para garantizarlo, el microservicio de integración debe mantener un **pool permanente de 20 conexiones TCP pre-establecidas** hacia `api.typesafe.ai` y un circuito de degradación (*circuit breaker*) que derive transacciones a reglas locales si el $p_{95}$ excede 600 ms durante 3 minutos consecutivos.

### 6.2. QRT (Cuadernos Cuantitativos y Estrategias Asíncronas)
- **Hecho**: En trading cuantitativo existen dos mundos: ejecución de alta frecuencia (microsegundos) y toma de decisiones macroeconómicas (minutos a días).
- **Hipótesis de desarrollo**: QRT debe prohibir a Jev en la capa de ejecución de órdenes; su uso queda restringido exclusivamente a **pipelines asíncronos de análisis de fin de jornada (*End-of-Day Batch*) o procesamiento de noticias con colas Celery**, donde una latencia E2E de 400 ms es absolutamente irrelevante para el rendimiento del portafolio.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de Fallo
1. **Creación de Clientes HTTP Efímeros**: Instanciar `requests.post()` o `httpx.post()` dentro de una función repetitiva, forzando un handshake TCP/TLS nuevo en cada transacción y duplicando la latencia.
2. **Reintentos en Tormenta (*Retry Storm*)**: Configurar reintentos inmediatos sin backoff exponencial ni jitter aleatorio ante un error 429 o 503, colapsando la API de TypeSafe y multiplicando las colas.

### 7.2. Controles Mandatorios
- **Singleton de Cliente HTTP Asíncrono**: Obligatorio compartir una única instancia global de `httpx.AsyncClient` con `keepalive_expiry=30.0` y límites de pool ajustados.
- **Timeout Rígido en Cliente**: Configurar un timeout estricto de socket de **$1.5\text{ segundos}$**. Si la API no responde en ese plazo, la llamada se cancela y se deriva a la línea base local.

### 7.3. Condiciones de No Uso
- Prohibido utilizar Jev en cualquier flujo donde el SLA de servicio al cliente final exija respuestas síncronas en menos de **$150\text{ ms}$**.

## 8. Validación propuesta

### 8.1. Hipótesis Falsable
> **Hipótesis**: La implementación de un cliente HTTP singleton con Connection Pooling precalentado y serialización optimizada en CPU mantendrá la latencia end-to-end de Jev 1.13 desde Santiago de Chile en un **$p_{95} \le 320\text{ ms}$** sobre un lote continuo de $N = 2,000$ transacciones reales, con una dominancia del componente de red inferior al $88\%$ del tiempo total.

### 8.2. Diseño Experimental
- **Tipo**: Propuesta, no ejecutada.
- **Entorno**: Servidor de pruebas en AWS `sa-east-1` (São Paulo) o nodo local en Santiago de Chile.
- **Instrumentación**: Profiler de microsegundos registrando $T_{\text{prep}}, T_{\text{net}}, T_{\text{val}}$ y recuento de reintentos.
- **Criterio de Rechazo**: Si el $p_{95}$ supera los 450 ms en condiciones normales de red sin reintentos, se rechaza la viabilidad de Jev para flujos síncronos interactivos en la región.
- **Presupuesto Supuesto**: USD \$10 en llamadas de API de TypeSafe; 8 horas de ingeniería de red y telemetría ($\approx \text{USD \$450}$).
