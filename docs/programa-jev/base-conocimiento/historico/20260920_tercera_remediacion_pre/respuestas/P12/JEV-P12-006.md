# JEV-P12-006 — Observabilidad Desacoplada: Trazas, Métricas y Diferenciación de Causa Raíz

## 1. Respuesta directa y decisión que permite tomar

La observabilidad del sistema debe instrumentarse con OpenTelemetry desacoplando rigurosamente las métricas del modelo, del proveedor de infraestructura, de los datos de entrada y de la lógica de integración. Cada transacción debe emitir cuatro métricas fundamentales (Las 4 Señales de Oro): 1) Latencia por tramo; 2) Tasa de errores tipificados; 3) Tráfico (solicitudes por segundo); y 4) Saturación de recursos de red. Si una métrica se desvía, los dashboards deben señalar inequívocamente el componente responsable.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Telemetría distribuida, trazabilidad de solicitudes y diagnóstico de causa raíz (RCA).
- **Supuesto clave**: Plataforma de monitoreo y telemetría distribuida activa en el entorno de despliegue.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia operativa**: Estándares del consorcio OpenTelemetry y mejores prácticas del Google Cloud Architecture Framework para observabilidad.
- **Contraste de confiabilidad**: Se descartan suposiciones de estabilidad perfecta en servicios cloud de terceros sin mecanismos de fallback.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Estructura de spans en OpenTelemetry: Span 1 `PreprocessValidation` -> Span 2 `TypeSafeAPI_SystemOne` (con etiquetas: `http.status_code`, `model.version`, `prompt.tokens`) -> Span 3 `PostprocessDomainLogic`.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import logging

logger = logging.getLogger("P12_06")

def registrar_metricas_opentelemetry(span_name: str, atributos: dict):
    try:
        # Metadatos estructurados para exportador OTel
        registro_otel = {
            "span": span_name,
            "attributes": atributos
        }
        logger.info(f"OTEL_SPAN_EVENT: {registro_otel}")
    except Exception as err:
        logger.error(f"Fallo en emision de telemetria: {type(err).__name__} (detalles omitidos por seguridad)")
```

- **Contraejemplo / Caso borde**: Registrar solo 'falló la transacción' sin registrar el código HTTP ni la latencia impide saber si el problema fue de red, de cuota o del backend propio.

## 6. Aplicación práctica o transferencia

En el clúster Kubernetes donde se ejecutan los servicios centrales de Wheelwork y QRT.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Logs no estructurados sin etiquetas | Horas de investigación manual ante caídas | Trazabilidad distribuida con OpenTelemetry | Instrumentar spans en todas las llamadas remotas |
| Agotamiento de sockets por conexiones no cerradas | Fuga de descriptores de archivos y crash | Monitoreo de descriptores de socket | Context managers asíncronos obligatorios |
| Desbordamiento de colas de memoria ante picos | Out of Memory (OOM) en contenedor | Métricas de memoria en Prometheus | Colas acotadas con descarte ordenado (backpressure) |

## 8. Validación propuesta

- **Hipótesis Falsable**: La instrumentación estructurada con OpenTelemetry reduce el MTTR de incidentes de producción en un 60%.
- **Métricas**: Tiempo medio de resolución de incidentes (MTTR en minutos).
- **Criterio de Rechazo**: Identificación de causa raíz en < 15 minutos.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
