# JEV-P12-005 — Control de Concurrencia y Colas Dinámicas ante Cuotas y Capacidad Flotante

## 1. Respuesta directa y decisión que permite tomar

El sistema cliente no debe asumir que el límite de tasa de la API de TypeSafe o la capacidad de cómputo son constantes. Debe implementarse un mecanismo de control de concurrencia en cliente mediante semáforos asíncronos (`asyncio.Semaphore`) y un limitador de tasa adaptativo (Token Bucket) que reduzca dinámicamente el número de hilos concurrentes si se detecta un aumento en los errores HTTP 429 o un incremento anómalo en la latencia del servidor.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Control de saturación, throttling dinámico y algoritmos de control de congestión.
- **Supuesto clave**: Plataforma de monitoreo y telemetría distribuida activa en el entorno de despliegue.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia operativa**: Principios de ingeniería de tráfico de red (TCP Vegas / AIMD: Additive Increase / Multiplicative Decrease) adaptados a llamadas de API REST.
- **Contraste de confiabilidad**: Se descartan suposiciones de estabilidad perfecta en servicios cloud de terceros sin mecanismos de fallback.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Algoritmo AIMD: Si la llamada es exitosa, incrementar el límite de concurrencia en +1 hasta un máximo de 20. Si la API retorna un error 429 o latencia > 400 ms, multiplicar el límite de concurrencia por 0.5 de forma inmediata.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import asyncio, logging

logger = logging.getLogger("P12_05")

class ControladorConcurrenciaAdaptativo:
    def __init__(self, limite_inicial: int = 10):
        self.concurrencia_actual = limite_inicial
        self.semaforo = asyncio.Semaphore(limite_inicial)

    def ajustar_por_retroalimentacion(self, codigo_http: int, latencia_ms: float):
        try:
            if codigo_http == 429 or latencia_ms > 400.0:
                self.concurrencia_actual = max(2, int(self.concurrencia_actual * 0.5))
                logger.warning(f"Congestion detectada: reduciendo concurrencia a {self.concurrencia_actual}")
            elif codigo_http == 200 and latencia_ms < 200.0:
                self.concurrencia_actual = min(25, self.concurrencia_actual + 1)
        except Exception as err:
            logger.error(f"Fallo en ajuste de concurrencia: {type(err).__name__} (detalles omitidos por seguridad)")
```

- **Contraejemplo / Caso borde**: Despachar 500 peticiones en paralelo con `asyncio.gather` sin límite provocará una cascada masiva de errores 429 y bloqueo temporal de IP.

## 6. Aplicación práctica o transferencia

En los procesos de indexación batch y triaje nocturno de noticias en QRT.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Inundación de peticiones paralelas | Errores 429 masivos y denegación de servicio | Semáforos asíncronos en cliente | Ajuste dinámico de tasa con algoritmo AIMD |
| Agotamiento de sockets por conexiones no cerradas | Fuga de descriptores de archivos y crash | Monitoreo de descriptores de socket | Context managers asíncronos obligatorios |
| Desbordamiento de colas de memoria ante picos | Out of Memory (OOM) en contenedor | Métricas de memoria en Prometheus | Colas acotadas con descarte ordenado (backpressure) |

## 8. Validación propuesta

- **Hipótesis Falsable**: El control adaptativo AIMD reduce los errores 429 en un 98% ante ráfagas repentinas de tráfico.
- **Métricas**: Tasa de errores 429 recibidos durante picos de carga.
- **Criterio de Rechazo**: Errores 429 < 1% del tráfico total durante picos.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
