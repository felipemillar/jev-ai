# JEV-P15-013 — Revisión de Requisitos de Software Cuantitativo y Pruebas Estáticas Obligatorias

## 1. Respuesta directa y decisión que permite tomar

Jev puede asistir en la revisión semántica de especificaciones técnicas y requisitos de software cuantitativo (verificando que las descripciones de las fórmulas no contengan contradicciones léxicas o ambigüedades en definiciones de variables). No obstante, esta revisión semántica no sustituye las pruebas estáticas de código obligatorias: linters (Ruff, Flake8), verificadores de tipos estáticos (Mypy) y análisis sintáctico con `ast.parse()` siguen siendo requisitos deterministas indispensables en CI/CD.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Ingeniería de software para finanzas cuantitativas, aseguramiento de contratos y testing estático.
- **Supuesto clave**: Entorno de investigación documental hermético y aislado del motor de trading algorítmico.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia cuantitativa**: Estándares de desarrollo de software financiero de alta criticidad (ISO 25010 y directrices de ingeniería de software de QRT).
- **Contraste econométrico**: Se prohíbe deducir rentabilidad o predicción financiera a partir de exactitud de clasificación de texto.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Validación dual en CI: Paso 1 (Determinista): `mypy --strict` + `ruff check` + `pytest`. Paso 2 (Semántico con Jev): Verificación de coherencia entre los docstrings de las funciones y los requisitos documentados en la especificación técnica.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import ast, logging

logger = logging.getLogger("P15_13")

def validar_sintaxis_script_cuantitativo(codigo_python: str) -> bool:
    try:
        # Validacion estatica obligatoria en CPU
        ast.parse(codigo_python)
        return True
    except Exception as err:
        logger.error(f"Fallo sintactico en script de trading: {type(err).__name__} (detalles omitidos por seguridad)")
        return False
```

- **Contraejemplo / Caso borde**: Asumir que un script en Python para MetaTrader 5 funcionará en producción solo porque Jev clasificó su especificación como 'clara y bien redactada'.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Despliegue de código con errores de sintaxis | Caída de servicios en producción | Pruebas de compilación con ast.parse() obligatorias | Mypy estricto antes de cualquier release |
| Look-ahead bias por fechas de reporte contable | Resultados de backtest sobreoptimizados | Filtro por publication_timestamp | Bloqueo estricto de eventos con timestamp futuro |
| Conexión accidental de módulos semánticos al broker | Ejecución errónea de órdenes de capital | Reglas de firewall de red (Air-Gap) | Prohibir APIs de FIX en servidores de inferencia |

## 8. Validación propuesta

- **Hipótesis Falsable**: La suite de linters estáticos + AST detecta el 100% de los defectos sintácticos antes del merge.
- **Métricas**: Errores de sintaxis o tipo detectados en staging.
- **Criterio de Rechazo**: 0 errores sintácticos tolerados en la rama principal.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
