# JEV-P09-020 — Guía de Integración Mínima (Runbook) y Criterios Claros de Retirada

## 1. Respuesta directa y decisión que permite tomar

Todo proyecto que integre Jev debe disponer de un Runbook técnico mínimo que especifique: requisitos de red (TLS 1.3 saliente hacia api.typesafe.ai), variables de entorno requeridas, pruebas de humo con mocks, métricas de observabilidad (latencia p95, tasa de códigos HTTP 4xx/5xx) y criterios explícitos de retirada (Decommissioning Criteria). Si la latencia supera 350 ms p95 o el costo supera el valor aportado, el conmutador conmuta a reglas deterministas locales.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Manual operativo de puesta en marcha, observabilidad continua y protocolo de desmantelamiento.
- **Supuesto clave**: Conectividad saliente HTTPS habilitada hacia los endpoints oficiales de TypeSafe.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia documental**: Estándares de SRE (Site Reliability Engineering) de Google aplicados a dependencias externas de terceros.
- **Contraste de hipótesis**: Se descartan integraciones basadas en suposiciones de APIs genéricas de OpenAI o protocolos no oficiales.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Criterios de retirada automatizada: Si la tasa de disponibilidad cae bajo 99.0% en una ventana de 24 horas, o si los falsos positivos superan el 8% en la muestra de auditoría, se activa el interruptor de apagado (Kill Switch) sin intervención humana.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import logging

logger = logging.getLogger("P09_20")

class RunbookIntegracionJev:
    def __init__(self, latencia_umbral_ms: float = 350.0):
        self.latencia_umbral = latencia_umbral_ms
        self.activo = True

    def verificar_condicion_operativa(self, latencia_actual_ms: float, tasa_error: float) -> bool:
        try:
            if latencia_actual_ms > self.latencia_umbral or tasa_error > 0.05:
                self.activo = False
                logger.critical("Activando Kill Switch de Jev por degradacion de servicio")
                return False
            return True
        except Exception as err:
            logger.error(f"Fallo en verificacion de runbook: {type(err).__name__} (detalles omitidos por seguridad)")
            return False
```

- **Contraejemplo / Caso borde**: Integrar un servicio externo sin métricas de observabilidad ni plan de retirada deja a la empresa rehén de caídas de terceros sin posibilidad de reacción rápida.

En las operaciones de trading de QRT y servicios corporativos de Wheelwork como estándar de homologación.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Ausencia de plan de contingencia | Parálisis operativa durante caídas de TypeSafe | Simulación periódica de corte de API | Kill Switch probado en pre-producción |
| Corte total de conectividad saliente | Caída del servicio dependiente | Monitoreo sintético cada 60s | Conmutación automática a clasificador determinista local |
| Variación no notificada en contrato | Errores 422 en llamadas de API | Pruebas de contrato diarias en CI | Fijar versión y alertar ante discrepancias |

## 8. Validación propuesta

- **Hipótesis Falsable**: La existencia del Runbook y Kill Switch permite conmutar a operación degradada en menos de 10 segundos ante incidentes.
- **Métricas**: Tiempo de respuesta ante indisponibilidad del proveedor (MTTR).
- **Criterio de Rechazo**: MTTR < 15 segundos mediante activación de fallback.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
