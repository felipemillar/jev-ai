# JEV-P09-003 — Diferenciación Arquitectónica: Conector Gemini Notebooks vs Inferencia Jev

## 1. Respuesta directa y decisión que permite tomar

Existe una estricta separación de planos de red y de control entre el conector que consulta los Gemini Notebooks (NotebookLM) y el cliente que invoca la inferencia de Jev. El primero es un conector de gestión de conocimiento que opera vía protocolo MCP sobre stdio o HTTP para extraer fuentes y resúmenes. El segundo es un cliente de datos de baja latencia que ataca directamente `https://api.typesafe.ai/v1/systemone`. Confundir ambos conectores compromete la trazabilidad y la seguridad.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Deslinde conceptual y operativo entre la base documental de investigación y el motor de decisiones en producción.
- **Supuesto clave**: Conectividad saliente HTTPS habilitada hacia los endpoints oficiales de TypeSafe.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia documental**: La auditoría de Codex de septiembre de 2026 subraya que las respuestas anteriores mezclaban herramientas MCP de NotebookLM con primitivas del SDK de inferencia de Jev.
- **Contraste de hipótesis**: Se descartan integraciones basadas en suposiciones de APIs genéricas de OpenAI o protocolos no oficiales.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Plano de Conocimiento: `gemini-notebooks-mcp` (lectura documental, llamadas a fuentes canónicas, latencia > 1s). Plano de Ejecución: `typesafe_sdk` (inferencia Sistema 1, latencia < 200 ms, payloads atómicos `state` y `questions`).

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import logging
from typesafe_sdk import TypeSafeClient, Noul

logger = logging.getLogger("P09_03")

class DespachadorHibrido:
    def __init__(self):
        self.cliente_jev = TypeSafeClient(model="jev-1.13.0")
        
    def procesar_decision(self, texto: str) -> bool:
        try:
            # Inferencia pura en el plano de datos
            res = self.cliente_jev.system_one(
                state=texto,
                questions={"valido": Noul(instructions="Determinar validez formal")}
            )
            prob = res.answers["valido"].noul
            return prob >= 0.5
        except Exception as err:
            logger.error(f"Error en inferencia de plano de datos: {type(err).__name__} (detalles omitidos por seguridad)")
            return False
```

- **Contraejemplo / Caso borde**: Intentar invocar herramientas MCP de NotebookLM dentro de un bucle de trading de alta frecuencia de QRT provocará timeouts masivos y bloqueos de red.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Cruce de credenciales entre planos | Fuga de tokens de API / 401 | Separación de variables de entorno | Aislar NOTEBOOKLM_KEY de TYPESAFE_API_KEY |
| Corte total de conectividad saliente | Caída del servicio dependiente | Monitoreo sintético cada 60s | Conmutación automática a clasificador determinista local |
| Variación no notificada en contrato | Errores 422 en llamadas de API | Pruebas de contrato diarias en CI | Fijar versión y alertar ante discrepancias |

## 8. Validación propuesta

- **Hipótesis Falsable**: La separación arquitectónica previene que fallos de red en NotebookLM degraden la disponibilidad de la inferencia en producción.
- **Métricas**: Disponibilidad del plano de datos (uptime %) ante caída del plano de consulta.
- **Criterio de Rechazo**: Uptime 100% en plano de inferencia durante fallos simulados en MCP.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
