# JEV-P12-003 — Idempotencia Estricta de Operaciones para Evitar Duplicidad tras Timeouts Inciertos

## 1. Respuesta directa y decisión que permite tomar

Cuando una llamada a Jev experimenta un timeout de red, el estado final en el servidor remoto es incierto (pudo haberse procesado antes del corte). Para evitar que el reintento duplique una decisión downstream o cobre créditos dobles, cada solicitud debe etiquetarse con una clave de idempotencia única (UUIDv4 generado en el cliente) inyectada en las cabeceras HTTP o almacenada en una tabla transaccional de estados antes de despachar la petición.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Consistencia transaccional, tolerancia a fallos bizantinos y diseño de APIs idempotentes.
- **Supuesto clave**: Plataforma de monitoreo y telemetría distribuida activa en el entorno de despliegue.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia operativa**: Patrones de diseño de APIs financieras (Stripe Idempotency Patterns) aplicados a inferencia estadística de backend.
- **Contraste de confiabilidad**: Se descartan suposiciones de estabilidad perfecta en servicios cloud de terceros sin mecanismos de fallback.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Registro de idempotencia: Almacenar en Redis `SET idempotency:<uuid> 'PROCESSING' NX EX 120`. Si la clave ya existe, esperar el resultado previo o retornar la respuesta almacenada sin invocar nuevamente a Jev.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import uuid, logging

logger = logging.getLogger("P12_03")

class ControlIdempotencia:
    def __init__(self):
        self.registro = {}

    def ejecutar_con_idempotencia(self, clave_operacion: str, accion_func, *args) -> dict:
        try:
            if clave_operacion in self.registro:
                logger.info(f"Reutilizando resultado de operacion idempotente: {clave_operacion}")
                return self.registro[clave_operacion]
            resultado = accion_func(*args)
            self.registro[clave_operacion] = resultado
            return resultado
        except Exception as err:
            logger.error(f"Fallo en ejecucion idempotente: {type(err).__name__} (detalles omitidos por seguridad)")
            return {"error": "fallo_operacion"}
```

- **Contraejemplo / Caso borde**: Reintentar una orden de compra financiera tras un timeout sin clave de idempotencia provocará la ejecución duplicada de la transacción en el broker.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Duplicidad de acciones por reintento de timeout | Pérdida de capital por doble ejecución | Claves UUIDv4 obligatorias por evento | Bloqueo distribuido en Redis con NX |
| Agotamiento de sockets por conexiones no cerradas | Fuga de descriptores de archivos y crash | Monitoreo de descriptores de socket | Context managers asíncronos obligatorios |
| Desbordamiento de colas de memoria ante picos | Out of Memory (OOM) en contenedor | Métricas de memoria en Prometheus | Colas acotadas con descarte ordenado (backpressure) |

## 8. Validación propuesta

- **Hipótesis Falsable**: El control de idempotencia previene el 100% de las transacciones duplicadas ante fallos de timeout.
- **Métricas**: Operaciones duplicadas registradas en auditoría financiera.
- **Criterio de Rechazo**: 0 operaciones duplicadas en 50.000 transacciones con inyección de fallos.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
