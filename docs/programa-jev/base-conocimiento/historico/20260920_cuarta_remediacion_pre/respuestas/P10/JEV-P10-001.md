# JEV-P10-001 — Tareas de Búsqueda Apoyadas por Jev vs Necesidad de Motores de Recuperación Externos

## 1. Respuesta directa y decisión que permite tomar

Jev 1.13 no es un motor de búsqueda, base de datos vectorial ni sistema de almacenamiento indexado. Su rol en arquitecturas de información se limita estrictamente a la segunda etapa del pipeline: reranking semántico puntual de candidatos pre-recuperados y evaluación de compuertas booleanas de relevancia sobre pasajes de texto. Toda recuperación primaria de primera fase requiere indefectiblemente un motor externo (BM25 con Elasticsearch/OpenSearch, o embeddings densos con Qdrant/Milvus).

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Delimitación funcional de Jev dentro de arquitecturas RAG (Retrieval-Augmented Generation) y motores de búsqueda corporativos.
- **Supuesto clave**: Existencia de un motor de recuperación primaria de primera fase configurado y poblado.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia documental**: La especificación de TypeSafe (`SRC-0040`) confirma la inexistencia de primitivas de indexación, almacenamiento de vectores o endpoints de consulta léxica.
- **Contraste metodológico**: Se descartan arquitecturas que confunden búsqueda masiva no estructurada con inferencia semántica puntual.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Arquitectura de recuperación en dos etapas: Etapa 1 (Recall masivo): Índice invertido BM25 o HNSW vectorial recupera los mejores 50 documentos en <15 ms. Etapa 2 (Precisión semántica): Jev procesa pares (query, pasaje) mediante primitivas `Score` o `Choice` para reordenar los top 10 candidatos.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
import logging
from typesafe_sdk import TypeSafeClient, Score
logger = logging.getLogger('P10_01')

def rerankear_candidato_con_jev(consulta: str, pasaje_candidato: str) -> int:
    try:
        client = TypeSafeClient(model='jev-1.13.0')
        prompt_estado = f'CONSULTA: {consulta}\nPASAJE: {pasaje_candidato}'
        res = client.system_one(state=prompt_estado, questions={'relevancia': Score(instructions='Grado de relevancia tematica', criteria=['Nivel 1: Muy deficiente / Sin alineación', 'Nivel 2: Deficiente / Baja alineación', 'Nivel 3: Aceptable / Alineación moderada', 'Nivel 4: Bueno / Alta alineación', 'Nivel 5: Excelente / Rigurosamente alineado'])})
        return res.answers['relevancia'].score
    except Exception as err:
        logger.error(f'Fallo en reranking de pasaje: {type(err).__name__} (detalles omitidos por seguridad)')
        return 1
```

- **Contraejemplo / Caso borde**: Pretender enviar un corpus de 10.000 documentos a Jev para que 'busque' la respuesta saturará el límite de 32 KB y provocará un error de validación inmediato.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Enviar corpus masivo en state | Error 400 Bad Request por tamaño | Validador previo de tamaño | Implementar recuperador BM25/Qdrant previo |
| Sobrecarga de pasajes en state (>32 KB) | Error 400 en runtime de API | Validación preventiva de bytes | Truncar o fragmentar pasajes a <= 400 palabras |
| Desalineación semántica en consultas OOD | Falsos positivos en clasificación | Monitoreo de entropía y certeza | Compuerta de abstención automática |

## 8. Validación propuesta

- **Hipótesis Falsable**: El pipeline de dos etapas (BM25 + Jev Reranker) mejora el MRR@10 en 22% frente a BM25 aislado.
- **Métricas**: Mean Reciprocal Rank (MRR@10) sobre 500 consultas de prueba.
- **Criterio de Rechazo**: Incremento de MRR >= 15% respecto a línea base léxica.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
