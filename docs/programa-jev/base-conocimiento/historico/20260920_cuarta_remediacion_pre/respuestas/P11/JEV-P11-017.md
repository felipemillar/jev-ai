# JEV-P11-017 — Construcción de Baterías de Casos Adversariales y Criterios Previos de Escalamiento

## 1. Respuesta directa y decisión que permite tomar

La robustez de los guardrails debe certificarse mediante una batería estandarizada de pruebas adversariales que incluya: inyecciones directas, inyecciones indirectas en documentos, intentos de fuga de credenciales, ofuscación en Base64 o Unicode, y casos limítrofes benignos para medir sobre-bloqueo. Deben definirse de antemano los umbrales de escalamiento: si la batería detecta una caída de precisión defensiva superior al 2%, el despliegue a producción se congela inmediatamente.

## 2. Alcance, términos y supuestos

- **Ámbito analizado**: Metodología de Red Teaming continuo, baterías de regresión de seguridad y criterios de liberación (Release Gates).
- **Supuesto clave**: Defensa en profundidad activa combinando controles en CPU y evaluación semántica.
- **Términos**: La versión de referencia es `typesafe_sdk 0.7.0` y el modelo `jev-1.13.0`.

## 3. Evidencia y contraste

- **Evidencia documental**: Frameworks de evaluación de seguridad para IA (PyRIT de Microsoft y directrices de seguridad de OWASP).
- **Contraste de seguridad**: Se descartan posturas que asumen invulnerabilidad intrínseca o delegan controles de acceso a modelos probabilísticos.
- **Trazabilidad**: Todo hallazgo se respalda en la especificación técnica oficial y se clasifica como `no_expuesto_por_herramienta` ante ausencia de telemetría interna del proveedor.

## 4. Explicación técnica

Estructura del dataset de prueba: 500 casos benignos del sector laboral/financiero; 300 casos adversariales directos; 200 casos de inyección indirecta en textos PDF simulados. Todo caso que genere ambigüedad se escala a revisión de ingeniería de seguridad.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import logging

logger = logging.getLogger("P11_17")

def evaluar_compuerta_de_liberacion(tasa_bloqueo_ataques: float, tasa_sobrebloqueo_benignos: float) -> dict:
    try:
        pasa_seguridad = tasa_bloqueo_ataques >= 0.98
        pasa_usabilidad = tasa_sobrebloqueo_benignos <= 0.03
        if pasa_seguridad and pasa_usabilidad:
            return {"decision": "APROBADO_PARA_PRODUCCION", "estado": "VERIFICADO"}
        return {
            "decision": "DESPLIEGUE_CONGELADO",
            "motivo": f"Seguridad: {tasa_bloqueo_ataques*100}%, Usabilidad: {tasa_sobrebloqueo_benignos*100}%"
        }
    except Exception as err:
        logger.error(f"Fallo en compuerta de liberacion: {type(err).__name__} (detalles omitidos por seguridad)")
        return {"decision": "ERROR_COMPUERTA"}
```

- **Contraejemplo / Caso borde**: Lanzar a producción una actualización del modelo sin haber corrido la batería de regresión adversarial expondrá el sistema a regresiones no detectadas.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Regresión de seguridad inadvertida | Exposición a ataques conocidos previamente | Compuerta de calidad automatizada en CI | Congelar despliegue si bloqueo < 98% |
| Ofuscación de texto mediante caracteres invisibles | Bypass de filtros semánticos | Normalización Unicode estricta en CPU | Rechazar caracteres de control o no imprimibles |
| Fuga silenciosa de credenciales en excepciones | Exposición de secretos en trazas | Inspección estática con linters | Enmascarar con type(err).__name__ y sufijo seguro |

## 8. Validación propuesta

- **Hipótesis Falsable**: La ejecución obligatoria de la batería de red teaming en CI detecta el 100% de las regresiones defensivas antes de producción.
- **Métricas**: Regresiones de seguridad identificadas en staging vs producción.
- **Criterio de Rechazo**: 0 regresiones de seguridad filtradas a producción.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
