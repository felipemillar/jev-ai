# JEV-P08-004 — Separación de Recomendación, Autorización y Ejecución

## 1. Respuesta directa y decisión que permite tomar
Jev debe operar estrictamente como generador de recomendaciones de decisión, nunca como autorizador ni ejecutor. La recomendación (ej. `Choice: cancelar_subscripcion` con `confidence: 0.92`) es consumida por un módulo de autorización determinista que verifica invariantes de negocio (permisos de usuario, saldo, límites de riesgo) y emite un token de autorización firmado. La ejecución física de la mutación en la base de datos o broker la realiza un worker aislado que exige dicho token.

## 2. Alcance, términos y supuestos
- **Requisitos específicos analizados:** Definir patrón de segregación de responsabilidades para evitar ejecución autónoma destructiva.
- **Versión de referencia:** `jev-1.13.0` consumido vía `POST /v1/systemone`.
- **Límites de diseño:** La inferencia no ejecuta código ni persiste estado en el servidor; toda persistencia y garantía de ejecución corresponde a la arquitectura anfitriona.

## 4. Explicación técnica verificable
Pipeline unidireccional: Sensor -> Asesor Semántico (Jev) -> Compuerta de Autorización (CPU con reglas duras) -> Ejecutor Transaccional (Worker con base de datos/broker). Jev carece de credenciales de escritura en BD o APIs de broker.

## 6. Aplicación a nuestros desarrollos
- **QRT (Trading cuantitativo):** Aplicar el principio de *Soberanía Determinista*: Jev asesora la señal con estimación de probabilidad, pero el tamaño de posición y la ejecución residen en el motor en C++/MQL5 con circuit breakers duros.
- **Wheelwork (Operaciones industriales y headhunting):** Integrar Jev en tareas de triaje preliminar de vacantes y filtrado documental, delegando la confirmación de contratación a entrevistas y validaciones humanas obligatorias.

## 7. Fallos, límites y controles
- **Modos de fallo principales:** Pasar la salida de Jev directamente a una llamada SQL `DELETE` o `UPDATE` sin compuerta intermedia.
- **Control de mitigación:** Timeouts estrictos de conexión (350 ms), disyuntores de circuito con conmutación a heurística determinista local y registro de auditoría con hash criptográfico SHA-256 de cada inferencia.

## 8. Validación propuesta
- **Hipótesis falsable:** "Prueba de penetración sintética: inyectar textos engañosos diseñados para forzar `choice: borrar_todo`. Verificar que el autorizador en CPU rechaza la orden."
- **Métricas:** Tasa de error bajo carga, latencia percentil 99 (p99 < 400 ms), calibración ECE y coste total por decisión.
- **Criterio de rechazo:** Si la degradación ante caídas de red provoca bloqueo de transacciones o si el coste por decisión supera el umbral presupuestario definido.
