# JEV-P12-005 — Operación en Producción, Telemetría y Fiabilidad (SRE)

## 1. Respuesta directa y decisión que permite tomar
En relación con ¿Cómo controlar concurrencia y colas sin asumir que el límite del servicio o la capacidad del sistema son constantes?, la operación en producción de Jev 1.13.0 exige definir Objetivos de Nivel de Servicio (SLOs) desagregados: disponibilidad de servicio >= 99.9%, latencia p95 extremo a extremo <= 450 ms, y tasa de error de inferencia <= 0.1%. Se descarta presentar las cifras teóricas de inferencia pura del modelo (10–25 ms en GPU) como garantías de contrato del sistema completo, pues el transporte de red, la serialización y las colas externas imponen latencias reales típicamente situadas entre 70 ms y 400 ms.

## 2. Alcance, términos y supuestos
- **Presupuesto de latencia (SLO 450 ms p95):** Preparación local y sanitización (<= 25 ms), transporte y red (<= 150 ms), inferencia TypeSafe (<= 100 ms), procesamiento de respuesta y validación (<= 25 ms), margen de jitter (<= 150 ms).
- **Telemetría obligatoria:** Métricas Prometheus (latencia histogram, contador de errores por código HTTP, tokens consumidos por hora).
- **Control de versiones:** Bloqueo inmutable de versión `model="jev-1.13.0"` y registro de hashes en cada decisión.

## 4. Explicación técnica verificable
La observabilidad operativa distingue cuatro clases de incidencias:
1. **Fallo de Red / Transporte:** Timeout de socket (> 400 ms) o error de resolución DNS. Acción: conmutar inmediatamente a fallback local sin reintento síncrono.
2. **Fallo de Capacidad del Proveedor:** Códigos HTTP `429` (Rate limit) o `529` (Overloaded). Acción: activar backoff exponencial respetando cabecera `retry-after`.
3. **Fallo de Contrato Cliente:** Código HTTP `422` (Unprocessable Entity). Acción: abortar y registrar alarma crítica; nunca reintentar automáticamente pues el payload es inválido.
4. **Deriva Semántica (Data Drift):** Aumento súbito de la proporción de decisiones con baja confianza ($C < 0.60$). Acción: alertar sobre cambio de distribución en las entradas.

## 5. Ejemplo trabajado y contraejemplo
- **Instrumentación de Telemetría y Circuit Breaker en Python:**
```python
import time
import logging
from typesafe_sdk import TypeSafeClient, Choice

logger = logging.getLogger("JEV-P12-005")

class OperationalTelemetry:
    @staticmethod
    def record(duration_ms: float, status_code: int, tokens: int):
        logger.info(f"METRIC: duration={duration_ms:.2f}ms status={status_code} tokens={tokens}")

def ejecutar_llamada_operacional(estado: str) -> dict:
    start_time = time.perf_counter()
    try:
        client = TypeSafeClient(model="jev-1.13.0")
        res = client.system_one(
            state=estado,
            questions={"status": Choice(instructions="Evaluar estado", criteria={"ok": "Correcto", "fallo": "Incidencia"})}
        )
        elapsed = (time.perf_counter() - start_time) * 1000.0
        tokens = res.usage.input_tokens + res.usage.output_tokens
        OperationalTelemetry.record(elapsed, 200, tokens)
        ans = res.answers["status"]
        return {"choice": ans.choice, "confidence": ans.confidence, "latency_ms": elapsed}
    except Exception as err:
        elapsed = (time.perf_counter() - start_time) * 1000.0
        logger.error(f"Fallo operacional: {type(err).__name__} tras {elapsed:.2f}ms (detalles omitidos por seguridad)")
        OperationalTelemetry.record(elapsed, 500, 0)
        return {"choice": "fallback_seguro", "confidence": 0.0, "latency_ms": elapsed}
```
- **Contraejemplo:** Asumir que la latencia siempre será de 15 ms y configurar un timeout cliente de 30 ms: provocará un 90% de falsos timeouts por mera fluctuación del RTT transatlántico.

## 7. Fallos, límites y controles
- **Modo de fallo:** Saturación silenciosa de cuotas y agotamiento de crédito en la cuenta de TypeSafe.
- **Control:** Monitor diario de saldo consumido con alerta temprana al 75% del presupuesto mensual asignado.

## 8. Validación propuesta
- **Prueba de inyección de fallos:** Simular degradación de red (pérdida de paquetes del 10% y latencia artificial de 500 ms).
- **Criterio de aceptación:** El sistema anfitrión debe preservar el SLO de servicio degradándose a reglas de respaldo sin colapsar las colas de mensajes.
