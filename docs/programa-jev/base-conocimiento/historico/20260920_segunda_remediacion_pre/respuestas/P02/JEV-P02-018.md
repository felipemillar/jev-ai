# JEV-P02-018 — Detalles Arquitectónicos Indispensables frente a Suplencia por Contratos

## 1. Respuesta directa y decisión que permite tomar

Para integrar Jev de forma segura, predecible y conforme a los estándares de producción, **un equipo de ingeniería NO necesita conocer los secretos industriales del modelo** (como el número exacto de parámetros, los hiperparámetros de pre-entrenamiento o la matriz de pesos del *backbone*). Lo único estrictamente indispensable de la arquitectura son sus **garantías contractuales y operativas**: el contrato I/O estrictamente tipado sin texto libre, el carácter 100% *stateless* de la API, la independencia total de las preguntas en el Parallel Sampler y los límites físicos (32k tokens de contexto y 255 opciones en `Choice`).

La decisión de ingeniería es: **tratar a Jev como un microservicio probabilístico de caja negra gobernado por contratos formales en el cliente**. Todo riesgo derivado de la opacidad interna del modelo (como la posibilidad de errores semánticos intra-esquema, alucinaciones factuales o desviaciones de calibración) se mitiga en el software orquestador mediante: (1) compuertas de confianza (*confidence gating*), (2) validación estricta de precondiciones en código y (3) suites continuas de pruebas de regresión empírica.

## 2. Alcance, términos, versiones y supuestos

- **Detalles Indispensables**: Invariantes arquitectónicos cuyo desconocimiento causaría fallos de diseño irrecuperables (ej. creer que la API guarda estado o que genera texto explicativo).
- **Detalles Suplibles**: Características internas que pueden abstraerse o blindarse mediante capas de software envolvente (*wrappers*), aserciones deterministas y contratos OpenAPI/Pydantic.
- **Confidence Gating**: Patrón de control donde solo se automatizan acciones si la probabilidad emitida por el modelo supera un umbral de seguridad $\tau$; en caso contrario, se desvía a revisión humana o a un modelo deliberativo (Sistema 2).
- **Versión analizada**: Jev v1.13 / API SaaS.

### 4.2 La regla de diseño: "Cápsula de Integración Segura"
Para aislar a la aplicación de la opacidad del modelo, la integración debe materializarse en una clase cliente que aplique el patrón *Guardrail Wrapper*:

```
[Llamada de Negocio]
        │
        ▼
┌────────────────────────────────────────────────────────┐
│              Cápsula de Integración (Wrapper)          │
│  1. Pre-validación: Verifica tamaño de estado < 32k    │
│     y valida que el cálculo aritmético se hizo en CPU. │
│  2. Serialización: Genera JSON DTO tipado.             │
└──────────────────────────┬─────────────────────────────┘
                           │ (Invocación HTTP)
                           ▼
               ┌───────────────────────┐
               │    API Jev (Remota)   │
               └───────────┬───────────┘
                           │ (Decisión + Confianza)
                           ▼
┌────────────────────────────────────────────────────────┐
│              Cápsula de Integración (Wrapper)          │
│  3. Post-validación: Lee `confidence` y `probability`. │
│     ¿Confianza >= Umbral_Seguridad?                    │
│     - SÍ: Devuelve decisión tipada a la aplicación.    │
│     - NO: Dispara Fallback (Sistema 2 / Alerta humana).│
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
               [Acción de Producción Segura]
```

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1 Ejemplo de implementación de Cápsula de Integración Segura
```python
from pydantic import BaseModel, Field
from typing import Literal

class ResultadoDecision(BaseModel):
    decision: Literal["aprobar", "rechazar", "revision_manual"]
    confianza: float
    ejecutada_por: Literal["jev_automatico", "fallback_humano"]

class ClienteJevSeguro:
    def __init__(self, cliente_api_jev, umbral_minimo_confianza: float = 0.85):
        self.api = cliente_api_jev
        self.umbral = umbral_minimo_confianza

    def juzgar_solicitud_credito(self, metricas_calculadas: dict, memo_cliente: str) -> ResultadoDecision:
        # Precondición: El código calcula ratios numéricos previamente en CPU
        assert "ratio_cobertura" in metricas_calculadas, "Falta cálculo financiero determinista"
        
        state = {
            "ratios": metricas_calculadas,
            "declaracion": memo_cliente
        }
        
        # Invocación a Jev
        respuesta = self.api.decide(
            state=state,
            question="¿Presenta el solicitante coherencia comercial y riesgo aceptable?",
            primitive="Choice",
            options=["aprobable", "inconsistente_rechazar"]
        )
        
        # Post-condición y Compuerta de Confianza
        if respuesta.confidence < self.umbral:
            # Opacidad de la arquitectura suplida por fallback seguro
            return ResultadoDecision(
                decision="revision_manual",
                confianza=respuesta.confidence,
                ejecutada_por="fallback_humano"
            )
            
        decision_mapeada = "aprobar" if respuesta.choice == "aprobable" else "rechazar"
        return ResultadoDecision(
            decision=decision_mapeada,
            confianza=respuesta.confidence,
            ejecutada_por="jev_automatico"
        )
```

### 5.2 Contraejemplo o caso límite: Integración ingenua
Un desarrollador confía ciegamente en que "Jev nunca alucina" e integra la salida cruda de Jev directamente en el disparador de liquidación automática de fondos de inversión sin verificar `confidence` ni aislar el cálculo aritmético.
- **Resultado**: Ante un caso límite donde el cliente tenía un memo ambiguo, Jev emite una decisión errónea con confianza $0.51$. La cuenta se liquida por error, provocando una demanda legal y pérdidas financieras irreparables.
- **Diagnóstico**: El fallo no fue de la arquitectura de Jev, sino del integrador, que no suplió la incertidumbre inherente a los modelos probabilísticos con una compuerta de confianza externa.

## 6. Aplicación a nuestros desarrollos

- **Aplicación en QRT**: En el sistema de control de riesgo cuantitativo, la opacidad de los pesos de Jev se suple exigiendo que toda decisión de clasificación de régimen de mercado emitida por Jev sea contrastada con un filtro de validación dura en C++ (ej. si Jev clasifica `baja_volatilidad` pero el indicador ATR de mercado está en el percentil 99, el filtro en C++ veta la decisión de Jev automáticamente).
- **Aplicación en Wheelwork**: Para la gestión de permisos y roles de usuario, Jev nunca debe tomar decisiones directas de autorización de seguridad (`Allow`/`Deny`). Las políticas de control de acceso basado en roles (RBAC) son deterministas y se evalúan mediante código estricto en el backend. Jev solo clasifica descripciones semánticas de puestos de trabajo.

## 7. Fallos, límites, controles y condiciones de no uso

| Modo de Fallo | Impacto | Detección | Control / Mitigación |
| :--- | :--- | :--- | :--- |
| **Omisión de compuertas de confianza** | Ejecución desatendida de decisiones dudosas o ruidosas. | Auditoría de decisiones con confianza $< 0.80$ ejecutadas en producción. | Bloqueo en tiempo de compilación/ejecución si el wrapper no verifica el umbral de confianza $\tau$. |
| **Delegación de cálculos formales a Jev** | Inconsistencia matemática por evaluar operaciones en la red neuronal. | Linter de preguntas en CI/CD que rechace prompts con operadores aritméticos. | Mandato estricto: Todo número y cálculo debe suministrarse precalculado en el `state`. |
| **Asunción de memoria conversacional** | Corrupción lógica en flujos secuenciales por enviar payloads parciales. | Logs de llamadas con estados incompletos. | Verificación de completitud del esquema del `state` mediante Pydantic antes de cada llamada. |

**Condición de no uso**: Prohibido integrar la API de Jev directamente a mecanismos de ejecución de fondos, borrado de bases de datos o comandos destructivos de infraestructura sin una compuerta de confirmación humana obligatoria (*Human-in-the-Loop*).

## 8. Validación propuesta

- **Hipótesis falsable**: Un wrapper de software que implementa compuertas de confianza ($\tau = 0.85$) y verificación de precondiciones elimina el 100% de los incidentes por decisiones erróneas de baja certeza, manteniendo una tasa de automatización desatendida superior al 75% en flujos semánticos de negocio.
- **Comparador**:
  - Variante A (Integración ingenua): Automatización directa del 100% de las salidas de Jev.
  - Variante B (Cápsula Segura): Automatización con compuerta de confianza ($\tau = 0.85$) y desvío a revisión manual.
- **Datos y particiones**: 1.000 solicitudes reales de soporte y clasificación histórica con etiquetas de verdad terreno (*ground truth*).
- **Métricas**:
  - Tasa de error en producción (*False Approvals / Critical Misclassifications*).
  - Tasa de automatización (porcentaje de casos que no requirieron intervención humana).
- **Condición de rechazo**: Si la Variante B reduce la tasa de automatización por debajo del 60% para lograr cero errores críticos.
- **Presupuesto supuesto**: $10 USD; 6 horas de implementación y evaluación en staging.
- **Estado**: Propuesto, no ejecutado.
