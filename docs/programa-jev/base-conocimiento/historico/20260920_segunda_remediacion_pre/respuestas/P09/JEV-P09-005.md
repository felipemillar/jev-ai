# JEV-P09-005 — Protocolos de Integración, API y Conectividad Técnica

## 1. Respuesta directa y decisión que permite tomar
Para resolver específicamente ¿Qué solicitud y respuesta mínimas están documentadas, incluidos campos obligatorios, tipos, errores y referencias de versión?, la integración de software con TypeSafe Jev debe realizarse a través del contrato HTTP oficial `POST https://api.typesafe.ai/v1/systemone` o mediante el SDK oficial tipado `typesafe_sdk`. Se prohíbe el uso de endpoints ficticios (`/v1/choice`, `/v1/score`) y se descarta asumir soporte de streaming (SSE), ya que Jev emite decisiones atómicas consolidadas en un único payload JSON. La arquitectura cliente debe implementar serialización determinista del estado, gestión de reintentos con backoff exponencial ante respuestas `429 Too Many Requests` o `529 Overloaded`, y timeouts estrictos de transporte (< 400 ms).

## 2. Alcance, términos y supuestos
- **Contrato de transporte:** HTTP/1.1 y HTTP/2 con TLS 1.3 obligatorio.
- **Autenticación:** Header estándar `Authorization: Bearer $TYPESAFE_API_KEY`.
- **Payload estructurado:** Parámetros requeridos: `state` (str | dict | list), `model` (`jev-1.13.0` o `jev-latest`), y `questions` (mapa de objetos tipados Choice, Score, Noul).
- **Límites de servicio documentados:** 250.000 tokens/segundo y 1.200 peticiones/minuto; contexto total de 64k tokens por solicitud (32k para el estado más la pregunta más larga).

## 4. Explicación técnica verificable
La interacción cliente-servidor sigue una semántica de evaluación en bloque:
1. **Serialización del Estado:** El cliente normaliza los datos de entrada a JSON canónico sin campos redundantes para minimizar el consumo de tokens facturables ($0.042/Mtok).
2. **Despacho Concurrente de Preguntas:** Se empaquetan hasta decenas de preguntas sobre el mismo estado en el diccionario `questions`, aprovechando que el estado se procesa en un solo pase matricial en GPU.
3. **Mapeo de Respuestas:** El payload de retorno contiene `model`, `answers` (indexado por los IDs de pregunta) y `usage` (`input_tokens`, `output_tokens`).
4. **Respuestas de Error:** `401` (clave inválida), `422` (error de validación de esquema en `instructions` o `criteria`), `429` (límite de tasa superado, honrar `retry-after`), `529` (sobrecarga del cluster).

## 5. Ejemplo trabajado y contraejemplo
- **Implementación de Cliente Asíncrono con Reintentos Seguros en Python:**
```python
import logging
from typesafe_sdk import AsyncTypeSafeClient, Choice, RetryPolicy

logger = logging.getLogger("JEV-P09-005")

async def clasificar_transaccion_async(datos_tx: dict) -> dict:
    try:
        retry_policy = RetryPolicy(max_retries=3, backoff_factor=1.5)
        async with AsyncTypeSafeClient(model="jev-1.13.0", retry_policy=retry_policy) as client:
            response = await client.system_one(
                state=datos_tx,
                questions={
                    "fraude": Choice(
                        instructions="Evaluar sospecha de anomalia operativa",
                        criteria={"normal": "Operacion legitima", "sospechosa": "Patron no habitual"}
                    )
                }
            )
            ans = response.answers["fraude"]
            return {"status": "ok", "choice": ans.choice, "confidence": ans.confidence}
    except Exception as err:
        logger.error(f"Fallo en clasificar_transaccion_async: {type(err).__name__} (detalles omitidos por seguridad)")
        return {"status": "error", "choice": "abstencion", "confidence": 0.0}
```
- **Contraejemplo:** Configurar un bucle `while True` que reintente inmediatamente ante error `429` sin leer el header `retry-after`, provocando bloqueo temporal de la clave API por parte de los firewalls de TypeSafe.

## 6. Aplicación a nuestros desarrollos
- **QRT (Quant Trading):** Implementar el cliente asíncrono en procesos de captura de noticias fuera del bucle de ejecución de mercado (p. ej. en microservicio dedicado en Python), garantizando que los bloqueos de red nunca afecten la sincronización de ticks de MetaTrader 5.
- **Wheelwork (Procesos Operacionales):** Integrar llamadas en lote (batching de 20 preguntas por vacante) en workers Celery, reduciendo el coste de transporte HTTP y maximizando el throughput.

## 7. Fallos, límites y controles
- **Modo de fallo:** Caída temporal del proveedor (error `529 Overloaded`).
- **Control:** Conmutación automática en cliente mediante circuit breaker a un clasificador local de respaldo (heurística determinista o modelo liviano local).

## 8. Validación propuesta
- **Protocolo de verificación:** Prueba de estrés de 1.000 peticiones concurrentes en entorno de staging simulando fallos de red y rate limits.
- **Criterio de cierre:** Cero excepciones no controladas; el 100% de los reintentos debe respetar la política de backoff exponencial sin duplicar transacciones.
