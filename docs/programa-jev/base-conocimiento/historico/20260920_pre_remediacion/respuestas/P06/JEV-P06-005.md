# JEV-P06-005: Protocolo de Anotación Humana Auditable y Rechazo del Consenso de Modelos como Verdad Absoluta

## 1. Respuesta directa y decisión que permite tomar

Establecer la verdad fundamental (*Ground Truth*) para evaluar a Jev 1.13 utilizando el consenso mayoritario de otros modelos de lenguaje (e.g., *"evaluar con GPT-4o o Claude 3.5 Sonnet como juez"*) es una falacia metodológica grave conocida como **Sesgo de Circularidad o Consenso de Modelos**. Los LLMs comparten sesgos de preentrenamiento, fallan de forma correlacionada ante sintaxis no estándar y carecen de responsabilidad operativa y jurídica.

Para construir un conjunto de referencia inexpugnable, la organización debe implementar el **Protocolo de Anotación Humana Tripartita con Adjudicación Jerárquica (PAHT-AJ)**:

1. **Anotación Ciega Múltiple ($M \ge 3$)**: Cada caso es clasificado independientemente por al menos 3 analistas humanos de dominio sin acceso a la predicción de Jev ni a las respuestas de sus colegas, erradicando el sesgo de anclaje (*anchoring bias*).
2. **Medición Formal de Acuerdo Inter-Anotador**: Cálculo estandarizado de **Fleiss' Kappa ($\kappa_{\text{Fleiss}}$)** o **Krippendorff's Alpha ($\alpha$)**:
   - $\kappa \ge 0.80$: **Acuerdo Fuerte**. La etiqueta mayoritaria se consolida como *Hard Label*.
   - $0.60 \le \kappa < 0.80$: **Acuerdo Moderado / Disputa**. Se remite obligatoriamente a una sesión de adjudicación técnica con el especialista líder.
   - $\kappa < 0.60$: **Ambigüedad Intrínseca o Defecto Taxonómico**. El caso se preserva como *Soft Label* probabilístico (distribución de votos) y se audita la redacción de la taxonomía del negocio.
3. **Adjudicación con Registro de Causalidad**: Cuando los anotadores discrepan, el adjudicador líder no solo elige la opción final, sino que registra obligatoriamente el **código de causalidad de la discrepancia** (e.g., `AMBIGÜEDAD_SEMANTICA`, `ERROR_DE_LECTURA`, `CASO_NO_PREVISTO_EN_GUIA`).
4. **Prohibición de LLM-as-a-Judge para Certificación**: Ningún reporte formal de validación de Jev puede basar sus métricas en jueces sintéticos de IA sin contraparte humana certificada.

**Decisión que permite tomar**: Prohibir que los pilotos de Wheelwork o QRT utilicen pseudo-etiquetas generadas por otros LLMs para evaluar a Jev; establecer un flujo formal de etiquetado humano remunerado y auditado con métricas $\kappa$ antes de autorizar cualquier benchmark de rendimiento.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Procedimientos de etiquetado de datos, control de calidad inter-anotador, resolución de controversias y gobernanza de la verdad fundamental en Wheelwork y QRT.
- **Términos formalizados**:
  - *Fleiss' Kappa ($\kappa$)*: Coeficiente estadístico que mide el grado de concordancia entre un número fijo de evaluadores al clasificar elementos en categorías mutuamente excluyentes, corrigiendo el acuerdo esperado por puro azar.
  - *Adjudicación*: Proceso formal mediante el cual un árbitro humano experto revisa los desacuerdos entre anotadores para emitir un veredicto definitivo documentado.
  - *Soft Labels*: Representación de la etiqueta como una distribución de probabilidades entre las clases (e.g. $[0.67, 0.33]$) en lugar de una asignación binaria forzada, reflejando la incertidumbre humana legítima.
- **Versiones de referencia**: Jev 1.13 (`typesafe-ai >= 0.1.0`), Python 3.11+, Statsmodels.
- **Supuestos fundamentales**:
  1. Los analistas humanos cometen errores por fatiga o distracción; por ello, una sola opinión humana no es suficiente para definir la verdad fundamental.
  2. Si tres expertos humanos competentes no logran ponerse de acuerdo tras una adjudicación, el problema reside en una ambigüedad irreductible del mundo real o en una guía de etiquetado deficiente.

## 4. Explicación técnica verificable

### 4.1. El Algoritmo de Fleiss' Kappa ($\kappa_{\text{Fleiss}}$)

Sean $N$ el número total de casos, $n$ el número de anotadores por caso ($n=3$), y $k$ el número de categorías.

1. **Acuerdo Observado ($P_o$)**: Proporción promedio de pares de anotadores que concuerdan sobre el mismo caso:
   $$P_o = \frac{1}{N n (n - 1)} \sum_{i=1}^N \sum_{j=1}^k n_{ij}(n_{ij} - 1)$$
   donde $n_{ij}$ es el número de anotadores que asignaron el caso $i$ a la categoría $j$.
2. **Acuerdo Esperado por Azar ($P_e$)**:
   $$p_j = \frac{1}{N n} \sum_{i=1}^N n_{ij}, \quad P_e = \sum_{j=1}^k p_j^2$$
3. **Fleiss' Kappa**:
   $$\kappa = \frac{P_o - P_e}{1 - P_e}$$

### 4.2. Flujo de Trabajo del Protocolo PAHT-AJ

```
          │

          │
          └─── [NO] ──► DEFECTO DE TAXONOMÍA DETECTADO
                        - Pausar anotación
                        - Refinar definiciones y re-entrenar humanos
```

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Implementación en Python: Motor de Anotación, Kappa y Adjudicación

```python
"""
Módulo de Protocolo de Anotación Humana y Cálculo de Fleiss' Kappa.
Gestiona la auditoría de acuerdos y el flujo de adjudicación.
"""

from typing import List, Dict, Any, Tuple
import numpy as np
import logging

logger = logging.getLogger("HumanAnnotationEngine")

class AnnotationAuditEngine:
    @staticmethod
    def compute_fleiss_kappa(ratings_matrix: np.ndarray) -> float:
        """
        Calcula Fleiss' Kappa sobre una matriz de forma (N, k),
        donde cada celda [i, j] es el número de evaluadores que eligieron la clase j.
        """
        try:
            N, k = ratings_matrix.shape
            n = np.sum(ratings_matrix[0, :])  # Número de anotadores por fila

            # Proporción de votos por categoría global
            p_j = np.sum(ratings_matrix, axis=0) / (N * n)
            P_e = np.sum(p_j ** 2)

            # Acuerdo observado por fila
            row_agreements = np.sum(ratings_matrix * (ratings_matrix - 1), axis=1)
            P_o = np.sum(row_agreements) / (N * n * (n - 1))

            if P_e >= 1.0:
                return 1.0

            kappa = (P_o - P_e) / (1.0 - P_e)
            return float(kappa)

        except Exception as err:
            logger.error(f"Error al calcular Fleiss Kappa: {type(err).__name__} (detalles omitidos por seguridad)")
            return 0.0

    @staticmethod
    def process_case(
        case_id: str,
        votes: List[str],
        categories: List[str],
        lead_adjudication: str = None
    ) -> Dict[str, Any]:
        """
        Determina si el caso es unánime o requiere adjudicación obligatoria.
        """
        try:
            unique_votes = set(votes)
            if len(unique_votes) == 1:
                return {
                    "case_id": case_id,
                    "final_label": votes[0],
                    "status": "UNANIMOUS_GOLD_STANDARD",
                    "requires_adjudication": False,
                    "soft_label_distribution": {cat: votes.count(cat) / len(votes) for cat in categories}
                }
            else:
                # Caso en disputa
                if not lead_adjudication:
                    return {
                        "case_id": case_id,
                        "final_label": None,
                        "status": "DISPUTE_PENDING_ADJUDICATION",
                        "requires_adjudication": True,
                        "raw_votes": votes
                    }
                else:
                    return {
                        "case_id": case_id,
                        "final_label": lead_adjudication,
                        "status": "ADJUDICATED_BY_EXPERT",
                        "requires_adjudication": False,
                        "adjudicated": True,
                        "soft_label_distribution": {cat: votes.count(cat) / len(votes) for cat in categories}
                    }

        except Exception as err:
            logger.error(f"Error procesando caso {case_id}: {type(err).__name__} (detalles omitidos por seguridad)")
            return {"case_id": case_id, "status": "ERROR", "details": str(type(err).__name__)}


if __name__ == "__main__":
    cats = ["PAGO_DUPLICADO", "DISCREPANCIA_PRECIO", "FACTURA_VALIDA"]

    # Simulación de matriz de votos para 5 casos con 3 evaluadores por caso
    # Filas: Casos; Columnas: Votos para [PAGO_DUPLICADO, DISCREPANCIA_PRECIO, FACTURA_VALIDA]
    ratings = np.array([
        [3, 0, 0],  # Caso 1: Unanimidad en PAGO_DUPLICADO
        [2, 1, 0],  # Caso 2: Disputa 2 vs 1
        [0, 3, 0],  # Caso 3: Unanimidad en DISCREPANCIA_PRECIO
        [0, 1, 2],  # Caso 4: Disputa 1 vs 2
        [0, 0, 3],  # Caso 5: Unanimidad en FACTURA_VALIDA
    ])

    engine = AnnotationAuditEngine()
    k_val = engine.compute_fleiss_kappa(ratings)
    print(f"Fleiss' Kappa del Lote: {k_val:.4f}")
    if k_val >= 0.80:
        print("Certificación de Lote: ALTA CONCORDANCIA (Aprobado)")
    else:
        print("Certificación de Lote: REQUIERE REVISIÓN TAXONÓMICA")

    # Procesar caso en disputa
    res = engine.process_case(
        case_id="TX-991",
        votes=["PAGO_DUPLICADO", "PAGO_DUPLICADO", "DISCREPANCIA_PRECIO"],
        categories=cats,
        lead_adjudication="PAGO_DUPLICADO"
    )
    print("\nDetalle Caso Adjudicado:", res)
```

### 5.2. Caso Límite / Contraejemplo

Un proyecto de fintech pretendió evaluar a Jev para detectar transferencias de lavado de activos utilizando como "verdad fundamental" el voto mayoritario de tres modelos: `GPT-4o`, `Claude 3.5 Sonnet` y `Gemini 1.5 Pro`.
- Los tres modelos compartían el mismo sesgo: ante transacciones internacionales con empresas de Hong Kong, los tres clasificaban automáticamente como *"Alto Riesgo de Lavado"* basándose en heurísticas superficiales de sus corpus web.
- Al contrastar con los oficiales de cumplimiento humano del banco:
  - Las transacciones correspondían a cartas de crédito de importación de repuestos agrícolas perfectamente documentadas ante el Banco Central.
  - El "consenso de modelos" tenía un **74% de Falsos Positivos**.
- Si el banco hubiera evaluado a Jev contra esa verdad sintética, hubiera premiado a Jev por cometer exactamente el mismo error alucinatorio que los otros LLMs.
- **Lección**: La verdad fundamental nunca puede emanar de la misma tecnología que se intenta evaluar.

## 6. Aplicación a nuestros desarrollos

### 6.1. Wheelwork (Screening de CVs y Ajuste al Perfil)
- **Hecho**: La idoneidad de un candidato para un puesto de liderazgo es una evaluación que involucra juicio cualitativo sutil.
- **Hipótesis de desarrollo**: Para construir el dataset de prueba de Jev en Wheelwork, cada perfil debe ser evaluado a ciegas por 2 reclutadores y 1 gerente del área contratante. Solo si $\kappa \ge 0.75$, el caso se integra al benchmark de evaluación; las discrepancias se analizan semanalmente para pulir la rúbrica de competencias del sistema.

### 6.2. QRT (Cuadernos de Trading y Eventos de Política Monetaria)
- **Hecho**: Determinar si el comunicado del Banco Central de Chile es *"Dovish"* (expansivo) o *"Hawkish"* (contractivo) requiere comprensión profunda de macroeconomía.
- **Hipótesis de desarrollo**: QRT debe contratar la anotación independiente de 2 analistas macroeconómicos con experiencia en renta fija. Si ambos discrepan en la clasificación de un párrafo de la minuta, el caso se preserva como *Soft Label* para evaluar si la entropía emitida por Jev refleja fielmente la duda de los economistas de mercado.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de Fallo
1. **Fatiga del Anotador Humano**: Sesiones de etiquetado de más de 90 minutos continuos donde el analista comienza a responder al azar para terminar el turno.
2. **Influencia del Anotador Dominante**: Realizar sesiones grupales abiertas donde el analista más senior impone su opinión a los demás, destruyendo la independencia de las anotaciones.

### 7.2. Controles Mandatorios
- **Aislamiento Físico y Ciego en Software**: La plataforma de anotación no debe permitir ver las respuestas de otros evaluadores ni volver atrás para modificar respuestas tras conocer opiniones ajenas.
- **Inyección de Casos Trampa (Gold Traps)**: Inyectar un 5% de casos con respuesta obvia conocida para medir la atención del anotador en tiempo real.

### 7.3. Condiciones de No Uso
- Prohibido utilizar conjuntos de prueba donde las etiquetas hayan sido producidas por un solo anotador sin revisión o por pipelines de "auto-etiquetado" LLM sin auditoría estadística humana.

## 8. Validación propuesta

### 8.1. Hipótesis Falsable
> **Hipótesis**: La implementación del protocolo PAHT-AJ con adjudicación obligatoria en discrepancias garantizará un coeficiente Fleiss' Kappa $\kappa \ge 0.82$ sobre un lote de $N = 600$ decisiones de negocio en Wheelwork, reduciendo los casos de desacuerdo no resueltos a menos del $3\%$ del total del dataset de evaluación.

### 8.2. Diseño Experimental
- **Tipo**: Propuesta, no ejecutada.
- **Anotadores**: 3 analistas senior de reclutamiento y operaciones.
- **Muestra**: 600 decisiones de categorización laboral y conciliación.
- **Métricas**: Fleiss' Kappa del lote, tiempo medio de adjudicación por caso en disputa, tasa de desacuerdo residual.
- **Criterio de Rechazo**: Si el Kappa final tras adjudicación es inferior a 0.75, la taxonomía del problema se declara inviable para automatización y se detiene el desarrollo.
- **Presupuesto Supuesto**: 3 analistas durante 15 horas ($\approx 45$ horas hombre, USD \$1,350 de costo operativo).
