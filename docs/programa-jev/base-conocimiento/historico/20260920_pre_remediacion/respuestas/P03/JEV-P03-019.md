# JEV-P03-019: Traducción de Salidas Estructuradas a Acciones Reversibles: Juicio, Autorización y Ejecución

## 1. Respuesta directa y decisión que permite tomar

El acoplamiento directo entre la salida de un modelo probabilístico y un actuador transaccional con efectos secundarios (e.g., disparar una orden de mercado en un broker o emitir un reembolso bancario en cuanto Jev clasifica una entrada como positiva) constituye una **vulnerabilidad crítica de arquitectura**. Los modelos discriminativos son estimadores estocásticos que cuantifican verosimilitud semántica, pero carecen de noción de responsabilidad jurídica, límites de saldo, cuotas de riesgo o reversibilidad operativa.

Para construir sistemas autónomos seguros y tolerantes a fallos, la arquitectura debe imponer una **Separación Estricta en Tres Capas Desacopladas (La Tríada Juicio-Autorización-Ejecución)**:
1. **Capa de Juicio Semántico (Jev 1.13 — Sensor Probabilístico)**:
   - *Función*: Mapear texto no estructurado a una salida estructurada (`Noul`, `Choice`, `Score`) con probabilidad calibrada $P(Y \mid x)$.
   - *Aislamiento*: Totalmente **libre de efectos secundarios (*side-effect free*)**. Jev no posee credenciales de infraestructura, no conoce la política de ejecución del cliente y no interactúa con sistemas externos.
2. **Capa de Autorización y Política de Negocio (CPU Determinista — Árbitro de Reglas)**:
   - *Función*: Evaluar la salida de Jev junto con el estado del sistema, matrices de costes bayesianas, invariantes lógicos, controles de fraude y límites de crédito/riesgo.
   - *Resultado*: Si se satisfacen todas las salvaguardas, emite un objeto de comando inmutable: `ExecutionIntent`. Si la confianza es insuficiente o el riesgo excede el límite autónomo, deriva a autorización humana (*Human-in-the-Loop*).
3. **Capa de Ejecución y Compensación (Worker Transaccional — Actuador Reversible)**:
   - *Función*: Consumir el `ExecutionIntent` y materializar el cambio de estado mediante un **Patrón Saga de Dos Fases**.
   - *Invariante*: Toda acción materializada $A$ debe contar con una acción compensatoria formal $A^{-1}$ (e.g., `bloquear_cuenta` $\implies$ `desbloquear_cuenta_con_notificacion`; `comprar_activo` $\implies$ `stop_loss_garantizado`).

**Decisión que permite tomar**: Prohibir taxativamente que el código de integración ejecute llamadas a APIs con efectos secundarios basándose directamente en el payload crudo de Jev. Exigir la mediación obligatoria de la capa de autorización en CPU y el despacho mediante `ExecutionIntent` con registro de compensación en base de datos.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Arquitectura de control y ejecución segura para agentes y autómatas basados en Jev 1.13 en entornos de alta criticidad (trading cuantitativo en QRT y automatización operativa en Wheelwork).
- **Términos formalizados**:
  - *Juicio Semántico*: Estimación probabilística del estado fáctico de una entidad o texto: $P(Y \mid x)$.
  - *Autorización Operativa*: Validación determinista de invariantes de negocio, políticas de acceso y matrices de riesgo que autoriza o bloquea una acción.
  - *Intención de Ejecución (`ExecutionIntent`)*: Objeto inmutable, firmado y auditado que encapsula la acción aprobada, sus parámetros validados y la tupla de compensación.
  - *Patrón Saga Transaccional*: Secuencia de transacciones locales coordinadas donde cada paso que altera el estado posee una transacción de compensación equivalente para deshacer los cambios si ocurre un fallo posterior o una impugnación.
- **Versiones de referencia**: Jev 1.13 (`typesafe-ai >= 0.1.0`), Python 3.11+, patrones arquitectónicos CQRS y Sagas distribuidas (Fowler).
- **Supuestos fundamentales**:
  1. Ninguna acción en el mundo real es 100% reversible físicamente (e.g., el coste de slippage en un trade o la lectura de un email enviado), pero los sistemas de negocio pueden compensar financieramente o mitigar administrativamente sus efectos mediante acciones de reversión protocolizadas.
  2. La capa de autorización corre en servidores seguros con privilegios restringidos, independiente del entorno donde se ejecutan los workers de scraping o inferencia.

## 4. Explicación técnica verificable

### 4.1. Arquitectura de la Tríada Juicio - Autorización - Ejecución

El ciclo de vida de cualquier interacción automatizada en el sistema se estructura en un grafo lineal desacoplado:

```text
+-----------------------------------------------------------------------------+
|                          1. CAPA DE JUICIO SEMÁNTICO                        |
|                                                                             |
|  [ Contexto crudo x ]  -->  [ Inferencia Jev 1.13 ]  -->  [ P(Y|x), certeza ] |
+-----------------------------------------------------------------------------+
                                       | (Payload JSON puro, 0 permisos)
                                       v
+-----------------------------------------------------------------------------+
|                         2. CAPA DE AUTORIZACIÓN (CPU)                       |
|                                                                             |
|  * Evaluación Matriz de Costes:   R(a|x) = sum P(y|x) * C(a, y)             |
|  * Invariantes de Seguridad:      Max_Capital <= $5,000; Rate_Limit <= 10/s |
|  * Validación de Umbral:          p >= tau*                                 |
|                                                                             |
|  [ Condición Insuficiente / Riesgo Alto ] --> [ COLA DE REVISIÓN HUMANA ]    |
|  [ Condición Válida ]                     --> [ Genera ExecutionIntent ]   |
+-----------------------------------------------------------------------------+
                                       | (Token de Ejecución Criptográfico)
                                       v
+-----------------------------------------------------------------------------+
|                         3. CAPA DE EJECUCIÓN REVERSIBLE                     |
|                                                                             |
|  [ Worker Transaccional ] --> Ejecuta Acción Primaria (A)                    |
|                           --> Registra Acción Compensatoria (A^-1)          |
|                           --> Auditoría Append-Only en Base de Datos        |
+-----------------------------------------------------------------------------+
```

### 4.2. Contrato de la Intención de Ejecución (`ExecutionIntent`)

El objeto `ExecutionIntent` representa la frontera formal entre la semántica y la acción. Sus campos obligatorios son:
1. `intent_id`: UUIDv4 unívoco de la transacción.
2. `timestamp_utc`: Marca temporal de alta resolución.
3. `decision_ref`: URN de la decisión de Jev (`urn:jev:p03:...`) y su valor de probabilidad asociado.
4. `action_name`: Identificador unívoco de la acción autorizada (e.g., `CLOSE_ORDER`).
5. `parameters`: Parámetros validados en CPU (nunca generados libremente por un modelo).
6. `compensation`: Definición explícita de la acción de reversión (e.g., `REOPEN_ORDER` con sus argumentos precalculados).
7. `ttl_seconds`: Tiempo de vida de la autorización; si el worker no ejecuta la acción en ese intervalo, el token caduca automáticamente para evitar ejecuciones desfasadas.

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Ejemplo sintético trabajado: Orquestador Transaccional Reversible en Python

```python
"""
reversible_action_orchestrator.py
Demostración de la Tríada Juicio -> Autorización -> Ejecución Reversible.
"""
import uuid
import time
from dataclasses import dataclass
from typing import Dict, Any, Optional

@dataclass(frozen=True)
class JevSemanticOutput:
    """Capa 1: Salida pura de Jev sin permisos de acción."""
    decision_urn: str
    probability: float
    certainty: float

@dataclass(frozen=True)
class ExecutionIntent:
    """Capa 2: Comando emitido por el evaluador de negocio en CPU."""
    intent_id: str
    action_type: str
    payload: Dict[str, Any]
    compensation_action: str
    compensation_payload: Dict[str, Any]
    issued_at: float
    ttl_seconds: int = 10

class SecurityAuthorizer:
    def __init__(self, tau_threshold: float = 0.85, max_allowed_loss: float = 1000.0):
        self.tau = tau_threshold
        self.max_loss = max_allowed_loss

    def authorize(self, jev_out: JevSemanticOutput, trade_id: str, current_exposure: float) -> Optional[ExecutionIntent]:
        # 1. Comprobar que el juicio semántico supera el umbral bayesiano
        if jev_out.probability < self.tau:
            print(f"[AUTH] RECHAZADO: Confianza insuficiente ({jev_out.probability:.2f} < {self.tau})")
            return None

        # 2. Comprobar invariantes de riesgo financiero
        if current_exposure > self.max_loss:
            print(f"[AUTH] RECHAZADO: Exposición ({current_exposure}) excede límite seguro ({self.max_loss})")
            return None

        # 3. Emitir token de ejecución con su correspondiente acción compensatoria
        return ExecutionIntent(
            intent_id=str(uuid.uuid4()),
            action_type="EMERGENCY_HALT_POSITION",
            payload={"trade_id": trade_id, "mode": "SOFT_CLOSE"},
            compensation_action="RESTORE_POSITION_AT_LIMIT",
            compensation_payload={"trade_id": trade_id, "prev_exposure": current_exposure},
            issued_at=time.time()
        )

class TransactionalWorker:
    """Capa 3: Actuador transaccional con soporte de reversión (Saga)."""
    def execute(self, intent: ExecutionIntent) -> bool:
        # Verificar TTL para evitar ejecución desfasada
        if time.time() - intent.issued_at > intent.ttl_seconds:
            print(f"[WORKER] ERROR: Token de ejecución caducado.")
            return False

        print(f"[WORKER] EJECUTANDO: {intent.action_type} con ID={intent.intent_id}")
        # Simulación de éxito de la mutación de estado
        print(f"[WORKER] Transacción confirmada. Compensación registrada: {intent.compensation_action}")
        return True

    def rollback(self, intent: ExecutionIntent):
        print(f"[WORKER-SAGA] REVIRTIENDO ACCIÓN: {intent.compensation_action}...")
        print(f"[WORKER-SAGA] Estado restaurado con payload: {intent.compensation_payload}")

if __name__ == "__main__":
    # Simulación de un flujo completo
    # 1. Juicio de Jev: Detección de caída de liquidez severa
    juicio = JevSemanticOutput(
        decision_urn="urn:jev:p03:liquidity_shock:v1.0.0",
        probability=0.92,
        certainty=0.84
    )

    authorizer = SecurityAuthorizer(tau_threshold=0.85, max_allowed_loss=2000.0)
    worker = TransactionalWorker()

    # 2. Evaluación y Autorización
    intent = authorizer.authorize(juicio, trade_id="TRD-9081", current_exposure=1500.0)
    
    # 3. Ejecución controlada
    if intent:
        exito = worker.execute(intent)
        
        # Simulación de contingencia posterior que requiere compensación
        print("\n--- Evento exógeno detectado: Impugnación de señal por el supervisor ---")
        worker.rollback(intent)
```

**Salida de ejecución**:

### 5.2. Contraejemplo y caso límite: Acoplamiento de Efectos Secundarios en el Callback

Un programador junior conecta la API de Jev mediante un webhook directo:
```python
# ANTIPATRÓN CRÍTICO
def on_jev_response(prediction):
    if prediction.category == "BORRAR_USUARIO_SPAM":
        db.execute(f"DELETE FROM users WHERE id = {prediction.user_id}")
```
- **Fallo**: Un usuario legítimo envió un ticket que contenía fragmentos de spam que estaba denunciando. Jev clasificó el texto como spam con $p = 0.88$.
- **Consecuencia catastrófica**: La base de datos ejecutó un `DELETE` permanente e instantáneo sin pasar por comprobación de antigüedad de la cuenta, sin validar permisos de administrador y sin registrar copia de seguridad previa. La cuenta de un cliente corporativo histórico quedó destruida de forma irrecuperable en microsegundos.
- **Control**: Prohibir llamadas directas a actuadores; todo borrado debe ser un borrado lógico (*soft delete*) mediado por `ExecutionIntent` con período de gracia reversible.

## 6. Aplicación a nuestros desarrollos

### 6.1. Ejecución y Guardrails Cuantitativos (QRT)
- **Hecho documentado**: El trading algorítmico opera en mercados reales donde errores de ejecución generan pérdidas financieras inmediatas e irreversibles.
- **Integración propuesta**:
  - En QRT, Jev actúa estrictamente en la Capa 1 como sensor semántico analítico.
  - La Capa 2 (Autorizador de Riesgo en C++) evalúa las matrices de límites de apalancamiento, drawdown intradía y comprobación de márgenes de garantía.
  - La Capa 3 (Gateway MT5 / FIX) ejecuta exclusivamente órdenes que cuentan con un `ExecutionIntent` válido y que incluyen su correspondiente orden compensatoria de parada de pérdidas (*Stop Loss*) garantizada.

### 6.2. Autómatas Transaccionales en Wheelwork
- **Hecho documentado**: Wheelwork automatiza operaciones corporativas internas (asignación de recursos cloud, aprobaciones de compras, gestión de accesos).
- **Integración propuesta**:
  - Implementar el patrón Saga en el bus de eventos de Wheelwork.
  - Para acciones críticas (e.g. aprovisionamiento de clústeres de cómputo caros), la Capa 2 exige una doble firma: autorización probabilística de Jev + token de aprobación de un responsable si el coste mensual estimado supera \$500.
  - Cada acción registra su compensación para permitir el desmantelamiento limpio de recursos en caso de cancelación.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla específicos
1. **Fallo por Desfase Temporal del Token (*Stale Execution Intent*)**: Si un `ExecutionIntent` queda retenido en una cola de mensajes saturada y se ejecuta horas después, cuando las condiciones del mercado o del sistema han cambiado radicalmente.
   - *Control*: Todo `ExecutionIntent` debe incorporar obligatoriamente un TTL estricto (`ttl_seconds <= 15`). El worker debe verificar la validez temporal y descartar tokens expirados.
2. **Fallo en la Transacción de Compensación (*Broken Compensation*)**: Intentar revertir una acción pero fallar porque el estado externo mutó de forma incompatible (e.g., intentar recomprar un activo cuyo mercado ya cerró).
   - *Control*: Registrar alertas críticas en el sistema de telemetría y derivar inmediatamente a resolución manual de contingencia.

### 7.2. Condiciones taxativas de no uso
- **No permitir ejecución automática si la acción es físicamente irreversible y de alto impacto financiero**: Acciones como transferencias bancarias de alto importe o revocación destructiva de certificados deben requerir obligatoriamente confirmación humana explícita en la Capa 2.

## 8. Validación propuesta (propuesta, no ejecutada)

- **Hipótesis falsable**: La implementación de la tríada Juicio-Autorización-Ejecución con Sagas reversibles elimina el **100%** de las ejecuciones accidentales derivadas de falsos positivos de Jev en producción y permite la reversión exitosa de al menos un **99.5%** de las acciones compensadas, con una sobrecarga de latencia inferior a **4 ms** en CPU.
- **Comparador / Línea base**: Sistema legacy con ejecución directa reactiva sobre webhooks sin capa de compensación.
- **Conjunto de datos sintético**: 10,000 transacciones simuladas, incluyendo un 5% de anomalías inducidas y 200 eventos de contingencia que fuerzan rollback inmediato.
- **Métricas cuantitativas**:
  - Tasa de Falsas Ejecuciones Irreversibles (debe ser 0).
  - Tasa de Éxito de Compensación en Rollback.
  - Sobrecarga de latencia añadida por la capa de autorización y firmado en CPU.
- **Umbral de éxito**: Falsas ejecuciones irreversibles $= 0$; Éxito de rollback $\ge 99.5\%$; Latencia añadida $\le 4\text{ ms}$.
- **Criterio de rechazo**: Si la arquitectura de Sagas introduce fallos de consistencia o sobrecargas de latencia superiores a $20\text{ ms}$.
- **Presupuesto supuesto**: 0 llamadas adicionales a Jev; 100% simulación en CPU local; \$0 de coste de API.
