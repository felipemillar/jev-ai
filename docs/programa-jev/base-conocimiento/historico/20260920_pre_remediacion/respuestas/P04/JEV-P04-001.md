# JEV-P04-001: Especificación del `state` (Contexto), Formatos, Tamaños y Límites de la API de Jev

## 1. Respuesta directa y decisión que permite tomar

En la documentación técnica oficial de TypeSafe AI para Jev 1.13, el **`state`** (o contexto) se define como el **conjunto finito, inmutable y autocontenido de observaciones de la aplicación** entregado al modelo para ser evaluado en un único pase de inferencia (*single forward pass*). A diferencia de los LLMs autorregresivos, el `state` en Jev no es un historial de chat ni una memoria compartida: representa el "único mundo conocido" para el codificador durante la solicitud, sin acceso a herramientas externas, navegación web ni memoria entre llamadas (*100% stateless*).

Los contratos técnicos exactos y soportados son:
1. **Formatos Soportados**:
   - `string`: Cadena de texto plano utf-8 para pasajes individuales o fragmentos no estructurados.
   - `object` (JSON tipado): **Estándar canónico obligatorio** para entornos de producción. Permite estructurar campos nombrados y tipados (e.g. `{"order_id": "...", "client_tier": "...", "log_extract": "..."}`) a los cuales las preguntas tipadas hacen referencia directa.
   - `array`: Lista secuencial de cadenas u objetos, adecuada para trazas cronológicas o eventos de auditoría ordenados temporalmente.
2. **Modalidad**: **Estrictamente de texto**. La API de TypeSafe no soporta de forma nativa imágenes, audio ni vídeo. Cualquier contenido multimodal debe ser preprocesado deterministamente en CPU (mediante OCR o Whisper/ASR) antes de serializarse dentro del `state`.
3. **Tamaños y Límites Operativos**:
   - Límite de Ventana Teórico: **64,000 tokens** (64k).
   - Asignación Operacional del Servidor: **32,000 tokens** (32k) dedicados al `state`.
   - **Recomendación Canónica de Ingeniería**: Limitar el `state` a un presupuesto compacto (*Lean State*) de **100 a 2,000 tokens**. Superar los 4,000 tokens activa el fenómeno de *Context Rot* (degradación de atención atencional y aplanamiento de probabilidades en codificadores densos).
4. **Límites de Tasa (*Rate Limits*)**: 250,000 tokens por segundo y 1,200 solicitudes por minuto (RPM). Errores por saturación retornan HTTP `429 Too Many Requests` o `529 Overloaded`.

**Decisión que permite tomar**: Estandarizar la propiedad `state` en todos los servicios de QRT y Wheelwork exclusivamente bajo el formato `object` (JSON estructurado validado con Pydantic). Fijar un umbral de corte duro en el cliente: si el `state` excede los 2,500 tokens, el middleware local debe podar el texto en CPU antes de invocar la API, prohibiendo volcados crudos de documentos completos.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Especificación del cuerpo de petición HTTP en la API de TypeSafe AI, límites de tokens, tipos de serialización y restricciones de transporte para Jev 1.13.
- **Términos formalizados**:
  - *`state`*: Campo JSON raíz que contiene las variables factuales que alimentan el codificador denso del modelo.
  - *`POST /v1/systemone`*: Endpoint canónico de inferencia tipada de TypeSafe AI.
  - *Lean State*: Principio de ingeniería que exige suministrar únicamente los hechos estrictamente necesarios para la decisión, excluyendo metadatos decorativos.
  - *Context Rot*: Pérdida de resolución semántica y disminución de la fidelidad probabilística provocada por la dispersión de la masa atencional en contextos largos.
- **Versiones de referencia**: Jev 1.13 (`typesafe-ai >= 0.1.0`), Python 3.11+, Pydantic v2+.
- **Supuestos fundamentales**:
  1. La API de TypeSafe opera bajo el protocolo HTTPS y serialización JSON estándar UTF-8.
  2. El cálculo de tokens en cliente se realiza mediante un tokenizador de longitud de bytes (e.g., Tiktoken o codificadores BPE estándar compatibles con Llama/DeBERTa) para predecir con exactitud el consumo antes de la llamada.

### 4.2. Dinámica Computacional de la Ventana y *Context Rot*

Sea $L$ la longitud en tokens del campo `state`. La capa de codificación de Jev aplica autoatención bidireccional sobre la secuencia:
$$\mathbf{A} = \text{softmax} \left( \frac{\mathbf{Q}\mathbf{K}^T}{\sqrt{d_k}} \right)$$

- **Complejidad de Cómputo**: Escala como $O(L^2)$ en memoria GPU durante el pase de codificación hacia adelante.
- **Efecto en la Distribución de Probabilidad**: A medida que $L$ pasa de $1,000$ tokens a $25,000$ tokens, el denominador de la función softmax de atención se dispersa entre miles de posiciones no informativas:
  $$\alpha_{ij} = \frac{\exp(s_{ij})}{\sum_{k=1}^L \exp(s_{ik})}$$
  Esto causa un **aplanamiento de la atención (*Attention Entropy Inflation*)**, lo que provoca que la respuesta de las primitivas (`Noul`, `Choice`) pierda agudeza y desplace sus probabilidades hacia el centro de máxima entropía ($p \to 0.50$ en binario, $p \to 1/K$ en multiclase), inutilizando los umbrales de decisión $\tau^*$.

### 5.1. Ejemplo sintético trabajado: Contrato de Entrada en Pydantic y Despacho

```python
"""
jev_state_contract.py
Especificación y validación del contrato de 'state' para Jev 1.13 usando Pydantic v2.
"""
import json
from typing import Dict, Any, List, Literal, Union
from pydantic import BaseModel, Field, field_validator

class TransactionState(BaseModel):
    """Esquema tipado del 'state' para la decisión de riesgo operacional."""
    trade_id: str = Field(..., description="ID unívoco de la operación")
    timestamp_utc: str = Field(..., description="Marca temporal ISO-8601")
    asset_class: Literal["FX", "EQUITY", "CRYPTO", "COMMODITY"]
    notional_usd: float = Field(..., ge=0.0, description="Volumen en USD")
    broker_message: str = Field(..., max_length=2000, description="Texto extraído del broker")

    @field_validator("broker_message")
    def check_token_budget_heuristic(cls, v: str) -> str:
        # Heurística de tokens: ~4 caracteres por token en inglés/español
        estimated_tokens = len(v) / 4
        if estimated_tokens > 1500:
            raise ValueError(f"El texto excede el presupuesto Lean State ({estimated_tokens:.0f} > 1500 tokens).")
        return v

class QuestionSchema(BaseModel):
    type: Literal["noul", "choice", "score"]
    instructions: str
    criteria: Optional[Dict[str, str]] = None

class JevRequestPayload(BaseModel):
    model: str = "jev-1.13.0"
    state: TransactionState
    questions: Dict[str, QuestionSchema]

if __name__ == "__main__":
    # Construcción de un estado sintético canónico
    state_data = TransactionState(
        trade_id="TRD-2026-X109",
        timestamp_utc="2026-09-19T23:15:00Z",
        asset_class="FX",
        notional_usd=500000.0,
        broker_message="Confirmación de ejecución: Compra 500k USD/CLP a 945.20. Spread ejecutado normal sin deslizamiento."
    )

    request_payload = JevRequestPayload(
        state=state_data,
        questions={
            "q_deslizamiento": QuestionSchema(
                type="noul",
                instructions="¿Informa el mensaje que la orden sufrió deslizamiento o slippage adverso?"
            ),
            "q_calidad_ejecucion": QuestionSchema(
                type="choice",
                instructions="Clasificar la calidad reportada de la ejecución",
                criteria={
                    "ejecucion_optima": "Ejecutada al precio límite o mejor sin fricciones",
                    "ejecucion_parcial": "Orden completada parcialmente",
                    "ejecucion_con_retraso": "Retraso notable en el enrutamiento",
                    "otra_categoria_residual": "Cualquier otra condición"
                }
            )
        }
    )

    json_str = request_payload.model_dump_json(indent=2)
    print("--- PAYLOAD CANÓNICO VALIDADO PARA POST /v1/systemone ---")
    print(json_str)
```

### 5.2. Contraejemplo y caso límite: Volcado Masivo de Documento (*Context Rot*)

Un equipo decide clasificar una disputa contractual y envía como `state` el texto íntegro de un contrato PDF escaneado de 80 páginas ($28,000$ tokens):
- **Manifestación de la falla**:
  1. **Latencia**: El tiempo de procesamiento en GPU pasa de $35\text{ ms}$ a $420\text{ ms}$; el tiempo de transporte JSON en HTTP salta de $10\text{ ms}$ a $180\text{ ms}$.
  2. **Colapso Atencional**: La pregunta era: *"¿Se pactó una cláusula de arbitraje en Santiago de Chile?"*. La cláusula real estaba en la página 42 (posición intermedia). Jev asigna $p = 0.51$ en `Noul` con certidumbre nula ($|2p-1| = 0.02$).
- **Causa raíz**: El efecto *Lost in the Middle* destruyó la visibilidad atencional de la cláusula en el mar de 28k tokens irrelevantes de definiciones y firmas.
- **Control Arquitectónico**: Poda previa en CPU. Se debe utilizar búsqueda semántica o filtrado por palabra clave para extraer exclusivamente el párrafo de resolución de conflictos (<300 tokens) y enviar dicho fragmento como `state`.

## 6. Aplicación a nuestros desarrollos

### 6.1. Especificación de Estado para Señales Cuantitativas (QRT)
- **Hecho documentado**: Los modelos cuantitativos en QRT requieren baja latencia y alta predictibilidad.
- **Integración propuesta**:
  - En QRT, el `state` se estructurará siempre como un `object` JSON estricto que contenga únicamente:
    1. `ticker_symbol` y `market_session`.
    2. `headline_clean` (titular procesado, <40 tokens).
    3. `summary_clean` (cuerpo sintetizado de la noticia, <250 tokens).
  - El tamaño total del `state` no excederá jamás los **350 tokens**. Esto garantiza que la inferencia en Jev se complete en menos de $30\text{ ms}$ en GPU y minimiza los tiempos de serialización.

### 6.2. Ingesta de Solicitudes y Tickets en Wheelwork
- **Hecho documentado**: Wheelwork procesa comunicaciones heterogéneas de usuarios y plataformas internas.
- **Integración propuesta**:
  - El servicio de ingesta de Wheelwork actuará como un filtro de normalización previa:
    - Convierte correos electrónicos o mensajes de chat extensos en un objeto `TicketState` (remitente anonimizado, asunto, fragmento del problema).
    - Aplica un límite duro de 1,200 tokens antes de despachar a Jev para la clasificación de departamento y severidad.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla específicos
1. **Fallo por Formato No Soportado (HTTP 400 / 422)**: Enviar estructuras binarias (Base64 de imágenes, bytes crudos) en el campo `state`. La API de TypeSafe rechaza la petición con error de serialización.
   - *Control*: Validador de esquema Pydantic en cliente que garantice que todos los valores son primitivas JSON (`str`, `int`, `float`, `bool`, `list`, `dict`).
2. **Fallo por Saturación de Rate Limits (HTTP 429 / 529)**: Despachar ráfagas de más de 1,200 peticiones concurrentes por minuto desde múltiples workers sin pooling centralizado.
   - *Control*: Implementar cola de salida en Redis con algoritmo de *Token Bucket* y reintentos con *Exponential Backoff* y fluctuación (*jitter*).

### 7.2. Condiciones taxativas de no uso
- **No usar el endpoint de Jev para procesamiento multimodal directo**: Cualquier necesidad de analizar gráficos de velas, imágenes de documentos o audio de llamadas debe utilizar modelos especializados satélite (e.g. Whisper, Vision-OCR) y alimentar a Jev únicamente con el texto resultante.
- **No enviar estados superiores a 10,000 tokens sin prueba previa de agudeza atencional**: A menos que se verifique que la decisión resiste el ruido contextual en ese tamaño específico.

## 8. Validación propuesta (propuesta, no ejecutada)

- **Hipótesis falsable**: Para una batería de 500 contratos sintéticos con cláusulas críticas ubicadas en distintas posiciones del texto, un `state` compacto y podado en CPU (<1,000 tokens) logra un **35% más de certidumbre** ($|2p-1| \ge 0.85$) y reduce la latencia extremo a extremo en un **60%** frente a un `state` que contiene el documento completo (>15,000 tokens).
- **Comparador / Línea base**: Inferencia sobre documentos íntegros sin podar ($L \in [15k, 25k]$ tokens).
- **Conjunto de datos sintético**: 500 documentos sintéticos generados con contratos estándar donde la cláusula de prueba se posiciona al inicio (10%), en el centro (50%) y al final (90%).
- **Métricas cuantitativas**:
  - Certidumbre media $\mathbb{E}[|2p-1|]$.
  - Exactitud Factual Top-1 en detección de cláusula.
  - Latencia E2E ($P_{50}, P_{95}$).
- **Umbral de éxito**: Certidumbre podada $\ge 0.85$ (vs. $\le 0.50$ en no podada); Exactitud $\ge 96\%$; Latencia $P_{95} \le 110\text{ ms}$.
- **Criterio de rechazo**: Si la poda elimina información indispensable y degrada la exactitud factual en más de un $2\%$.
- **Presupuesto supuesto**: 1,000 llamadas a endpoints de Jev; coste API estimado en \$0.015; tiempo de ejecución: 15 minutos.
