# JEV-P02-013 — Memoria y Persistencia entre Llamadas en la Arquitectura de Jev

## 1. Respuesta directa y decisión que permite tomar

Toda la evidencia documental, especificación OpenAPI e inspección de clientes SDK confirma que **Jev es una API estrictamente sin estado (*stateless*)**. No existe ningún concepto de sesión, identificador de conversación (`conversation_id`), caché persistente del servidor ni memoria compartida entre llamadas HTTP consecutivas. Incluso dentro de una misma llamada con múltiples preguntas (Parallel Sampler), las evaluaciones son mutuamente independientes y sin memoria cruzada.

La decisión de arquitectura es categórica: **el diseño de integración debe asumir amnesia total del servidor y trasladar la gestión del estado íntegramente al cliente**. Toda memoria histórica, evolución temporal, traza de auditoría o encadenamiento de decisiones debe implementarse mediante un almacén externo (Redis, PostgreSQL o memoria en proceso) utilizando el patrón de diseño *State Accumulator*, serializando en cada llamada el snapshot de datos estrictamente necesario dentro del límite de 32k tokens.

## 2. Alcance, términos, versiones y supuestos

- **Stateless (Sin Estado)**: Propiedad arquitectónica donde cada solicitud HTTP contiene toda la información requerida para ser procesada de forma aislada, sin depender de transacciones previas en el servidor.
- **State Accumulator Pattern**: Patrón de diseño en el cual el software orquestador mantiene el estado canónico del proceso, actualizándolo con las decisiones discretas devueltas por Jev y alimentándolo en llamadas posteriores.
- **Context Window (32k tokens)**: Presupuesto máximo de contexto para serializar el estado en una llamada individual; no es una memoria persistente, sino un búfer de inferencia efímero.
- **Versión analizada**: Jev v1.13 / SDK Typesafe 0.1.x.

## 4. Explicación técnica verificable

### 4.1 Implicaciones de la ausencia de estado
Al carecer de memoria en el backend, Jev no puede:
1. "Recordar" lo que decidió hace 100 ms para el mismo usuario o activo financiero.
2. Reconocer correcciones interactivas directas («La decisión anterior fue incorrecta, rectifícala») a menos que el historial del error se serialice explícitamente en el nuevo `state`.
3. Optimizar el tiempo de atención mediante *KV Cache Sharing* entre llamadas HTTP independientes (a menos que el proveedor implemente *Prefix Caching* transparente a nivel de infraestructura, lo cual no está documentado públicamente).

### 4.2 Arquitectura del Patrón Acumulador de Estado (*State Accumulator*)
Para construir procesos de múltiples etapas o agentes autónomos, la arquitectura debe estructurarse según el siguiente flujo desacoplado:

```
[Entorno / Sensores / DB]
          │ (Telemetría / Evento)
          ▼
┌────────────────────────────────────────┐
│      Cliente Orquestador Local         │
│  (Mantiene `AgentState` en memoria)   │
└──────────────────┬─────────────────────┘
                   │
                   ├─ 1. Serializa snapshot actual en JSON
                   │
                   ▼
┌────────────────────────────────────────┐
│         API de Jev (Stateless)         │
│   (Evalúa `state` en un solo paso)     │
└──────────────────┬─────────────────────┘
                   │
                   ├─ 2. Devuelve decisión tipada (Choice/Score/Noul)
                   │
                   ▼
┌────────────────────────────────────────┐
│      Cliente Orquestador Local         │
│  - Actualiza `AgentState` con decisión │
│  - Ejecuta acción de negocio (código)  │
│  - Persiste traza en PostgreSQL/Redis  │
└────────────────────────────────────────┘
```

### 4.3 Manejo de la ventana de contexto en procesos largos
Si un proceso continuo (como una sesión de trading o un flujo de soporte técnico) acumula eventos en el estado, el tamaño del JSON eventualmente alcanzará el límite de 32k tokens o degradará la atención (*Lost in the Middle*). La integración debe aplicar:
1. **Ventana deslizante (*Rolling Window*)**: Mantener únicamente los últimos $K$ eventos estructurados (ej. los últimos 10 cambios de estado).
2. **Compresión semántica por eventos**: En lugar de acumular logs textuales crudos, registrar transiciones discretas: `{"estado_anterior": "espera", "transicion": "confirmado", "ts": 1726780000}`.

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1 Ejemplo correcto: Orquestador con estado cliente
```python
class OrquestadorRiesgoQRT:
    def __init__(self, cliente_jev, redis_client):
        self.jev = cliente_jev
        self.db = redis_client

    def evaluar_evento_mercado(self, cuenta_id: str, tick: dict):
        # 1. Recuperar estado acumulado previo
        estado_previo = self.db.get_json(f"estado:{cuenta_id}") or {"historial_alertas": []}
        
        # 2. Construir nuevo payload de estado para Jev
        payload_estado = {
            "precio_actual": tick["last"],
            "volatilidad_15m": tick["vol"],
            "ultimas_decisiones": estado_previo["historial_alertas"][-3:]  # Rolling window
        }
        
        # 3. Llamada stateless a Jev
        decision = self.jev.decide(
            state=payload_estado,
            question="¿Amerita la dinámica actual una pausa preventiva de órdenes?",
            primitive="Noul"  # Devuelve booleano y probabilidad
        )
        
        # 4. Actualizar estado en cliente
        nuevo_evento = {"ts": tick["timestamp"], "alerta": decision.value, "prob": decision.probability}
        estado_previo["historial_alertas"].append(nuevo_evento)
        self.db.set_json(f"estado:{cuenta_id}", estado_previo, ttl=3600)
        
        return decision
```

### 5.2 Contraejemplo o caso límite: Asunción errónea de memoria conversacional
Un desarrollador envía en la llamada 1:
- `state`: `{"documento": "Informe de balances Q3", "texto": "..."}`
- `question`: `Choice` sobre si hay riesgo de liquidez. Resultado: `alto`.

En la llamada 2 (inmediatamente después):
- `state`: `{}` (vacío)
- `question`: `Choice` con opciones `["reducir_posicion", "mantener"]`: «Considerando el informe que analizaste recién, ¿qué debemos hacer?».
- **Resultado catastrófico**: La llamada 2 fallará por validación o devolverá una elección aleatoria de baja confianza. Jev no sabe qué se envió en la llamada 1.

## 6. Aplicación a nuestros desarrollos

- **Aplicación en QRT (Trading Cuantitativo)**: En los sistemas de trading de alta fidelidad, la separación estricta de estado es una ventaja de seguridad. El motor de ejecución en Rust/C++ mantiene el libro de órdenes y los saldos de forma determinista y auditada en memoria protegida. Cuando se consulta a Jev para una evaluación de régimen macro o sentimiento, el motor construye un DTO inmutable y efímero. No hay riesgo de fuga de datos entre cuentas en el servidor de inferencia.
- **Aplicación en Wheelwork (Flujos Operativos)**: Para la atención de usuarios o automatización de flujos de trabajo, una base de datos relacional (PostgreSQL) o de documentos almacena el ticket completo. El servicio backend extrae únicamente el fragmento relevante para la decisión atómica que Jev debe calificar.

## 7. Fallos, límites, controles y condiciones de no uso

| Modo de Fallo | Impacto | Detección | Control / Mitigación |
| :--- | :--- | :--- | :--- |
| **Envío de estado incompleto por asumir persistencia** | Decisiones erróneas por falta de contexto en llamadas secundarias. | Respuestas con confianza anómalamente baja ($\approx 0.5$) o pruebas de regresión. | Validación de esquemas en el middleware cliente antes de invocar la API; rechazar estados vacíos o incompletos. |
| **Desbordamiento de contexto por acumulación no acotada** | Error HTTP 400 (Context length exceeded) o degradación de atención en llamadas tardías. | Monitoreo de conteo de tokens en el payload saliente. | Implementar poda automática (*pruning*) y límite de ventana deslizante en el objeto de estado. |
| **Condiciones de carrera en concurrencia cliente** | Dos hilos actualizan el estado local de forma desincronizada tras respuestas paralelas de Jev. | Inconsistencia en la base de datos de auditoría local. | Uso de bloqueos optimistas o colas serializadas de eventos en el orquestador cliente. |

**Condición de no uso**: Prohibido asumir que Jev mantendrá contexto conversacional o que un hilo de ejecución en el servidor puede almacenar identificadores temporales de sesión.

## 8. Validación propuesta

- **Hipótesis falsable**: Un sistema cliente que implementa el patrón *State Accumulator* con ventana deslizante de $K=5$ eventos serializados logra un 100% de coherencia contextual y reduce el tamaño promedio del payload en un 65% frente a la acumulación histórica bruta.
- **Comparador**:
  - Variante A: Acumulador con historial completo no podado (crecimiento lineal de tokens).
  - Variante B: Acumulador con ventana deslizante estructurada ($K=5$) y compresión de transiciones.
- **Datos y métricas**: Simulación de 50 sesiones operativas de 50 pasos cada una (2.500 llamadas totales a Jev).
  - Consistencia semántica de decisiones encadenadas.
  - Consumo promedio de tokens por llamada (meta: $<1.500$ tokens en Variante B).
  - Tasa de errores HTTP 400 / degradación por contexto largo (meta: 0.0%).
- **Condición de rechazo**: Si la Variante B pierde información crítica requerida para decisiones en pasos avanzados ($t > 30$) reduciendo la precisión semántica frente a la Variante A.
- **Presupuesto supuesto**: $12 USD; 6 horas de desarrollo.
- **Estado**: Propuesto, no ejecutado.
