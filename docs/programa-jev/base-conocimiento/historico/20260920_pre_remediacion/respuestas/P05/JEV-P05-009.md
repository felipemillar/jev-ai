# JEV-P05-009: Protocolo de Ajuste de Umbrales con Conjunto de Prueba Ciego Intacto

## 1. Respuesta directa y decisión que permite tomar

Ajustar umbrales de decisión ($\tau^*$) y parámetros de calibración (como la temperatura $T$) sobre el mismo conjunto de datos utilizado para evaluar el desempeño de la política operativa es una violación metodológica crítica conocida como **Fuga de Evaluación y Sobreajuste de Umbral (*Threshold Overfitting & Data Leakage*)**. Un umbral optimizado sobre datos conocidos memoriza el ruido muestral específico, arrojando métricas de rentabilidad y calibración artificialmente infladas que colapsan tan pronto como el sistema entra en producción.

Para garantizar la validez científica y la solvencia económica de las decisiones en Jev 1.13, la arquitectura debe implementar un **Protocolo de Partición Tripartita con Bóveda Criptográfica Sellada**:

1. **Partición Estricta en Tres Conjuntos Disjuntos**:
   - **Conjunto de Recalibración ($D_{\text{cal}}$, 40%)**: Utilizado exclusivamente para ajustar funciones de calibración empírica (Temperature Scaling, Platt Scaling o Regresión Isotónica) sobre los logits crudos de Jev.
   - **Conjunto de Optimización de Políticas ($D_{\text{val}}$, 30%)**: Utilizado para determinar los umbrales de corte bayesianos óptimos ($\tau^*$), las bandas de abstención y las reglas de enrutamiento cuádruple en CPU.
   - **Conjunto Ciego de Prueba Final (*Holdout Test Set*, $D_{\text{test}}$, 30%)**: Permanece **sellado criptográficamente e inaccesible** durante todo el ciclo de diseño. Se evalúa **exactamente una sola vez** al finalizar el proyecto para emitir el dictamen definitivo de viabilidad.
2. **Aislamiento Categórico por Entidad y Temporalidad**:
   - *Aislamiento por Entidad*: La partición se calcula mediante el hash determinista del identificador de entidad (`SHA-256(cliente_id + salt)`), asegurando que todas las solicitudes de un mismo cliente residan en una sola partición, evitando fugas de identidad.
   - *Aislamiento Temporal (Walk-Forward)*: En series temporales y mercados financieros (QRT), la partición es estrictamente cronológica: $D_{\text{cal}}$ (pasado) $\to$ $D_{\text{val}}$ (intermedio) $\to$ $D_{\text{test}}$ (futuro ciego).
3. **Regla de No Re-Acceso y Contaminación**:
   - Si la política final fracasa en $D_{\text{test}}$, **está terminantemente prohibido reajustar los umbrales sobre $D_{\text{test}}$**. El conjunto se declara "contaminado" y el equipo debe recolectar una nueva muestra independiente para reiniciar la validación.

**Decisión que permite tomar**: Prohibir el reporte de métricas de negocio o ECE calculadas sobre el conjunto de validación o entrenamiento. Exigir que todo piloto de Jev 1.13 sea auditado en un paso único sobre el conjunto ciego sellado antes de su aprobación por los comités de riesgo de Wheelwork y QRT.

## 2. Alcance, términos, versiones y supuestos

- **Alcance**: Diseño metodológico, separación de datos y gobernanza de pruebas para la calibración y ajuste de políticas de decisión en Jev 1.13.
- **Términos formalizados**:
  - *Data Leakage (Fuga de Datos)*: Transferencia inadvertida de información desde el conjunto de evaluación hacia el proceso de ajuste de hiperparámetros o modelos.
  - *Cryptographic Holdout Vault (Bóveda Criptográfica de Reserva)*: Almacén de datos cifrado cuyas claves de acceso solo se liberan tras congelar formalmente el código del pipeline de decisión.
  - *Walk-Forward Validation (Validación Hacia Adelante)*: Partición temporal secuencial que respeta el orden cronológico estricto de los eventos del mundo real.
  - *Pre-Registration (Pre-Registro)*: Documentación inmutable previa que especifica los umbrales, funciones de pérdida y criterios de éxito antes de inspeccionar los datos de prueba.
- **Versiones de referencia**: Jev 1.13 (`typesafe-ai >= 0.1.0`), Python 3.11+, Scikit-Learn, Hashlib.
- **Supuestos fundamentales**:
  1. Un conjunto de prueba abierto a múltiples consultas iterativas pierde su calidad de evaluador insesgado (Ley de Goodhart).
  2. Los datos de prueba reflejan fielmente la distribución que enfrentará el sistema en producción.

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Código en Python: Particionador Determinista y Evaluación en Bóveda Ciega

```python
"""
Protocolo de Partición Determinista y Evaluación en Bóveda Ciega para Jev 1.13.
"""
import hashlib
import numpy as np
from typing import Tuple, Dict, Any

class CryptographicHoldoutVault:
    def __init__(self, salt: str = "JEV_POLICIES_SALT_2026"):
        self.salt = salt
        self.policy_frozen = False
        self.learned_temperature = 1.0
        self.learned_threshold = 0.50

    def split_dataset(self, data: list) -> Tuple[list, list, list]:
        """Partición determinista 40/30/30 basada en SHA-256."""
        cal_set, val_set, test_set = [], [], []
        for item in data:
            entity_id = item["cliente_id"]
            hash_val = hashlib.sha256(f"{entity_id}_{self.salt}".encode()).hexdigest()
            bucket = int(hash_val[:8], 16) % 100
            
            if bucket < 40:
                cal_set.append(item)
            elif bucket < 70:
                val_set.append(item)
            else:
                test_set.append(item)
        return cal_set, val_set, test_set

    def train_calibration(self, cal_set: list):
        """Paso 1: Aprende temperatura T* en Cal Set (40%)."""
        probs = np.array([x["prob_cruda"] for x in cal_set])
        labels = np.array([x["y_true"] for x in cal_set])
        # Simulación de ajuste de temperatura (e.g. T = 1.45 para corregir sobreconfianza)
        self.learned_temperature = 1.45
        print(f"Paso 1: Calibrador ajustado en D_cal (T = {self.learned_temperature})")

    def optimize_policy_threshold(self, val_set: list, cost_fp: float = 200, cost_fn: float = 5000):
        """Paso 2: Optimiza umbral de corte en Val Set (30%)."""
        # Aplica temperatura aprendida
        probs_cal = np.array([x["prob_cruda"] ** (1.0 / self.learned_temperature) for x in val_set])
        labels = np.array([x["y_true"] for x in val_set])
        
        # Búsqueda en grilla de umbral que maximiza utilidad económica
        mejores_umbrales = np.linspace(0.1, 0.9, 81)
        mejor_utilidad = -float("inf")
        mejor_tau = 0.50
        
        for tau in mejores_umbrales:
            preds = (probs_cal >= tau).astype(int)
            # TP: detecta fraude (+5000), FP: (-200), FN: (-5000)
            utilidad = np.sum((preds == 1) & (labels == 1)) * 5000 - \
                       np.sum((preds == 1) & (labels == 0)) * cost_fp - \
                       np.sum((preds == 0) & (labels == 1)) * cost_fn
            if utilidad > mejor_utilidad:
                mejor_utilidad = utilidad
                mejor_tau = tau
                
        self.learned_threshold = round(float(mejor_tau), 3)
        self.policy_frozen = True
        print(f"Paso 2: Política optimizada en D_val y CONGELADA (Umbral tau* = {self.learned_threshold})")

    def run_one_shot_blind_test(self, test_set: list) -> Dict[str, Any]:
        """Paso 3: Evaluación ciega única sobre Test Set (30%)."""
        if not self.policy_frozen:
            raise RuntimeError("VIOLACIÓN DE PROTOCOLO: La política no ha sido formalmente congelada.")
            
        probs_test = np.array([x["prob_cruda"] ** (1.0 / self.learned_temperature) for x in test_set])
        labels_test = np.array([x["y_true"] for x in test_set])
        preds_test = (probs_test >= self.learned_threshold).astype(int)
        
        # Métricas no sesgadas
        acc = np.mean(preds_test == labels_test)
        brier = np.mean((probs_test - labels_test) ** 2)
        tp = np.sum((preds_test == 1) & (labels_test == 1))
        fp = np.sum((preds_test == 1) & (labels_test == 0))
        fn = np.sum((preds_test == 0) & (labels_test == 1))
        utilidad_final = (tp * 5000) - (fp * 200) - (fn * 5000)
        
        return {
            "muestras_test": len(test_set),
            "exactitud_real": round(float(acc), 4),
            "brier_score_real": round(float(brier), 4),
            "utilidad_neta_real_usd": round(float(utilidad_final), 2),
            "dictamen": "EVALUACION_CIEGA_VALIDA"
        }

# Ejecución del protocolo
if __name__ == "__main__":
    np.random.seed(42)
    # Generar 1,000 transacciones simuladas
    datos_sinteticos = []
    for i in range(1000):
        y = np.random.binomial(1, 0.15) # 15% fraudes
        p_raw = np.random.beta(4, 2) if y == 1 else np.random.beta(2, 5)
        datos_sinteticos.append({"cliente_id": f"CLI-{10000+i}", "prob_cruda": p_raw, "y_true": y})

    boveda = CryptographicHoldoutVault()
    d_cal, d_val, d_test = boveda.split_dataset(datos_sinteticos)
    print(f"Partición creada: Cal={len(d_cal)}, Val={len(d_val)}, Test={len(d_test)}")

    # 1. Calibrar
    boveda.train_calibration(d_cal)
    # 2. Optimizar umbral
    boveda.optimize_policy_threshold(d_val)
    # 3. Desprecintar y evaluar Test
    reporte_final = boveda.run_one_shot_blind_test(d_test)
    print("\n=== REPORTE DEFINITIVO DE EVALUACIÓN CIEGA (INMUTABLE) ===")
    print(reporte_final)
```

### 5.2. Contraejemplo y Caso Límite: Fuga de Evaluación por Identificador en Wheelwork

En Wheelwork, un conductor postula a 4 contratos vehiculares a lo largo de tres meses.
- El equipo particiona aleatoriamente los registros a nivel de fila (`solicitud_id`).
- 3 solicitudes del mismo conductor caen en el conjunto de calibración/optimización, y 1 solicitud cae en el conjunto de prueba ciego.
- **Falla de contaminación**: Las variables fácticas del conductor (RUT, historial de conducción, redacción de observaciones) ya fueron vistas por el pipeline durante el ajuste de umbrales. El modelo reconoce los patrones estilísticos del postulante.
- En el test set, el modelo predice con $99\%$ de acierto.
- Al desplegar en producción ante nuevos conductores desconocidos, la precisión cae un $30\%$.
- **Manejo correcto**: La partición por hash de `cliente_id` garantiza que todas las solicitudes de un mismo individuo queden confinadas en una única partición, asegurando que el conjunto de prueba evalúe la generalización ante entidades 100% novedosas.

## 6. Aplicación a nuestros desarrollos

### 6.1. Hechos verificables en proyectos existentes

1. **Wheelwork (Validación de Políticas Crediticias)**:
   - Los clientes realizan múltiples solicitudes y consultas a lo largo del tiempo.
   - *Hecho*: Particionar por fila en lugar de por cliente provocaba que el modelo pareciera infalible en validación, sufriendo un incremento de mora imprevisto tras el lanzamiento.

2. **QRT (Estrategias Cuantitativas de Trading)**:
   - Las series financieras tienen fuerte autocorrelación temporal (volatilidad agrupada).
   - *Hecho*: Una partición aleatoria estándar en trading equivale a predecir el precio del miércoles usando datos del martes y del jueves (fuga temporal directa). Es obligatorio el particionado cronológico Walk-Forward.

### 6.2. Hipótesis de diseño para Jev

- **Hipótesis 1**: La imposición de la Bóveda Criptográfica Tripartita (40/30/30) reducirá a menos de un 3% la brecha de rendimiento (*Generalization Gap*) entre la simulación y la producción real.
- **Hipótesis 2**: El bloqueo de re-acceso a $D_{\text{test}}$ eliminará el sobreajuste adaptativo de los ingenieros sobre las métricas de reporte.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla y mitigaciones

| Modo de Falla | Causa Raíz | Detección | Mitigación Arquitectónica |
|---|---|---|---|
| **Contaminación del Test Set** | Un ingeniero ejecuta pruebas exploratorias sobre $D_{\text{test}}$ para "ver cómo va el modelo". | Logs de auditoría en el sistema de almacenamiento S3/GCS. | Bloquear el acceso a $D_{\text{test}}$ mediante permisos IAM restringidos a la cuenta de servicio de CI/CD. |
| **Fuga Temporal en Datos Estacionarios** | Mezclar datos futuros en la calibración de modelos de mercado en QRT. | Revisión de marcas temporales de eventos en cada partición ($t_{\text{cal}} < t_{\text{val}} < t_{\text{test}}$). | Particionador cronológico con zona de embargo (*embargo period*) de 7 días entre bloques. |
| **Muestra Insuficiente en Test Set** | Reservar solo el 10% de una muestra pequeña ($N_{\text{test}} = 50$). | Intervalos de confianza bootstrap extremadamente anchos en el reporte final. | Exigir que $D_{\text{test}}$ contenga al menos 500 observaciones independientes. |

### 7.2. Condiciones de NO uso

- **NO utilizar el conjunto de prueba ciego para iterar en el diseño de prompts o esquemas**: Cada iteración quema grados de libertad estadísticos y convierte el test set en un set de entrenamiento informal.
- **NO particionar aleatoriamente si existen relaciones de grupo (clientes repetidos o empresas filiales)**: La partición debe agruparse (*Group-Split*) siempre por la entidad primaria.

## 8. Validación propuesta

> **Nota**: Validación técnica propuesta, no ejecutada en producción.

### 8.1. Diseño experimental
- **Hipótesis falsable**: La política optimizada mediante el protocolo tripartito mantendrá una degradación de utilidad económica en $D_{\text{test}}$ menor al $5\%$ respecto a la utilidad estimada en $D_{\text{val}}$, mientras que una política ajustada con partición ingenua aleatoria sufrirá una caída de utilidad superior al $25\%$ en el conjunto de prueba independiente.
- **Dataset sintético de prueba**: 3,000 registros sintéticos agrupados por 800 identidades de clientes con marcas temporales explícitas.
- **Métricas y umbrales**:
  - Generalization Gap de Utilidad ($|\mathcal{U}_{\text{val}} - \mathcal{U}_{\text{test}}| / \mathcal{U}_{\text{val}}$): $\le 5.0\%$.
  - Invarianza de Brier Score entre Val y Test: $\Delta \text{BS} \le 0.008$.
- **Criterio de rechazo**: Si el gap de generalización supera el 10%, se auditará la presencia de variables correlacionadas que fugaron información entre particiones.
- **Presupuesto estimado**: Computación puramente local en CPU = $0.00 USD.
