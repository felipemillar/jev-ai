# JEV-P01-006 — Los Tres Significados de «Determinista» en Jev: Esquema, Servicio y Repetición

## 1. Respuesta directa y decisión que permite tomar
En las fuentes de Jev, el término «determinista» se utiliza en tres planos técnicos radicalmente distintos: (1) **determinismo de esquema y tipo** (garantía matemática de 0% de error sintáctico; la salida siempre respeta el JSON y el enum solicitado); (2) **determinismo del servicio y flujo de control** (la lógica de la aplicación anfitriona mantiene el control estricto de bifurcaciones, umbrales y acciones, usando a Jev solo como una "sentencia IF semántica"); y (3) **determinismo de repetición de decisiones** (consistencia ante entradas idénticas). Las fuentes demuestran que **Jev es 100% determinista en esquema y permite construir servicios deterministas, pero NO es determinista estocástico estricto en la repetición de inferencias**. Esta distinción permite decidir no depender de Jev como función pura sin estado, fijar obligatoriamente la versión de API (`jev-1.13.0`), almacenar en caché las decisiones evaluadas para evitar reconsultas redundantes y aplicar siempre umbrales en código para controlar los efectos secundarios.

## 4. Explicación técnica verificable
- **Por qué el esquema es determinista:** En la capa de inferencia final de Jev, no opera un decodificador autorregresivo que pueda generar caracteres arbitrarios. Se evalúan los logits de las opciones provistas y se normalizan con softmax. El deserializador JSON del SDK solo recibe datos que ya cumplen la interfaz TypeScript/Python.
- **Por qué la repetición no es estrictamente determinista:** En arquitecturas de inferencia en servidores con hardware paralelo masivo (ej. kernels de atención en bfloat16/fp8 distribuidos entre múltiples instancias), las operaciones de reducción de coma flotante no son asociativas. Por tanto, dos peticiones idénticas pueden producir ligeras fluctuaciones en el tercer o cuarto decimal de probabilidad (ej. `0.9421` vs `0.9418`), lo que en la frontera exacta de un umbral podría alterar una clasificación marginal si no se aplica una banda de histéresis.

## 5. Ejemplo trabajado y contraejemplo
- **Ejemplo trabajado (Diseño de servicio determinista con Jev):**
  - *Código anfitrión:*
    ```python
# Ejemplo ilustrativo no ejecutado
from typesafe_sdk import TypeSafeClient, Choice

client = TypeSafeClient(model="jev-1.13.0")
res = client.system_one(
    state=ticket_body,
    questions={
        "severidad": Choice(
            instructions="Determinar severidad operativa del ticket",
            criteria={
                "critica": "Incidencia crítica que bloquea la operación",
                "normal": "Incidencia de prioridad normal o rutinaria",
                "otra": "Otra categoría de incidencia"
            }
        )
    }
)
decision = res.answers["severidad"].choice
confidence = res.answers["severidad"].probabilities[decision]

# Servicio determinista gobernado por código:
if decision == "critica" and confidence >= 0.90:
    disparar_alerta_guardia()
elif confidence < 0.70 or decision == "otra":
    escalar_a_cola_humana()
else:
    asignar_flujo_estandar()
```
  - *Resultado:* El esquema es determinista (res.decision siempre es una de las 3 opciones); el servicio es determinista (las reglas de negocio y ramas if/else son fijas).
- **Contraejemplo (Antipatrón: Suponer repetición determinista pura):**
  - Un desarrollador omite guardar el log de la decisión asumiento que si vuelve a llamar a Jev mañana con el mismo ticket obtendrá exactamente la misma probabilidad para una auditoría contable. Si el modelo fue actualizado bajo el alias `jev-latest`, la probabilidad puede cambiar de 0.89 a 0.91, alterando el resultado de auditoría.

## 6. Aplicación a nuestros desarrollos
- **QRT:** 
  - Almacenar en base de datos el payload exacto de entrada (`state`), el ID de respuesta, la versión explícita del modelo (`jev-1.13.0`) y la distribución completa de probabilidades devueltas. Nunca reejecutar llamadas históricas asumiendo determinismo retroactivo.
  - Aplicar bandas de tolerancia ($\pm 0.02$) en umbrales de decisión para evitar oscilaciones en casos de borde.
- **Wheelwork:**
  - Garantizar que las decisiones de compatibilidad de candidatos utilicen el esquema cerrado para guardar directamente en PostgreSQL (campos JSONB tipados) sin fallos de parseo.
- **Flujos personales:**
  - Usar caché local (Redis o SQLite) indexada por el hash SHA-256 del `state` para evitar pagar dos veces por evaluar el mismo contenido.

## 7. Fallos, límites y controles
- **Modo de fallo 1: Oscilación en el umbral.** Un caso con confianza 0.8499 se rechaza y en una segunda llamada da 0.8501 y se aprueba.
  - *Control:* Implementar zona de incertidumbre / histéresis (ej. decisiones automáticas requieren $\ge 0.88$, rechazos $\le 0.75$, y el rango intermedio se escala a revisión).
- **Modo de fallo 2: Confusión terminológica en especificaciones.** Presentar el sistema a clientes o inversores como "IA 100% determinista".
  - *Control:* Corregir la documentación comercial a "Arquitectura de control determinista con evaluación semántica tipada".
- **Condición de no uso:** No emplear Jev en funciones criptográficas, generación de números pseudoaleatorios deterministas o pruebas unitarias que hagan asserts sobre floats de probabilidad exacta.

## 8. Validación propuesta
- **Hipótesis falsable:** "En 100 llamadas idénticas consecutivas con el mismo payload sobre `jev-1.13.0`, la tasa de cumplimiento de esquema será del 100.0%, mientras que la desviación estándar de la probabilidad de la opción ganadora será $\sigma > 0$ pero acotada ($\sigma < 0.01$)."
- **Comparador:** Llamadas repetidas a Jev vs función hash determinista (SHA-256) vs LLM generativo con temperature=0.
- **Datos:** 10 payloads sintéticos variados ejecutados 10 veces cada uno.
- **Métricas:** Tasa de error de validación JSON, varianza de probabilidad máxima y estabilidad de la categoría predicha.
- **Criterio de confirmación:** Confirma la presencia de determinismo de tipos con variabilidad probabilística mínima de inferencia.
- **Estado:** Propuesta, no ejecutada (diseño conceptual).
