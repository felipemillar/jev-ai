# JEV-P12-018 — Gestión de Dependencias Compartidas y Ciclo de Retirada de Versiones (Deprecation)

## 1. Respuesta directa y decisión que permite tomar

La integración con Jev en múltiples proyectos (QRT, Wheelwork, automatizaciones internas) debe gestionarse a través de un paquete interno centralizado (`company-jev-client`) con políticas claras de deprecación. Cuando se libera una versión mayor o se modifica un contrato, la versión anterior entra en estado de deprecación con una ventana fija de mantenimiento de 90 días. Se prohíbe mantener más de dos versiones activas simultáneamente en producción.

## 4. Explicación técnica

Alertas de deprecación en logs de compilación: La versión obsoleta emite un warning `DeprecationWarning` en cada inicio y agrega la cabecera `X-Company-API-Deprecated: true` en las respuestas para alertar a los equipos consumidores.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import warnings, logging

logger = logging.getLogger("P12_18")

def comprobar_version_deprecada(version_usada: str, version_vigente: str):
    try:
        if version_usada != version_vigente:
            msg = f"Version {version_usada} esta DEPRECADA. Migrar a {version_vigente} antes de 90 dias."
            logger.warning(msg)
            warnings.warn(msg, DeprecationWarning)
    except Exception as err:
        logger.error(f"Fallo en verificador de deprecacion: {type(err).__name__} (detalles omitidos por seguridad)")
```

- **Contraejemplo / Caso borde**: Permitir que un microservicio siga utilizando una versión de hace 2 años del cliente impide actualizar la infraestructura central y acumula vulnerabilidades de seguridad.
