# JEV-P12-017 — Ingeniería de Caos y Pruebas de Fallos Simulados (Indisponibilidad, Latencia y Cuota)

## 1. Respuesta directa y decisión que permite tomar

La resiliencia operativa debe certificarse mediante ejercicios periódicos de Ingeniería de Caos (Chaos Engineering) en staging. La suite de pruebas debe inyectar deliberadamente: 1) Indisponibilidad de API (errores HTTP 503 forzados); 2) Inyección de latencia extrema (pausas de 2.000 ms); 3) Agotamiento súbito de cuota (HTTP 429 masivos); y 4) Corrupción de paquetes de red. El sistema aprueba el ejercicio solo si conmuta limpiamente al fallback local sin lanzar excepciones no controladas.

## 2. Alcance, términos y supuestos

El dominio de JEV-P12-017 comprende el diseño e inyección de fallos controlados para verificar la tolerancia ante cortes de conectividad, latencia y respuestas malformadas. Se modela sobre el runtime oficial 1.13 estableciendo circuitos de corte inmediato ante transgresión de SLA.

## 4. Explicación técnica

Inyección de fallos a nivel de middleware HTTP mediante interceptores en `httpx`: Un proxy de prueba introduce artificialmente retardos y códigos de error aleatorios sobre el 20% del tráfico sintético.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
import random, logging

logger = logging.getLogger("P12_17")

class InyectorCaosProxy:
    def __init__(self, probabilidad_fallo: float = 0.2):
        self.probabilidad = probabilidad_fallo

    def interceptar_llamada(self) -> dict:
        try:
            if random.random() < self.probabilidad:
                tipo_falla = random.choice(["TIMEOUT_SIMULADO", "HTTP_503", "HTTP_429"])
                logger.warning(f"CAOS INYECTADO: Simulando fallo {tipo_falla}")
                return {"falla_inyectada": True, "tipo": tipo_falla}
            return {"falla_inyectada": False}
        except Exception as err:
            logger.error(f"Fallo en inyector de caos: {type(err).__name__} (detalles omitidos por seguridad)")
            return {"falla_inyectada": False}
```

- **Contraejemplo / Caso borde**: Asumir que el código de respaldo funciona sin haber simulado jamás una caída de red terminará en caídas fatales el día que ocurra un corte real.

## 7. Fallos conocidos, advertencias y contraindicaciones

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Fallback no probado en condiciones reales | Caída del sistema durante cortes del proveedor | Ejercicios mensuales de Chaos Engineering | Validación de conmutación sin excepciones no controladas |
| Agotamiento de sockets por conexiones no cerradas | Fuga de descriptores de archivos y crash | Monitoreo de descriptores de socket | Context managers asíncronos obligatorios |
| Desbordamiento de colas de memoria ante picos | Out of Memory (OOM) en contenedor | Métricas de memoria en Prometheus | Colas acotadas con descarte ordenado (backpressure) |

## 8. Validación propuesta

- **Hipótesis Falsable**: Las pruebas de caos periódicas reducen los fallos imprevistos en incidentes de red reales en un 90%.
- **Métricas**: Tasa de transacciones exitosas durante cortes reales del proveedor.
- **Criterio de Rechazo**: Éxito >= 99.0% vía fallback durante incidentes externos.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
