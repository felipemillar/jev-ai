# JEV-P07-007: Pruebas Conductuales para Diferenciar Solicitudes Explícitas, Cortesía Indirecta, Condiciones y Promesas

## 1. Respuesta directa y decisión que permite tomar

En la comunicación profesional corporativa y financiera en español (particularmente en Chile), los mensajes rara vez adoptan formas imperativas directas. La teoría de los actos de habla (Searle, 1969) demuestra que existe una divergencia continua entre la **forma locutiva** (la sintaxis superficial) y la **fuerza ilocutiva** (la intención pragmática real). Un clasificador de Sistema 1 como TypeSafe Jev puede confundir sistemáticamente:
1. Una **cortesía indirecta** (*"¿Sería posible si acaso pudieran anular el cobro?"*) con una mera consulta informativa (falso negativo de acción).
2. Una **condición hipotética** (*"Si no me mejoran la tasa de interés, cerraré la cuenta corriente"*) con una orden de cierre inmediata (falso positivo transaccional).
3. Una **promesa o compromiso de pago futuro** (*"El lunes a primera hora saldo la cuota"*) con un pago ya ejecutado y liquidado.

Para garantizar que el software aguas abajo no ejecute acciones destructivas prematuras ni ignore peticiones genuinas, la arquitectura canónica de Jev implementa una **batería de sondeo ortogonal de 4 dimensiones** (*Speech Act Probing Suite*). En lugar de pedirle a Jev una clasificación holística ambigua, se ejecutan en paralelo preguntas desacopladas (`Noul`) sobre la inmediatez operacional, la existencia de contingencias condicionales y el horizonte temporal de la acción.

### 2.1. Alcance y Postura Oficial del Proveedor
El análisis de Jev 1.13 en lo concerniente a diferenciación de actos de habla (solicitudes, cortesía indirecta y promesas) aborda la delimitación de responsabilidades entre el modelo y las salvaguardas de software. Dado que TypeSafe AI no ofrece soporte contractual multilingüe ni garantías específicas para este fenómeno (`SRC-0002`), la arquitectura del sistema debe implementar controles deterministas que garanticen la fiabilidad de las decisiones en producción.

### 2.2. Términos formalizados y supuestos territoriales
- **Foco operativo**: fuerza ilocutiva pragmática y compromisos contractuales en entornos transaccionales de alta exigencia.
- **Límites de tolerancia**: Cero tolerancia a fallos silenciosos en clasificación de bordes con impacto financiero o contractual.
- **Supuesto clave**: Las particularidades de diferenciación de actos de habla (solicitudes, cortesía indirecta y promesas) no deben delegarse al espacio latente no verificado del modelo sin compuerta de validación en CPU.

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Implementación de Referencia en Python

El siguiente módulo implementa la suite de sondeo ortogonal que desacopla la fuerza ilocutiva mediante tres preguntas binarias concurrentes (`Noul`) y una máquina de estados determinista.

```python
# Ejemplo ilustrativo no ejecutado
"""
Módulo de Sondeo Ortogonal de Actos de Habla para Jev AI.
Diferencia de forma determinista entre solicitudes explícitas, cortesía, condiciones y promesas.
"""

from dataclasses import dataclass
from typing import Dict, Any, Tuple
import logging

logger = logging.getLogger("SpeechActProber")


@dataclass(frozen=True)
class SpeechActClassification:
    category: str  # "EXPLICIT_REQUEST", "INDIRECT_REQUEST", "CONDITIONAL_TRIGGER", "PROMISE_COMMITMENT", "INFORMATIONAL"
    requires_immediate_execution: bool
    requires_conditional_monitoring: bool
    confidence: float
    routing_action: str


class SpeechActProbingEngine:
    """
    Motor de sondeo ortogonal que combina múltiples preguntas de Sistema 1 con lógica de ruteo.
    """

    def __init__(self, confidence_floor: float = 0.80):
        self.confidence_floor = confidence_floor

    def probe_message(self, text: str, state_metadata: Dict[str, Any]) -> SpeechActClassification:
        try:
            # En producción, estas tres preguntas se envían en fan-out paralelo a Jev API (POST /v1/systemone)
            # 1. ¿El texto expresa una orden o petición operativa (incluso si está formulada con cortesía)?
            is_request, conf_request = self._mock_noul(text, "¿El usuario solicita o exige una acción concreta del servicio?")

            # 2. ¿La acción está explícitamente condicionada a un evento futuro o incumplimiento ("si ocurre X")?
            is_conditional, conf_cond = self._mock_noul(text, "¿La acción mencionada está supeditada a una condición o evento futuro?")

            # 3. ¿El usuario realiza un compromiso o promesa de actuar él mismo a futuro ("pagaré el lunes")?
            is_promise, conf_promise = self._mock_noul(text, "¿El usuario expresa una promesa o compromiso de pago/acción personal futura?")

            # Matriz Lógica de Ruteo Determinista
            if is_promise:
                return SpeechActClassification(
                    category="PROMISE_COMMITMENT",
                    requires_immediate_execution=False,
                    requires_conditional_monitoring=False,
                    confidence=conf_promise,
                    routing_action="SCHEDULE_PROMISE_FOLLOWUP"
                )

            if is_conditional:
                return SpeechActClassification(
                    category="CONDITIONAL_TRIGGER",
                    requires_immediate_execution=False,
                    requires_conditional_monitoring=True,
                    confidence=conf_cond,
                    routing_action="REGISTER_CONDITIONAL_WATCHER"
                )

            if is_request:
                # Distinguir entre solicitud explícita e indirecta basada en mitigadores
                is_indirect = any(m in text.lower() for m in ["sería posible", "si acaso", "si fueran tan amables", "quisiera saber si pueden"])
                category_label = "INDIRECT_REQUEST" if is_indirect else "EXPLICIT_REQUEST"

                return SpeechActClassification(
                    category=category_label,
                    requires_immediate_execution=True,
                    requires_conditional_monitoring=False,
                    confidence=conf_request,
                    routing_action="EXECUTE_TRANSACTION"
                )

            return SpeechActClassification(
                category="INFORMATIONAL",
                requires_immediate_execution=False,
                requires_conditional_monitoring=False,
                confidence=min(conf_request, conf_cond),
                routing_action="ROUTE_TO_FAQ_SUPPORT"
            )

        except Exception as err:
            logger.error(f"Error procesando acto de habla: {type(err).__name__} (detalles omitidos por seguridad)")
            return SpeechActClassification(
                category="UNKNOWN_ERROR",
                requires_immediate_execution=False,
                requires_conditional_monitoring=False,
                confidence=0.0,
                routing_action="ESCALATE_HUMAN_OPERATOR"
            )

    def _mock_noul(self, text: str, question: str) -> Tuple[bool, float]:
        lower = text.lower()
        if "supeditada a una condición" in question:
            return ("si " in lower or "en caso de" in lower or "a menos que" in lower), 0.91
        if "promesa o compromiso" in question:
            return ("el lunes" in lower and "pagaré" in lower) or ("me comprometo" in lower), 0.89
        if "solicita o exige" in question:
            return ("anular" in lower or "dar de baja" in lower or "cancele" in lower), 0.88
        return False, 0.70
```

### 5.2. Contraejemplo y Modos de Fallo Reales

### 4.1 El Falso Positivo Destructivo por Confusión de Condición con Solicitud
Un banco despliega un bot de autoservicio impulsado por Jev para clasificar correos de clientes.
- **Correo de cliente:** `"Si la semana que viene no me ha llegado la tarjeta de coordenadas, voy a dar de baja mi cuenta corriente."`
- **Pregunta formulada a Jev (`Choice`):** `¿Cuál es el trámite solicitado por el cliente? [Consulta de Despacho, Cancelación de Cuenta, Actualización de Datos]`.
- **Fallo del Modelo:** Jev clasifica en `Cancelación de Cuenta` con confianza $0.84$, arrastrado por la fuerza del sintagma `"dar de baja mi cuenta corriente"`.
- **Consecuencia Operacional:** El middleware transaccional bloquea preventivamente las tarjetas del usuario y genera una carta de cierre. El cliente, indignado, demanda al banco ante la CMF por clausura indebida de su cuenta bancaria.

## 6. Aplicación a nuestros desarrollos

> **Nota de Gobernanza (JEV-P07-007)**: La formulación lingüística y sectorial analizada para '"¿Qué pruebas diferencian solicitudes explícitas, cortesía indirecta, ...' se califica como hipótesis de diseño técnico sujeta a validación en banco de pruebas local.

### 3.1 Wheelwork: Mesa de Ayuda y Retención de Clientes
- **Mensaje entrante:** `"Quería consultar si acaso me podrían eximir de la comisión de mantenimiento, porque si no me tocará cambiarme de banco."`
- **Análisis por componentes:**
  - *Cortesía indirecta:* `"Quería consultar si acaso me podrían eximir..."` $\implies$ Solicitud real de condonación de tarifa.
  - *Condición / Advertencia:* `"...porque si no me tocará cambiarme de banco"` $\implies$ Riesgo de fuga de cliente (*churn*), pero **no** solicitud inmediata de cierre de cuenta.
- **Riesgo en pipeline ingenuo:** Si el clasificador asigna *"Cierre de cuenta"*, el sistema inicia el proceso de término de contrato de un cliente que sólo estaba pidiendo una rebaja tarifaria.
- **Solución Canónica:** Preguntas ortogonales determinan que la acción inmediata requerida es `Gestionar Reclamo / Retención`, mientras que `Cerrar Cuenta` arroja `False` con confianza $0.94$.

### 3.2 QRT: Ejecución de Mandatos en Trading Desk
- **Mensaje de cliente institucional:** `"Si el tipo de cambio USD/CLP supera los 950 pesos antes del mediodía, liquiden el 50% de la posición en dólares."`
- **Análisis:** Condición estricta ($P \implies \text{Ejecución}$).
- **Comportamiento requerido:** El sistema de Jev debe catalogar el mensaje como `Condicional Pendiente de Trigger` y asociar los metadatos `threshold: 950, asset: "USD/CLP", deadline: "12:00"`. Si Jev evalúa el texto como una orden a mercado inmediata, causaría una venta no autorizada contraria a la voluntad del cliente.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de Falla y Controles de Mitigación
1. **Atenuación formal de mandatos perentorios bajo fórmulas condicionales de cortesía**: Mitigado mediante validación previa de reglas y enriquecimiento de metadatos en CPU.
2. **Clasificación errónea de solicitudes urgentes como consultas informativas**: Mitigado elevando el umbral de abstención a confidence >= 0.82 en casos ambiguos.
3. **Falta de telemetría de casos frontera**: Mitigado registrando cada decisión y su nivel de confianza en logs auditables.

### 7.2. Gobernanza, Privacidad y Condiciones de No Uso
1. **Protección contra Ejecuciones No Intencionales (Safety Guarantees):**
   - El principio de menor asombro (*Principle of Least Surprise*) exige que ninguna acción financiera irreversible (venta de activos, transferencia de fondos o cierre contractual) sea disparada por un mensaje que contenga condicionales o mitigadores de cortesía sin confirmación previa en un canal secundario.
2. **Trazabilidad de la Fuerza Ilocutiva:**
   - La base de datos de auditoría debe almacenar el desglose de los 3 booleanos de sondeo, permitiendo reconstruir exactamente por qué el software interpretó que una queja cortés constituía una directiva transaccional.

---

### 7.3. Condiciones Taxativas de NO Uso
- **NO confiar en la salida directa del modelo ante diferenciación de actos de habla (solicitudes, cortesía indirecta y promesas) sin verificar el umbral de confianza calibrado**.
- **NO automatizar decisiones irreversibles en flujos donde este fenómeno pueda alterar el significado de la transacción**.
- **NO omitir el escalamiento a supervisión humana cuando la confianza se sitúe en la zona de abstención**.

### 7.1 Hipótesis Falsable
$$H_0: \text{Precision}_{\text{Single-Prompt}}(\text{Condición}) \ge \text{Precision}_{\text{Orthogonal-Probing}}(\text{Condición})$$
*La hipótesis nula postula que una única pregunta clasificatoria multidominio logra igual o mayor precisión para aislar condiciones hipotéticas que una batería de sondeo ortogonal desacoplada.*

### 7.2 Protocolo Experimental
1. **Población:** 120 casos balanceados (30 solicitudes explícitas, 30 peticiones con cortesía indirecta chilena, 30 condiciones con advertencia de cierre y 30 promesas de pago).
2. **Procedimiento Pareado:**
   - Brazo A: Prompt único multiclase en `Choice`: `[Ejecución Inmediata, Espera Condicional, Registro de Promesa, Consulta]`.
   - Brazo B: Sistema de sondeo ortogonal con `SpeechActProbingEngine`.
3. **Criterio de Falsación:**
   - Si $\text{Precision}_{\text{Brazo B}}(\text{Condición}) - \text{Precision}_{\text{Brazo A}}(\text{Condición}) \ge 0.18$ ($p < 0.001$), se **rechaza categóricamente $H_0$**, formalizando el sondeo ortogonal como el único patrón arquitectónico válido para mensajes complejos en producción.
