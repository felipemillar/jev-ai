# JEV-P03-004 — Representación de Información Insuficiente y Abstención en Jev

## 1. Respuesta directa y decisión que permite tomar

La API de Jev v1.13 no cuenta con una bandera mágica de "no lo sé" a nivel de protocolo: la capa Softmax normaliza forzosamente la suma de probabilidades a $1.0$ ($\sum p_k = 1$). Si el objeto `state` carece de los datos necesarios para juzgar pero la pregunta solo ofrece opciones afirmativas o sustantivas, el modelo se verá matemáticamente forzado a elegir la opción menos improbable, emitiendo una decisión errónea inducida por diseño.

La decisión de ingeniería mandataria es: **implementar la abstención formal mediante un diseño dual contractualmente válido**:
1. **A nivel semántico (en el esquema)**: Incluir siempre en las preguntas `Choice` una opción explícita de escape estructurado (ej. `"informacion_insuficiente"` o `"no_consta_en_estado"`).
2. **A nivel algorítmico (en el cliente)**: Aplicar la teoría de **Clasificación Selectiva** (Geifman & El-Yaniv, 2017 / Hendrickx et al., 2021). El software cliente debe rechazar la predicción y abstenerse si la confianza máxima no supera un umbral de cobertura $\tau$ ($\max p_k < \tau$) o si la dispersión de entropía supera el umbral crítico, derivando el caso a un revisor humano o solicitando más telemetría.

## 4. Explicación técnica verificable

### 4.1 Por qué falla el modelo si no se diseña la abstención
Sea un conjunto de opciones cerrado en `Choice`: $\mathcal{Y} = \{\text{Aprobado}, \text{Rechazado}\}$.
Si el `state` contiene únicamente: `{"nombre": "Empresa X"}` (omitiendo balances, facturación e historial crediticio), la red calcula los logits $z_1, z_2$. Aunque ambos sean cercanos a cero o negativos:
$$P(\text{Aprobado}) = \frac{e^{z_1}}{e^{z_1} + e^{z_2}} \approx 0.50, \quad P(\text{Rechazado}) = \frac{e^{z_2}}{e^{z_1} + e^{z_2}} \approx 0.50$$
Jev devolverá forzosamente una de las dos opciones. Si el cliente no inspecciona la confianza y toma el campo `choice`, estará automatizando una decisión crítica basada en puro ruido estadístico.

### 4.2 Arquitectura del Patrón Dual de Abstención

```
                      [ Estado Entrante (state) ]
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────┐
│ MECANISMO 1: ESCAPE SEMÁNTICO EN ESQUEMA (In-Model)             │
│ Question Choice: ¿Es la entidad solvente según el estado?       │
│ Options: ["solvente", "insolvente", "informacion_insuficiente"] │
└─────────────────────────────────┬───────────────────────────────┘
                                  │
                                  ▼
                   [ Inferencia de Jev (API) ]
                                  │
         ┌────────────────────────┴────────────────────────┐
         ▼                                                 ▼
¿Choice == "informacion_insuficiente"?            ¿Choice es sustantiva?
         │                                                 │
         │ (Abstención Explícita)                          ▼
         │                                ┌─────────────────────────────────┐
         │                                │ MECANISMO 2: COMPUERTA CLIENTE  │
         │                                │ (Selective Classification)      │
         │                                │ ¿confidence >= tau (ej. 0.85)?  │
         │                                └────────┬───────────────┬────────┘
         │                                         │               │
         │                                    SÍ ──┘               └── NO
         ▼                                    ▼                        ▼
┌──────────────────┐               ┌──────────────────┐     ┌──────────────────┐
│ SOLICITAR MÁS    │               │ ACCIÓN AUTOMÁTICA│     │ DERIVACIÓN A     │
│ DATOS AL CLIENTE │               │ SEGURA (ACT)     │     │ REVISIÓN HUMANA  │
└──────────────────┘               └──────────────────┘     └──────────────────┘
```

### 4.3 Aplicación de la Abstención a las Tres Primitivas
1. **En `Choice`**:
   - Agregar siempre el valor centinela en el array: `options: ["A", "B", "C", "no_consta_en_estado"]`.
2. **En `Score`**:
   - En una escala de 1 a 5, un estado ambiguo no debe recibir un score inventado de 3.0 (falsa neutralidad). La abstención se detecta analizando la **varianza de la distribución** de probabilidades `probabilities`:
     $$\text{Var}(L) = \sum_{i} (i - \mathbb{E}[L])^2 \cdot p_i$$
     Si la varianza supera un umbral crítico $\sigma^2_{\max}$ (distribución plana o bimodal), el cliente descarta el score y se abstiene.
3. **En `Noul`**:
   - `Noul` devuelve un escalar de probabilidad $p \in [0, 1]$. La abstención se define por la **zona de indiferencia**:
     $$\text{Abstención} \iff |p - 0.5| < \delta \quad (\text{ej. } \delta = 0.25 \implies p \in [0.25, 0.75])$$
     Si la probabilidad está en la zona de duda, el cliente no ejecuta la acción booleana y solicita intervención humana.

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1 Ejemplo Trabajado: Evaluación de Riesgo de Crédito con Documentos Faltantes
- **Estado truncado recibido**:
  ```json
  {
    "rut": "76.123.456-7",
    "razon_social": "Transportes del Sur SpA",
    "monto_solicitado_uf": 500,
    "carpeta_tributaria": null,
    "balance_anual": "archivo_corrupto_no_leible"
  }
  ```
- **Diseño del Criterio con Escape en Choice**:
  - `question`: *«¿Acredita la documentación adjunta en el estado capacidad de pago suficiente para el crédito?»*
  - `options`: `["capacidad_acreditada", "capacidad_insuficiente", "documentacion_incompleta_no_concluyente"]`
- **Respuesta devuelta por Jev**:
  - `choice`: `"documentacion_incompleta_no_concluyente"`
  - `confidence`: `0.962`
- **Acción downstream del cliente**:
  El orquestador detiene el proceso de aprobación y envía un correo automático al solicitante pidiendo re-subir la carpeta tributaria. Se evitó un rechazo injusto o una aprobación temeraria.

### 5.2 Contraejemplo: El Antipatrón de Falsa Certeza Forzada
- **Esquema sin opción de escape**: Se envía el mismo estado truncado con opciones: `["aprobar_credito", "rechazar_credito"]`.
- **Fallo**: Al no tener cómo expresar que faltan datos, Jev evalúa que "un préstamo de 500 UF a una SpA suena estándar" y emite `aprobar_credito` con probabilidad $0.54$.
- **Impacto catastrófico**: Si el integrador solo evaluó `if resp.choice == "aprobar_credito":`, la empresa desembolsará capital a ciegas sin haber visto un solo balance financiero.

## 6. Aplicación a nuestros desarrollos

- **Aplicación en QRT (Trading Cuantitativo)**: En los clasificadores de régimen de mercado, si los datos del libro de órdenes o feeds de volatilidad se desconectan temporalmente o presentan brechas de tiempo (*gaps*), el prompt a Jev debe incluir la opción `"datos_discontinuos_abstencion"`. Si Jev o la compuerta cliente detecta incertidumbre, el sistema conmuta automáticamente al modo *Risk-Off / Flat*, cancelando órdenes activas hasta que se restablezca el flujo de datos.
- **Aplicación en Wheelwork (Soporte Operativo)**: Al clasificar tickets de clientes para auto-resolución con reembolso, si el mensaje del usuario dice simplemente *"Hola, tengo un problema"* sin adjuntar detalles, Jev debe seleccionar `"mensaje_incompleto_pedir_aclaracion"`. Prohibido adivinar si el ticket es de facturación o de bug técnico.

## 7. Fallos, límites, controles y condiciones de no uso

| Modo de Fallo | Impacto | Detección | Control / Mitigación |
| :--- | :--- | :--- | :--- |
| **Omisión de opción de escape en `Choice`** | Alucinaciones forzadas y decisiones erróneas ante datos incompletos. | Linter de esquemas en CI/CD que verifique la presencia de una opción de abstención en cada array de opciones. | Rechazar en el build cualquier pregunta `Choice` que no incluya un centinela de insuficiencia de datos. |
| **Ignorar la zona de indiferencia en `Noul`** | Automatizar acciones cuando la probabilidad es cercana al 50% (lanzar una moneda). | Monitoreo de decisiones tomadas con $|p - 0.5| < 0.20$. | Implementar una compuerta estricta: `if abs(p - 0.5) < 0.25: defer_to_human()`. |
| **Falso escape por sesgo de opción fácil** | El modelo abusa de la opción de abstención incluso cuando el estado sí tiene datos suficientes. | Monitoreo de la tasa de abstención empírica; si supera el 25% en datos normales, hay sesgo de escape. | Ajustar la redacción del escape para que sea explícitamente restrictiva: *"Solo si el estado no contiene X..."*. |

**Condición de no uso**: Prohibido utilizar esquemas de decisión binarios o cerrados sin opción de abstención en flujos donde los datos de entrada provengan de fuentes externas no validadas o sujetas a interrupciones de servicio.

## 8. Validación propuesta

- **Hipótesis falsable**: La combinación de una opción de escape en el esquema con una compuerta de confianza en cliente ($\tau = 0.80$) reduce la tasa de falsos positivos en estados ruidosos o truncados en $>95\%$, logrando un riesgo residual $< 1.5\%$ con una cobertura $\ge 85\%$ en datos completos.
- **Comparador**:
  - Variante A (Control sin abstención): `Choice` con solo opciones sustantivas y aceptación ciega.
  - Variante B (Tratamiento Dual): `Choice` con opción de escape + compuerta de confianza selectiva.
- **Datos y particiones**: 500 escenarios de prueba sintéticos:
  - 300 con información completa y verídica.
  - 100 con información parcial/truncada deliberadamente.
  - 100 con texto completamente irrelevante o corrupto.
- **Métricas**:
  - Tasa de error en casos truncados (*Risk on Truncated Data*).
  - Cobertura global (*Coverage*).
  - Curva Cobertura vs Riesgo (*Risk-Coverage Profile*).
- **Condición de rechazo**: Si la Variante B reduce la cobertura en datos completos por debajo del 80% debido a un exceso de abstenciones indebidas.
- **Presupuesto supuesto**: $12 USD para llamadas de API; 6 horas de evaluación matemática.
- **Estado**: Propuesto, no ejecutado.
