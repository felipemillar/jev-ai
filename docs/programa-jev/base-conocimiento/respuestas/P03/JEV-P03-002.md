# JEV-P03-002 — Descomposición de Peticiones de Negocio en Decisiones Semánticas Atómicas

## 1. Respuesta directa y decisión que permite tomar

Las peticiones de negocio suelen formularse de manera difusa, subjetiva y con objetivos cruzados (ej. *"Filtrar usuarios sospechosos"*, *"Determinar si una orden de trading es segura"* o *"Ver si un reclamo es urgente"*). Enviar estas frases directamente como preguntas a Jev produce juicios inconsistentes, alucinaciones inducidas y fallos de integración. Para automatizar procesos con fiabilidad matemática, el equipo debe aplicar el **Marco de Descomposición Cuádruple (ECSD: Entrada, Criterio, Salida, Destinatario)**.

La decisión metodológica obligatoria es: **prohibir la implementación de cualquier llamada a Jev que no cuente con una Ficha de Decisión Semántica formalmente aprobada**. Dicha ficha debe aislar los cálculos deterministas en la CPU, definir criterios observables libres de ambigüedad léxica, seleccionar la primitiva adecuada (`Choice`, `Score`, `Noul`) y explicitar el componente de software consumidor junto con su compuerta de confianza ($\tau$) y su política de acción ante abstención.

## 2. Alcance, términos y supuestos

- **Ámbito de JEV-P03-002**: El perímetro de JEV-P03-002 modela la interacción del sistema al abordar «¿Cómo descomponer una petición de negocio ambigua en una decisión semántica con entrada, criterio, salida y destinatario definidos».

## 4. Explicación técnica verificable

### 4.1 El Protocolo de Descomposición ECSD en 4 Pasos

```
[ PETICIÓN DE NEGOCIO AMBIGUA ]
"Revisar si el cliente es riesgoso y decidir si le damos crédito"
                    │
                    ▼
┌────────────────────────────────────────────────────────┐
│ 1. AISLAR CÁLCULO NUMÉRICO DE JUICIO SEMÁNTICO         │
│    • CPU calcula: Ratios financieros, mora, DTI.       │
│    • Jev juzga: Coherencia semántica del memo laboral. │
└───────────────────┬────────────────────────────────────┘
                    │
                    ▼
┌────────────────────────────────────────────────────────┐
│ 2. DISEÑAR EL STATE DTO (Entrada Mínima Relevante)     │
│    • Serializar solo variables indispensables.         │
│    • Poda de ruido y anonimización de PII.             │
└───────────────────┬────────────────────────────────────┘
                    │
                    ▼
┌────────────────────────────────────────────────────────┐
│ 3. FORMULAR EL CRITERIO ATÓMICO Y PRIMITIVA (Salida)   │
│    • Mapear a Choice (nominal), Score (ordinal) o Noul.│
│    • Definir anclas mutuamente excluyentes y escape.   │
└───────────────────┬────────────────────────────────────┘
                    │
                    ▼
┌────────────────────────────────────────────────────────┐
│ 4. DEFINIR DESTINATARIO, UMBRAL Y POLÍTICA DE ACCIÓN   │
│    • Código consumidor downstream.                     │
│    • Umbral de confianza: tau = 0.85.                  │
│    • Política de fallback ante incertidumbre.          │
└────────────────────────────────────────────────────────┘
```

### 4.2 La Ficha Canónica de Especificación de Decisión

Todo requerimiento de negocio debe transcribirse en el siguiente contrato técnico antes de escribir código:

```markdown
### FICHA DE ESPECIFICACIÓN: DEC-[ÁMBITO]-[ID]
1. PETICIÓN DE NEGOCIO ORIGINAL: [Texto literal del stakeholder]
2. ENTRADA (State DTO):
   - Campos incluidos: [Variables mínimas y tipos]
   - Cálculos previos en CPU: [Métricas numéricas precalculadas]
   - Límite de tamaño: [< 2.000 tokens]
3. CRITERIO SEMÁNTICO (Question & Schema):
   - Primitiva: [Choice | Score | Noul]
   - Pregunta: [Redacción atómica directa en español/inglés]
   - Opciones / Anclas: [Lista exhaustiva y excluyente + opción de escape]
4. SALIDA TIPADA (Output Schema):
   - Tipo de retorno esperado: [Enum string | Float | Bool]
   - Rango válido: [Ej. 1.0 a 5.0]
5. DESTINATARIO Y POLÍTICA DE ACCIÓN:
   - Consumidor de software: [Módulo / Microservicio que recibe la respuesta]
   - Umbral de confianza automática: [tau >= 0.85]
   - Acción si Confianza >= tau: [Ejecutar acción A en código]
   - Acción si Confianza < tau: [Derivar a revisión humana / Sistema 2]
```

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1 Ejemplo Trabajado: Deconstrucción de "Filtrar usuarios fraudulentos en registro"
- **Petición difusa de negocio**: *"Queremos una IA que mire el registro de usuarios y bloquee automáticamente a los estafadores"*.
- **Paso 1 (Aislamiento en CPU)**:
  - El código valida deterministamente: formato de email (regex), concordancia de IP con país declarado (GeoIP), repetición de número de teléfono en base de datos.
- **Paso 2 (Entrada - State DTO)**:
  ```json
  {
    "antiguedad_dominio_email_dias": 3,
    "coincidencia_nombre_tarjeta": "parcial",
    "descripcion_actividad_declarada": "Inversiones de alta rentabilidad garantizada 500% semanal"
  }
  ```
- **Paso 3 (Criterio y Primitiva - Jev Noul)**:
  - `primitive`: `"Noul"`
  - `statement`: *«¿Presenta la descripción de actividad del usuario promesas financieras inverosímiles, ilícitas o patrones típicos de captación piramidal?»*
- **Paso 4 (Destinatario y Política de Acción en Código)**:
  - **Consumidor**: `ServicioVerificacionIdentidad` (Backend Python).
  - **Lógica downstream**:
    ```python
# Ejemplo ilustrativo no ejecutado
if decision.value == True and decision.probability >= 0.90:
    usuario.bloquear_preventivamente(motivo="fraude_semantico_evidente")
elif decision.probability > 0.40:  # Zona de duda
    usuario.marcar_para_revision_humana_kyc()
else:
    usuario.habilitar_cuenta_estandar()
```

### 5.2 Contraejemplo: El Antipatrón Monolítico
- **Diseño erróneo**: Se envía a Jev:
  - `state`: El objeto completo del usuario de la base de datos (con 40 campos incluyendo contraseñas hasheadas y logs de sesión).
  - `question`: `Choice`: *«¿Es este usuario un estafador y qué debemos hacer con su cuenta?»* con opciones: `["bloquear_cuenta", "pedir_documento", "dejar_pasar", "revisar_manana"]`.
- **Fallo inevitable**: Jev mezcla la probabilidad de fraude con la política de mitigación de la empresa. Si el usuario comete un fraude menor, Jev no sabe si la política corporativa exige pedir documento o bloquear. El modelo emite respuestas inconsistentes porque la decisión no era atómica.

## 6. Aplicación a nuestros desarrollos

- **Aplicación en QRT**: Petición de trading: *"Evaluar si la rueda de prensa del Banco Central fue positiva para el Euro"*.
  - Descomposición obligatoria:
    1. CPU calcula la sorpresa del dato de tasas (Tasa real - Tasa esperada).
    2. Jev (`Score`, escala -2 a +2): Evalúa únicamente el tono discursivo sobre inflación futura (*hawkish* vs *dovish*).
    3. Destinatario (`MotorEjecucionFX`): Si Score > +1.2 y Confianza > 0.85 y Sorpresa >= 0, emite orden de compra escalonada.
- **Aplicación en Wheelwork**: Petición de talento: *"Ver si este candidato calza con la empresa"*.
  - Descomposición: Jev nunca califica "calce global". Se divide en dos decisiones atómicas:
    1. Decisión 1 (`Choice`): Nivel de experiencia demostrado en el rol objetivo (`junior`, `semi_senior`, `senior`).
    2. Decisión 2 (`Score`): Alineación cultural con valores operativos según respuestas del formulario.

## 7. Fallos, límites, controles y condiciones de no uso

| Modo de Fallo | Impacto | Detección | Control / Mitigación |
| :--- | :--- | :--- | :--- |
| **Preguntas multi-intento o compuestas** | Inconsistencia semántica y colapso de certeza. | Detección de conjunciones copulativas ("y", "además") o disyuntivas en el texto de la pregunta. | Linter de CI/CD que rechace preguntas compuestas; forzar la división en dos llamadas paralelas o secuenciales. |
| **Omisión de cálculos previos en CPU** | Errores matemáticos graves en la evaluación del estado. | Presencia de operadores aritméticos en el prompt de la pregunta. | Suministrar métricas numéricas ya calculadas y masticadas en el `state`. |
| **Ausencia de política ante baja confianza** | Ejecución desatendida de decisiones inciertas. | Revisión de código en Pull Requests comprobando si existe `if confidence >= tau`. | Aserción obligatoria en el SDK cliente: rechazar ejecución directa si no se valida el umbral $\tau$. |

**Condición de no uso**: Prohibido enviar peticiones de negocio globales directamente a Jev sin pasar por el proceso de descomposición y redacción de la ficha ECSD.

## 8. Validación propuesta

- **Hipótesis falsable**: La aplicación sistemática de fichas de especificación ECSD reduce en $>50\%$ la discrepancia entre la decisión automática del modelo y el criterio de auditores humanos, comparado con formulaciones directas basadas en el texto original del requerimiento de negocio.
- **Comparador**:
  - Enfoque A: Preguntas formuladas directamente a partir del texto de la petición de negocio.
  - Enfoque B: Preguntas descompuestas bajo el protocolo ECSD con cálculo numérico aislado y criterios atómicos.
- **Datos y particiones**: 200 casos de negocio históricos de QRT y Wheelwork evaluados a ciegas por 3 ingenieros seniors.
- **Métricas**:
  - Coeficiente Kappa de Cohen (concordancia entre modelo y humanos).
  - Tasa de rechazos de auditoría por ambigüedad.
- **Condición de rechazo**: Si el enfoque B no alcanza un Kappa $\ge 0.80$ (acuerdo casi perfecto) frente al panel humano.
- **Presupuesto supuesto**: $10 USD para API tokens; 8 horas de revisión y etiquetado.
- **Estado**: Propuesto, no ejecutado.
