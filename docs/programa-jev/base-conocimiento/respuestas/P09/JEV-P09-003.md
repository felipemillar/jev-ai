# JEV-P09-003 — Diferenciación Arquitectónica: Conector Gemini Notebooks vs Inferencia Jev

## 1. Respuesta directa y decisión que permite tomar

Existe una estricta separación de planos de red y de control entre el conector que consulta los Gemini Notebooks (NotebookLM) y el cliente que invoca la inferencia de Jev. El primero es un conector de gestión de conocimiento que opera vía protocolo MCP sobre stdio o HTTP para extraer fuentes y resúmenes. El segundo es un cliente de datos de baja latencia que ataca directamente `https://api.typesafe.ai/v1/systemone`. Confundir ambos conectores compromete la trazabilidad y la seguridad.

## 2. Alcance, términos y supuestos

- **Ámbito de JEV-P09-003**: La formulación de JEV-P09-003 estandariza la interacción con la API para «¿Cómo diferenciar el conector que consulta Gemini Notebooks del que eventualmente llama a Jev desde Antigravity».
- **Versión de Referencia**: Jev 1.13 (`typesafe_sdk==0.7.0` / `POST /v1/systemone`).
- **Supuesto Operacional**: Se requiere enmascaramiento de datos sensibles previo a la serialización del payload.

## 4. Explicación técnica

Plano de Conocimiento: `gemini-notebooks-mcp` (lectura documental, llamadas a fuentes canónicas, latencia > 1s). Plano de Ejecución: `typesafe_sdk` (inferencia Sistema 1, latencia < 200 ms, payloads atómicos `state` y `questions`).

## 8. Validación propuesta

- **Hipótesis Falsable**: La separación arquitectónica previene que fallos de red en NotebookLM degraden la disponibilidad de la inferencia en producción.
- **Métricas**: Disponibilidad del plano de datos (uptime %) ante caída del plano de consulta.
- **Criterio de Rechazo**: Uptime 100% en plano de inferencia durante fallos simulados en MCP.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
