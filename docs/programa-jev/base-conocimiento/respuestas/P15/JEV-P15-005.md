# JEV-P15-005 — Preservación Estricta del Momento de Disponibilidad (Point-in-Time Compliance)

## 1. Respuesta directa y decisión que permite tomar

Para que una evaluación histórica en QRT tenga validez científica, cada noticia, documento o hecho esencial debe registrar de forma inmutable el momento exacto en que la información estuvo disponible para el mercado (`available_timestamp`), y no la fecha de ocurrencia del suceso ni la fecha de reporte contable. Utilizar una noticia con fecha de ayer que solo se publicó hoy introduce un sesgo de anticipación (look-ahead bias) fatal que invalida cualquier conclusión de simulación.

## 4. Explicación técnica

Doble marca de tiempo: `event_timestamp` (cuándo ocurrió el hecho) y `publication_timestamp` (cuándo se publicó en el cable). En toda simulación de backtesting, el filtro temporal debe ejecutarse estrictamente como `WHERE publication_timestamp <= :simulation_time`.

## 5. Ejemplo ilustrativo, verificación o contraejemplo

```python
# Ejemplo ilustrativo no ejecutado
from datetime import datetime
import logging

logger = logging.getLogger("P15_05")

def validar_point_in_time(fecha_publicacion: datetime, fecha_simulacion: datetime) -> bool:
    try:
        if fecha_publicacion > fecha_simulacion:
            logger.critical("VIOLACION DE POINT-IN-TIME: Intento de usar informacion futura en backtest")
            return False
        return True
    except Exception as err:
        logger.error(f"Fallo en chequeo Point-in-Time: {type(err).__name__} (detalles omitidos por seguridad)")
        return False
```

- **Contraejemplo / Caso borde**: Simular una decisión de trading a las 09:00 AM usando un hecho esencial que la CMF publicó a las 10:30 AM del mismo día generará ganancias irreales en la simulación.

| Modo de Fallo | Impacto Operativo | Detección Temprana | Mitigación Arquitectónica |
| :--- | :--- | :--- | :--- |
| Fuga de información futura (Look-Ahead Bias) | Estrategias ruinosas que parecían rentables en simulación | Filtro estricto por publication_timestamp | Bloqueo absoluto de noticias con timestamp posterior |
| Look-ahead bias por fechas de reporte contable | Resultados de backtest sobreoptimizados | Filtro por publication_timestamp | Bloqueo estricto de eventos con timestamp futuro |

## 8. Validación propuesta

- **Hipótesis Falsable**: La verificación de Point-in-Time elimina en 100% las anomalías por anticipación de noticias en backtests.
- **Métricas**: Eventos con marca temporal posterior al momento de simulación en datasets.
- **Criterio de Rechazo**: 0 registros anacrónicos presentes en simulaciones históricas.
- **Estado**: Protocolo de validación propuesto para banco de pruebas local.
