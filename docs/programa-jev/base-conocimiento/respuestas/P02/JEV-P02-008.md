# JEV-P02-008 — Decisión Tipada Directa vs Generación Autorregresiva con JSON Schema: Análisis Comparativo en Tarea Fija

## 1. Respuesta directa y decisión que permite tomar
Al mantener **estrictamente fija la tarea de juicio semántico** (ej. clasificar la severidad de un incidente en tres categorías a partir de un log de 2.000 tokens), la elección entre proyectar directamente la decisión en **cabezas tipadas nativas (Jev / Sistema Uno)** o forzar a un **modelo autorregresivo a emitir texto sujeto a un esquema JSON (Structured Outputs / Gramáticas BNF)** produce diferencias operativas de naturaleza estructural:
1. **Mecanismo Computacional:** Jev ejecuta un *single forward pass* ($O(1)$ en pasos de decodificación), mientras que un LLM autorregresivo ejecuta un bucle iterativo token a token ($O(N)$) gestionando memoria caché KV y enmascaramiento de logits.
2. **Latencia:** Jev responde en **70–500 ms**, mientras que los Structured Outputs en LLMs toman entre **1.5 y 8+ segundos** (hasta 30–300 s en modelos de razonamiento como o1/o3).
3. **Costo Financiero:** Jev factura **$0.042 / MTok de entrada con salidas gratuitas**, mientras que los LLMs cobran tarifas de entrada 5x a 50x superiores y penalizan fuertemente los tokens de salida estructurados.
4. **Tasa de Error Sintáctico:** Jev garantiza un **0.0% de error de sintaxis por construcción matemática** (imposible emitir JSON roto o claves fuera de enum); en los LLMs estructurados, la tasa de fallo de parseo oscila entre el **0.58% y el 45.5%** en esquemas complejos o cuando el enmascaramiento forzado desestabiliza la atención del decodificador.
5. **Tasa de Error Semántico:** **PERSISTE EN AMBOS PARADIGMAS**. Obligar a la salida a respetar un enum no previene que el modelo elija la categoría equivocada con alta confianza (~32.2% de error semántico).

Esta evidencia permite **decidir adoptar Jev de forma exclusiva para decisiones semánticas de bucle interno donde la latencia (<500 ms) y el coste sean críticos**, eliminando el overhead computacional de los LLMs estructurados, pero manteniendo intactas las compuertas de confianza y la supervisión de errores de juicio semántico.

## 4. Explicación técnica verificable
- **Por qué los Structured Outputs en LLMs son lentos e ineficientes para decisiones puras:**
  Para emitir un simple booleano `"es_urgente": true` mediante JSON Schema, un LLM convencional debe decodificar secuencialmente:
  ```json
  { <token 1>
    "es_urgente" <token 2, 3>
    : <token 4>
    true <token 5>
  } <token 6>
  ```
  Esto exige al menos 6 pasadas autorregresivas completas por la red, actualizando la memoria de atención en cada paso y consultando un analizador léxico de gramática BNF para enmascarar los 128.000 tokens del vocabulario que no sean válidos en ese punto del schema.
- **La eficiencia de la proyección directa en Jev:**
  Jev computa el tensor del estado $H$ una sola vez. La cabeza de `Noul` aplica una multiplicación matricial directa $W \cdot H \to z \in \mathbb{R}$, seguida de un sigmoid escalar. La respuesta se obtiene en **una fracción de microsegundo** sin generar ningún token intermedio de sintaxis JSON.
- **La persistencia del Error Semántico Intra-Esquema:**
  La garantía de 0% de errores de sintaxis en Jev no altera la física del juicio semántico:
  $$\text{Espacio de Salida} = \{\text{"Rutinario"}, \text{"Urgente"}, \text{"Emergencia"}\}$$
  Si un ataque de ciberseguridad sofisticado es clasificado como `"Rutinario"` con probabilidad $p = 0.89$, el cliente HTTP recibe un JSON sintácticamente perfecto, pero el sistema comete un **fallo semántico catastrófico**. Creer que Structured Outputs o Jev eliminan el error del juicio es un error conceptual crítico.

## 5. Ejemplo trabajado y contraejemplo
- **Ejemplo trabajado (Sustitución de Structured Outputs por Jev en triaje de logs):**
  - *Contexto:* Triaje de 50.000 logs de servidor por hora en la infraestructura de QRT.
  - *Arquitectura previa con LLM estructurado (GPT-4o-mini con Pydantic):*
    - Latencia promedio: 1.800 ms por log.
    - Coste por millón de logs: $50.000 \times 1.000\text{ tokens} = 50\text{ MTok in} \times \$0.15 + 2\text{ MTok out} \times \$0.60 = \$8.70\text{ USD}$.
    - Fallos de validación JSON observados: 0.8% (400 errores/hora que requerían reintentos).
  - *Nueva arquitectura con Jev (`Choice` + `Score`):*
    - Latencia promedio: 290 ms por log.
    - Coste por millón de logs: $50\text{ MTok in} \times \$0.042 + \$0.00\text{ out} = \$2.10\text{ USD}$ (Ahorro del 76%).
    - Fallos de validación JSON: **0.0% (Cero reintentos por sintaxis).**
  - *Resultado:* El pipeline procesa el cuádruple de volumen con menor coste y sin errores de parseo.
- **Contraejemplo (Antipatrón: Forzar a Jev a hacer tareas que requieren un LLM estructurado):**
  - Un desarrollador necesita que el sistema analice un contrato legal y extraiga una lista de cláusulas con una breve explicación de por qué representan un riesgo financiero. Intenta usar Jev con múltiples `Choice`. Como Jev no puede generar explicaciones en prosa ni listas dinámicas de longitud variable, el desarrollador fracasa. La tarea requería obligatoriamente un LLM generativo con JSON Schema y cadena de pensamiento previa.

## 6. Aplicación a nuestros desarrollos
- **QRT:**
  - Migrar todos los microservicios de clasificación de texto y triaje de eventos que utilicen actualmente wrappers tipo `Instructor` o `Outlines` sobre LLMs hacia la API de Jev, reduciendo latencias de segundos a cientos de milisegundos.
  - Mantener los LLMs generativos estructurados únicamente para tareas de extracción de entidades nombradas complejas (NER) o redacción de minutas ejecutivas.
- **Wheelwork:**
  - Usar Jev para el cálculo de compatibilidad de habilidades (`Score`) y descarte rápido (`Choice`); usar LLMs estructurados cuando se requiera extraer el historial educativo en un schema relacional complejo con fechas y cargos.

## 7. Fallos, límites y controles
- **Modo de fallo 1: Complacencia ante la perfección sintáctica.** Asumir que porque el validador de Pydantic no arroja excepciones en cliente, la decisión es correcta.
  - *Control:* Implementar compuertas de confianza ($\tau \ge 0.85$) y registrar la distribución de probabilidades devuelta para auditoría estadística de errores semánticos.
- **Modo de fallo 2: Intentar schemas anidados dinámicos de longitud variable.**
  - *Control:* Los schemas de Jev deben ser planos y declarados estáticamente en la llamada; para estructuras de árbol profundamente anidadas de longitud variable, usar LLMs generativos tradicionales.
- **Condición de no uso:** No usar Jev en tareas donde la decisión requiera razonamiento paso a paso (*Scratchpad / Chain-of-Thought*) visible previo a la emisión del resultado.

## 8. Validación propuesta
- **Hipótesis falsable:** "En una tarea idéntica de clasificación de 1.000 tickets con 4 opciones, `jev-1.13.0` registrará una latencia mediana al menos 5 veces menor y una tasa de error de validación sintáctica de exactamente 0.0%, mientras que `gpt-4o-mini` con Structured Outputs registrará al menos 3 fallos de parseo sintáctico o timeouts en el mismo conjunto."
- **Comparador:** Jev `Choice` vs `gpt-4o-mini` con esquema Pydantic en modo `json_schema: { strict: true }`.
- **Datos:** 1.000 tickets de soporte técnico de longitud media (800 tokens).
- **Métricas:** Latencia P50 y P95, coste facturado en USD y tasa de errores de esquema (excepciones de validación).
- **Criterio de rechazo:** Si `gpt-4o-mini` iguala la latencia de Jev o si Jev emite un solo error sintáctico, la hipótesis se considerará refutada.
- **Estado:** *Propuesta, no ejecutada.* (Presupuesto estimado: ~$2.50 USD).
