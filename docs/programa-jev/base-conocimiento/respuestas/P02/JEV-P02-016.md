# JEV-P02-016 — Condiciones que Anulan la Ventaja de Inferencia Anunciada

## 1. Respuesta directa y decisión que permite tomar

Aunque el mecanismo interno de Jev ejecute su pasada de inferencia en GPU en menos de $30\text{–}50\text{ ms}$ exactamente como describe el fabricante, **en un entorno de producción real existen al menos cuatro condiciones externas que pueden degradar o anular totalmente esta ventaja de velocidad**: 
1. La latencia de transporte de red y negociación TLS (que añade $120\text{–}250\text{ ms}$ desde fuera de US-West).
2. El coste de serialización y ancho de banda de payloads de estado extensos ($>15\text{ KB}$).
3. Las colas de espera en los servidores del proveedor ante picos de tráfico (*rate limiting* HTTP 429 o cola saturada HTTP 529).
4. La comparación contra alternativas locales deterministas (funciones en C++/Rust o modelos pequeños en memoria local que resuelven en microsegundos o sub-10 ms sin saltos de red).

La decisión técnica es: **no diseñar arquitecturas de alta frecuencia o de bucle cerrado estricto ($<100\text{ ms}$) basadas en la API remota de Jev**. En sistemas críticos como QRT, Jev debe desplegarse únicamente en componentes asíncronos o con SLAs de decisión superiores a $300\text{ ms}$, o bien evaluar implementaciones abiertas auto-hospedadas (*self-hosted drop-ins* como `jeff`, `SRC-0009`) en la misma red local.

## 2. Alcance, términos y supuestos

- **Ámbito de JEV-P02-016**: El alcance de JEV-P02-016 estructura los requerimientos de «¿Qué condiciones podrían romper una ventaja de inferencia anunciada aunque el mecanismo interno funcione como fue descrito» bajo typesafe-sdk 0.7.0.

## 4. Explicación técnica verificable

### 4.1 Ecuación de descomposición de latencia en producción
La latencia total percibida por la aplicación está gobernada por:
$$T_{\text{E2E}} = T_{\text{ser}} + T_{\text{TLS}} + T_{\text{RTT\_red}} + T_{\text{queue}} + T_{\text{GPU}} + T_{\text{deser}}$$

1. **Transporte Físico y RTT ($T_{\text{RTT\_red}} + T_{\text{TLS}}$)**:
   La velocidad de propagación de la luz en fibra óptica impone un límite físico infranqueable de $\approx 5\text{ ms}$ por cada 1.000 km. Una conexión desde Santiago de Chile o Madrid hacia los servidores de TypeSafe en Oregón/California acumula entre $110\text{ ms}$ y $170\text{ ms}$ de RTT puro, más el apretón de manos TLS inicial.
2. **Serialización de Estados Complejos ($T_{\text{ser}} + T_{\text{deser}}$)**:
   Si el estado incluye un snapshot financiero con cientos de transacciones o un árbol DOM de 20 KB de texto JSON:
   - Serializar el objeto en Python (`json.dumps`): $\approx 2\text{–}6\text{ ms}$.
   - Transmisión por red del paquete fragmentado en múltiples MTUs: $\approx 10\text{–}30\text{ ms}$.
   - Parseo JSON en el servidor: $\approx 2\text{–}5\text{ ms}$.
3. **Colas de Servicio y Batching Dinámico ($T_{\text{queue}}$)**:
   Para ser económicamente viable, el gateway de TypeSafe agrupa peticiones de múltiples clientes en micro-lotes (*dynamic batching*, parámetro `JEFF_MAX_WAIT_MS` en implementaciones abiertas). Si el servidor retiene una petición hasta $20\text{ ms}$ para llenar el lote de la GPU, la latencia individual se incrementa directamente.
4. **Respuesta a Errores y Reintentos**:
   Bajo congestión, si el gateway emite un error HTTP 429 (*Rate Limit Exceeded*) o HTTP 529 (*Server Overloaded*), cualquier política estándar de reintento con retroceso exponencial (*exponential backoff*) añade un mínimo de $500\text{–}2.000\text{ ms}$, destruyendo por completo cualquier ventaja de velocidad.

```

┌────────┬───────────────────────────────────┬────────┬────────┐
│  Ser   │       Transporte de Red + TLS     │ Colas  │  GPU   │
│ (5 ms) │              (150 ms)             │(15 ms) │(50 ms) │
└────────┴───────────────────────────────────┴────────┴────────┘
 0 ms                                                         220 ms
          ▲

```

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1 Ejemplo trabajado: Comparación de ejecución para decisión en trading
- **Tarea**: Validar si un tick de precio entrante presenta una divergencia de liquidez anómala que exige pausar las órdenes.
- **Opción A (Jev SaaS remoto)**:
  - Serialización DTO: $3\text{ ms}$.
  - RTT de red Santiago $\to$ US-West: $135\text{ ms}$.
  - Inferencia Jev: $40\text{ ms}$.
  - Deserialización: $2\text{ ms}$.
  - **Latencia total**: **$180\text{ ms}$**. Para cuando la respuesta llega, el precio del activo ya cambió y 5 bloques de transacciones pasaron en el exchange.
- **Opción B (Regla en memoria C++ en servidor colocalizado)**:
  - Cálculo de Z-Score de volumen en microsegundos: $0.005\text{ ms}$.
  - Decisión determinista: **$<0.01\text{ ms}$**.
  - **Conclusión**: La ventaja de Jev queda completamente rota frente a código determinista local.

### 5.2 Contraejemplo o caso límite: Dónde la ventaja SÍ se mantiene
- **Tarea**: Clasificación de tickets de soporte o enriquecimiento de leads en un flujo batch asíncrono.
- **Comparador**: GPT-4o vía API remota vs Jev vía API remota (ambas sujetas a la misma latencia de red de $140\text{ ms}$).
  - GPT-4o tarda $140\text{ ms (red)} + 850\text{ ms (generación 50 tokens)} = 990\text{ ms}$.
  - Jev tarda $140\text{ ms (red)} + 40\text{ ms (GPU)} = 180\text{ ms}$.
  - **Resultado**: En este escenario, la eliminación de la decodificación autorregresiva otorga una ganancia real de $5.5\times$ en velocidad y $400\times$ en costo.

## 6. Aplicación a nuestros desarrollos

- **QRT (Directriz de Arquitectura)**: QRT descarta tajantemente el uso de la API remota de Jev dentro del bucle de microestructura de mercado (*order execution hot-path*). Jev solo es elegible para:
  1. Tareas de investigación offline y análisis de diarios de trading al cierre de mercado.
  2. Detección de régimen macroeconómico en marcos temporales de 15 minutos a 1 hora.
  3. En caso de requerir juicios semánticos de menor latencia, se debe evaluar el despliegue del equivalente auto-hospedado (`jeff`) en la misma red local del servidor de trading.
- **Wheelwork (Flujos Asíncronos)**: En Wheelwork, la latencia de $250\text{ ms}$ es perfectamente aceptable para ruteo de tickets o moderación de contenido en background. Se debe configurar un *Connection Pool* HTTP persistente (HTTP keep-alive) para evitar renegociar el apretón de manos TLS en cada llamada.

## 7. Fallos, límites, controles y condiciones de no uso

| Modo de Fallo | Impacto | Detección | Control / Mitigación |
| :--- | :--- | :--- | :--- |
| **Picos de latencia de red (Jitter / Packet Loss)** | Tiempos de respuesta impredecibles que superan el SLA del sistema. | Telemetría p99 de tiempos de socket y timeouts frecuentes. | Establecer un *timeout* agresivo en el cliente (ej. $350\text{ ms}$) y conmutar a un fallback determinista local si expira. |
| **Saturación de colas por lote (HTTP 529)** | Rechazo de peticiones en momentos de alta demanda global de TypeSafe. | Monitoreo de códigos de estado HTTP en el gateway del cliente. | Implementar patrón *Circuit Breaker* para no inundar el servicio saturado. |
| **Payloads JSON inflados** | Degradación de tiempo de red y serialización que triplica la latencia normal. | Alertas de tamaño de solicitud saliente en bytes. | Comprimir o filtrar claves irrelevantes del estado antes de serializar; límite de $10\text{ KB}$ por solicitud. |

**Condición de no uso**: Prohibido el uso de la API SaaS de Jev en cualquier componente de software con un presupuesto de latencia estricto menor a $200\text{ ms}$ ubicado geográficamente fuera de la región cloud del proveedor.

## 8. Validación propuesta

- **Hipótesis falsable**: La variabilidad de red (RTT + jitter) y la serialización JSON explican más del 70% de la varianza total de latencia en peticiones a la API SaaS de Jev realizadas desde servidores fuera de la región US-West.
- **Comparador**: 
  - Mediciones de latencia desglosada (Socket Connect, TLS Handshake, TTFB, Total Transfer) hacia la API remota.
  - Mediciones idénticas hacia un contenedor local con `jeff` en la misma máquina.
- **Datos y particiones**: 5.000 peticiones sintéticas distribuidas en 24 horas continuas para capturar congestión diurna y nocturna.
- **Métricas**:
  - Tiempo de ida y vuelta de red (RTT).
  - TTFB (Time to First Byte).
  - Tiempo total de llamada (p50, p95, p99).
- **Condición de rechazo**: Si el tiempo de inferencia del servidor explica más del 50% de la latencia total E2E.
- **Presupuesto supuesto**: $15 USD para llamadas a la API; script de telemetría en Python con `httpx`.
- **Estado**: Propuesto, no ejecutado.
