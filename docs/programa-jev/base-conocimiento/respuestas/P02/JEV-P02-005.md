# JEV-P02-005 — Mecanismo Interno frente a Contrato Externo: Qué Conductas de la API Revelan y Cuáles Ocultan la Arquitectura

## 1. Respuesta directa y decisión que permite tomar
Existe una relación de diseño estricta y deliberada entre el mecanismo interno divulgado por TypeSafe AI y el contrato externo de su API: (1) la separación forzosa entre el campo `state` y el array `questions` responde directamente a la necesidad de **codificar el contexto una sola vez en GPU** antes de proyectarlo en múltiples cabezas de decisión; (2) el mecanismo del **Parallel Sampler** explica por qué el contrato HTTP no ofrece soporte para streaming de tokens (SSE) y devuelve siempre un payload JSON monolítico con tensores de probabilidad; y (3) la **regla de independencia estricta** garantiza que las preguntas se evalúen como dimensiones ortogonales sin atención cruzada entre salidas.

Sin embargo, tres conductas observables de la API **son a menudo malinterpretadas como pruebas de la arquitectura interna cuando en realidad no revelan nada sobre el modelo subyacente**:
1. **La baja latencia (70–500 ms) y el bajo coste ($0.042/M):** Confirman la ausencia de decodificación autorregresiva token a token, pero **no revelan el tamaño de parámetros** (no se puede inferir si el modelo tiene 400M, 1.5B o 3B de parámetros) ni la topología del cluster de GPU.
2. **El cumplimiento de esquema JSON al 100%:** Una salida estructurada infalible puede lograrse mediante cabezas de clasificación fijas, decodificación restringida por gramáticas BNF (tipo Outlines o Guidance) o decodificación guiada por máscaras de logits sobre decodificadores tradicionales; por tanto, **no demuestra que el modelo sea un codificador puro tipo BERT**.
3. **Las probabilidades normalizadas en coma flotante:** La presencia de números decimales que suman 1.0 no revela la función de pérdida del entrenamiento (si fue RLCD, entropía cruzada o Brier Score), ni si el modelo fue preentrenado desde cero o destilado a partir del consenso de GPT-6 Astra y Claude Fable.

Esta evidencia permite **decidir no hacer ingeniería inversa especulativa sobre la arquitectura interna de TypeSafe**, tratar a Jev estrictamente como un oráculo de clasificación de caja negra gobernado por contratos externos, y diseñar nuestras pruebas de validación midiendo el comportamiento empírico de caja negra sin suponer propiedades de modelos abiertos.

## 4. Explicación técnica verificable
- **La falacia de la deducción de arquitectura por formato:**
  Consideremos dos arquitecturas radicalmente distintas:
  - *Arquitectura A (Codificador Denso Bidireccional):* Un modelo tipo DeBERTa-v3 de 1.5B parámetros con una capa lineal de clasificación acoplada al token de pooling `[CLS]`.
  - *Arquitectura B (Decodificador Generativo con Gramática Restringida):* Un modelo tipo Llama-3 de 3B decapitado donde un motor de gramática BNF enmascara los logits para que solo pueda emitir los tokens exactos del schema `{"decision": "X", "confidence": 0.YY}`.
  - *Resultado observable:* Para un cliente que envía un HTTP POST, **ambas arquitecturas producen exactamente la misma conducta externa**: latencia de cientos de milisegundos, 0% errores de esquema y salida JSON tipada.
  - Por tanto, es metodológicamente incorrecto afirmar que la conducta de la API "demuestra" que Jev es un encoder o que utiliza una nueva familia de redes neuronales.
- **Lo que SÍ impone el contrato externo:**
  El contrato impone que no existe estado compartido entre llamadas. Dos llamadas consecutivas con 1 milisegundo de diferencia no comparten caché KV a nivel de cliente; cada llamada debe autosufragar todo su contexto dentro de los 32k tokens del `state`.

## 5. Ejemplo trabajado y contraejemplo
- **Ejemplo trabajado (Diseño agnóstico de la arquitectura interna en QRT):**
  - *Contexto:* Un equipo desea desacoplar el sistema de trading de la implementación específica de TypeSafe.
  - *Diseño de contrato:*
    ```python
# Ejemplo ilustrativo no ejecutado
from typing import Protocol, Dict
from typesafe_sdk import TypeSafeClient, Choice

# Contrato abstracto basado estrictamente en la conducta observable:
class DecisionOracle(Protocol):
    def evaluate_choice(self, state: str, question: str, criteria: Dict[str, str]) -> Dict[str, float]:
        ...

# Implementación A: TypeSafe Jev (SaaS)
class TypeSafeJevOracle:
    def __init__(self, client: TypeSafeClient):
        self.client = client

    def evaluate_choice(self, state: str, question: str, criteria: Dict[str, str]) -> Dict[str, float]:
        res = self.client.system_one(
            state=state,
            questions={question: Choice(instructions=question, criteria=criteria)}
        )
        return res.answers[question].probabilities

# Implementación B: Local Fallback con GLiFormer (jeff) o DeBERTa-v3
class LocalNLIOracle:
    def evaluate_choice(self, state: str, question: str, criteria: Dict[str, str]) -> Dict[str, float]:
        return local_zero_shot_classifier(state, list(criteria.keys()))
```
  - *Resultado:* El código de trading interactúa con una interfaz abstracta; si TypeSafe cambia su infraestructura o sufre caídas, se activa el oráculo local sin modificar la lógica de negocio.
- **Contraejemplo (Antipatrón: Acoplar el software a suposiciones sobre el mecanismo interno):**
  - Un desarrollador asume que Jev internamente almacena en caché el embedding del `state` entre diferentes peticiones HTTP si el hash es el mismo. Diseña un sistema que envía un `state` masivo en la primera llamada y luego envía 10 llamadas subsecuentes con preguntas individuales esperando que "el servidor reutilice el embedding en memoria". Como la API no mantiene estado de sesión (stateless), cada llamada vuelve a facturar los 30k tokens de entrada y a recomputar el embedding completo, multiplicando por 10 el coste y la latencia.

## 6. Aplicación a nuestros desarrollos
- **QRT:**
  - Tratar a Jev como un componente sin estado (*stateless*). Toda la información necesaria para el juicio debe viajar explícitamente en el payload de entrada.
  - Implementar el patrón de interfaz abstracta `DecisionOracle` para permitir conmutación transparente entre Jev oficial, proxies de pasarela (Cloudflare/Vercel) y modelos locales de fallback.
- **Wheelwork:**
  - No asumir que Jev "aprende" o "recuerda" candidatos anteriores a partir de las decisiones tomadas; cada candidato debe ser evaluado contra un `state` completo y autónomo.

## 7. Fallos, límites y controles
- **Modo de fallo 1: Creer que la API tiene memoria entre peticiones.**
  - *Control:* El SDK debe validar que cada petición sea completamente independiente y no dependa de contextos previos.
- **Modo de fallo 2: Confundir probabilidades normalizadas con probabilidades bien calibradas.**
  - *Control:* Recordar que un softmax siempre suma 1.0; la calibración real debe verificarse experimentalmente con ECE en datos locales.
- **Condición de no uso:** No utilizar Jev esperando que mantenga sesiones de diálogo, buffers conversacionales o memoria asociativa distribuida.

## 8. Validación propuesta
- **Hipótesis falsable:** "La ejecución de 10 llamadas idénticas consecutivas con el mismo `state` de 10.000 tokens registrará una latencia de inferencia en servidor indistinguible entre la primera y la décima llamada (variación $<\pm 5\%$), confirmando que el servicio no implementa caché de embeddings de estado entre peticiones HTTP distintas."
- **Comparador:** Latencia de primera llamada en frío vs llamadas 2 a 10 con idéntico payload.
- **Datos:** 1 payload de 10.000 tokens repetido en ráfaga rápida (1 req/segundo).
- **Métricas:** Latencia de servidor y tiempo de procesamiento en GPU informado por la API.
- **Criterio de rechazo:** Si a partir de la segunda llamada la latencia cae en más de un 60%, se confirmará la existencia de un mecanismo interno de KV/Embedding Caching inter-peticiones no documentado.
- **Estado:** *Propuesta, no ejecutada.* (Presupuesto estimado: <$0.15 USD).
