# JEV-P04-006: Comparación de Formatos de Estado (Texto, JSON, Tablas) con Información Constante

## 1. Respuesta directa y decisión que permite tomar

Para evaluar rigurosamente el impacto del formato de entrada en Jev 1.13, se debe aislar la sintaxis de serialización manteniendo **rigurosamente constante el contenido informativo** (exactamente las mismas entidades, relaciones temporales, valores numéricos y hechos observables). Bajo este control univariante:

1. **JSON Estructurado (`object`) — Estándar de Oro**: Es el formato superior y obligatorio para decisiones en producción. Al encapsular datos en pares clave-valor tipados (`{"orden_id": "...", "importe_usd": 4500.0, "estado": "CONFIRMADO"}`), delimita fronteras semánticas inequívocas, elimina la ambigüedad entre metadatos y contenido, y permite que las instrucciones de Jev hagan referencia directa a rutas de atributos específicas (e.g. *"Evaluar si `telemetry.error_code` indica una falla crítica"*). Minimiza la entropía de la atención y maximiza la estabilidad probabilística.
2. **Texto Plano Desestructurado (`string`)**: Conviene únicamente para pasajes literarios continuos, transcripciones de voz fluidas o artículos periodísticos donde no existen campos formalizables. Su uso en datos transaccionales es desaconsejado: el modelo se ve forzado a inferir implícitamente qué palabras corresponden a roles, marcas temporales o importes, lo que incrementa la varianza atencional y diluye la certeza de softmax.
3. **Tablas / Arreglos Secuenciales (`array`)**: Son óptimos para series cronológicas de eventos homogéneos (e.g. trazas de logs `[t0, t1, t2]`) o listas de ítems de una factura. Sin embargo, resultan inferiores a JSON para consultas atómicas sobre propiedades individuales.
4. **Combinación Híbrida (JSON Canónico con Campos Textuales)**: La arquitectura óptima consiste en un envoltorio JSON raíz cuyas claves estructuran los metadatos y el tipo de evento, y dentro del cual residen cadenas de texto limpio para las citas o fragmentos textuales relevantes.

**Decisión que permite tomar**: Estandarizar el uso de JSON estructurado (`object`) para el 100% de los contratos de entrada de QRT y Wheelwork. Prohibir el aplanamiento de datos estructurados a párrafos de texto libre (*prompt stuffing* en prosa) cuando las fuentes de origen ya son tablas o registros de base de datos.

## 4. Explicación técnica verificable

### 4.1. Protocolo de Evaluación bajo Información Constante

Para comparar objetivamente los tres formatos, se construye un triplete sintético isomorphicamente equivalente:
- **Grafo de Hechos Base $\mathcal{G}$**: $\{\text{Sujeto: Empleado\_A1}, \text{Acción: Intento\_Acceso}, \text{Hora: 03:15 UTC}, \text{IP: 192.168.1.50}, \text{Resultado: Bloqueado}\}$.

#### Formato 1: Texto Plano Desestructurado
```text
El Empleado_A1 intentó acceder al servidor a las 03:15 UTC desde la dirección IP 192.168.1.50 pero la operación resultó bloqueada por las políticas de seguridad.
```
- *Tokens*: 34 tokens.
- *Atención*: El modelo debe computar dependencias sintácticas entre sujeto, verbo, complementos circunstanciales y adverbios adversativos (`"pero"`).

#### Formato 2: Objeto JSON Estructurado Canónico
```json
{
  "sujeto": "Empleado_A1",
  "accion": "Intento_Acceso",
  "hora_utc": "03:15",
  "ip_origen": "192.168.1.50",
  "resultado": "BLOQUEADO"
}
```
- *Tokens*: 38 tokens.
- *Atención*: Las claves actúan como anclas atencionales unívocas. La instrucción `"¿Cuál es el valor de resultado?"` canaliza directamente los pesos de atención hacia el token `"BLOQUEADO"`, reduciendo la entropía del clasificador.

#### Formato 3: Tabla Markdown
```markdown
| Sujeto | Acción | Hora UTC | IP Origen | Resultado |
| :--- | :--- | :--- | :--- | :--- |
| Empleado_A1 | Intento_Acceso | 03:15 | 192.168.1.50 | BLOQUEADO |
```
- *Tokens*: 48 tokens.
- *Atención*: Sobrecarga de tokens estructurales (`|`, `---`) que dispersan la atención posicional sin aportar semántica.

Generador de variantes isomórficas con información estrictamente constante

import json
from typing import Dict, Any, Tuple

# Hechos constantes de un incidente de trading
TRADE_FACTS = {
    "trade_id": "TRD-8891",
    "timestamp_utc": "2026-09-19T23:30:00Z",

def generate_text_variant(facts: Dict[str, Any]) -> str:

        f"Se solicitaron {facts['requested_volume']:,.0f} unidades pero solo se ejecutaron {facts['executed_volume']:,.0f} unidades. "

        },
        "diagnostico_broker": {
            "estado": facts["status"],
            "observacion": facts["broker_comment"]
        }
    }

def generate_table_variant(facts: Dict[str, Any]) -> str:

        f"| Ejecutado | {facts['executed_volume']} |\n"

    print(f"Longitud estimada: {len(v_table)/4:.0f} tokens")

### 5.2. Contraejemplo y caso límite: Inyección de Prosa Ambigua que Provoca Colapso de Criterio

Considérese el caso en el que se suministra el texto en prosa libre para verificar si una orden de compra fue totalmente liquidada:
- **Texto en Prosa**: `"La orden de 500k USD se ejecutó a 945.20 excepto por una fracción de 10k que fue cancelada por tiempo."`
- **Inferencia en Prosa**: Al leer la oración, la proximidad léxica entre `"se ejecutó"` y `"500k USD"` provoca que Jev asigne $p = 0.82$ en `Noul` a la pregunta *"¿Fue la orden liquidada completamente?"*. El modelo pasó por alto la subordinada adversativa `"excepto por una fracción..."`.
- **Inferencia en JSON Canónico**: Si el estado se serializa como:
  ```json
  {"volumen_solicitado": 500000, "volumen_liquidado": 490000, "volumen_cancelado": 10000, "estado": "EJECUCION_PARCIAL"}
  ```
  Jev evalúa directamente el atributo `estado` y asigna $p = 0.01$ (Cero coincidencia). El JSON eliminó por completo el error inducido por la ambigüedad sintáctica de la prosa.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla específicos
1. **Fallo por Claves Extensas o Redundantes**: Diseñar estructuras JSON con nombres de clave excesivamente verbosos (e.g. `la_orden_de_compra_que_fue_solicitada_por_el_usuario_final`), lo que desperdicia tokens útiles de contexto.
   - *Control*: Exigir nombres de clave concisos y descriptivos en *snake_case* (e.g. `orden_solicitada`).
2. **Fallo por Escapado de Caracteres en JSON**: Incluir texto libre que contenga comillas no escapadas o caracteres de control que rompan la deserialización en el servidor de Jev.
   - *Control*: Utilizar librerías robustas de serialización (`json.dumps` o Pydantic) que garanticen JSON 100% conforme a RFC 8259.

### 7.2. Condiciones taxativas de no uso
- **No usar tablas complejas con celdas fusionadas (merged cells) ni matrices multidimensionales sin aplanar**: Jev no interpreta relaciones de matrices densas bidimensionales en un solo pase atencional; se debe desanidar la tabla en una lista lineal de objetos.

## 8. Validación propuesta (propuesta, no ejecutada)

- **Hipótesis falsable**: Para una batería de 300 eventos de trading con ambigüedad sintáctica en su descripción, la representación en JSON estructurado obtiene un **18% más de precisión** y una certidumbre $|2p-1|$ un **25% superior** en comparación con la representación en texto plano en prosa, manteniendo el contenido factual estrictamente idéntico.
- **Comparador / Línea base**: Inferencia de Jev sobre texto plano en prosa equivalente.
- **Conjunto de datos sintético**: 300 eventos sintéticos generados en tripletes idénticos (Prosa, JSON y Tabla Markdown).
- **Métricas cuantitativas**:
  - Exactitud Factual Top-1.
  - Certidumbre media $\mathbb{E}[|2p-1|]$.
  - Tasa de Desacuerdo Inter-Formato (Inconsistency Rate).
- **Umbral de éxito**: Precisión JSON $\ge 95\%$ vs. Prosa $\le 78\%$; Certidumbre JSON $\ge 0.88$ vs. Prosa $\le 0.65$.
- **Criterio de rechazo**: Si el texto plano supera al JSON estructurado en precisión o calibración.
- **Presupuesto supuesto**: 900 llamadas a endpoints de Jev; coste API estimado en \$0.003; tiempo de cómputo en CPU: 7 minutos.
