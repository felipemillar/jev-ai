# JEV-P04-018: Diseño de Validador Previo de Completitud sin Falsos Rechazos de Casos Límite

## 1. Respuesta directa y decisión que permite tomar

El diseño de un validador previo en la arquitectura de Jev 1.13 enfrenta un dilema crítico de ingeniería:
- Si el validador es **excesivamente laxo**, permite que cargas incompletas, truncadas o corruptas lleguen a Jev, provocando llamadas costosas inútiles, alucinaciones inductivas y fallas de calibración por falta de hechos esenciales.
- Si el validador es **excesivamente rígido** (exigiendo que el 100% de los campos de un formulario estén poblados), descarta sistemáticamente **casos límite válidos pero atípicos** (e.g., un cliente joven sin historial bancario que adjunta un contrato de trabajo, o una empresa recién constituida que carece de balance anual del año anterior).

Para resolver este dilema, el validador previo no debe diseñarse como una lista plana de campos obligatorios, sino como un **Validador Jerárquico en Dos Niveles con Lógica de Ramas de Evidencia Suficiente (Evidence Trees)**:

1. **Nivel 1: Validación Estructural Sintética Dura (Esquema e Invariantes Operacionales)**:
   - Valida la integridad del JSON, tipos de datos, rangos numéricos razonables y presencia de metadatos de sobre (`cliente_id`, `timestamp_iso8601_utc`, `version_esquema`).
   - Verifica que el payload no supere el límite duro de tokens ($32,000$) ni el umbral de advertencia ($2,000$).
2. **Nivel 2: Validación Semántica por Ramas de Evidencia Mínima Suficiente (REMS)**:
   - Emplea la **Lógica Cuadrivaluada** (JEV-P04-003): distingue si un dato ausente es una falla de ingesta (`DATO_NO_PROVISTO`) o una ausencia legítima de negocio (`NO_APLICA` o `CONFIRMADO_NEGATIVO`).
   - Define el requerimiento de información mediante **Fórmulas Booleanas de Suficiencia (Dra. DNF / CNF)**. Por ejemplo: para evaluar capacidad de pago, la regla exige `(Declaración_Renta) O (Liquidación_Sueldo AND Contrato_Vigente) O (Extractos_Bancarios_3_Meses)`. Si el usuario no tiene liquidación de sueldo pero presenta extractos bancarios, el validador reconoce un caso límite válido y lo aprueba para inferencia en Jev.
3. **Contrato de Rechazo Diagnóstico Accionable**:
   - Si la carga útil se rechaza, el validador en CPU no emite un genérico "Bad Request", sino un objeto diagnóstico estructurado (`HTTP 422 Unprocessable Content`) que especifica exactamente qué rama de suficiencia falló y qué combinaciones de datos permitirían satisfacerla.

**Decisión que permite tomar**: Prohibir validadores planos basados únicamente en `required: [field1, field2, ...]`. Toda compuerta pre-Jev debe evaluar árboles de suficiencia lógica multivaluada, permitiendo la inferencia de casos límite con datos dispersos siempre que satisfagan al menos una rama probatoria completa.

### 5.1. Ejemplo sintético trabajado: Validador de Ramas de Evidencia en Python

```python
# Ejemplo ilustrativo no ejecutado
"""
Validador pre-vuelo de completitud y casos límite para Jev 1.13.
"""
from dataclasses import dataclass, field
from typing import Dict, Any, List, Optional, Tuple
from enum import Enum
import json

class EstadoDato(str, Enum):
    PRESENTE = "PRESENTE"
    CONFIRMADO_NEGATIVO = "CONFIRMADO_NEGATIVO"
    NO_APLICA = "NO_APLICA"
    DATO_NO_PROVISTO = "DATO_NO_PROVISTO"

@dataclass
class RequisitoDato:
    nombre_campo: str
    estado_esperado: List[EstadoDato] = field(default_factory=lambda: [EstadoDato.PRESENTE])

@dataclass
class RamaEvidencia:
    id_rama: str
    descripcion: str
    requisitos: List[str]  # Lista de campos que deben estar PRESENTE o válidamente justificados

class ValidadorPreVueloJev:
    def __init__(self, ramas: List[RamaEvidencia]):
        self.ramas = ramas

    def validar_sintaxis_basica(self, payload: Dict[str, Any]) -> Tuple[bool, Optional[str]]:
        """Nivel 1: Validación estructural dura."""
        if not isinstance(payload, dict):
            return False, "Payload debe ser un objeto JSON."
        if "cliente_id" not in payload or not payload["cliente_id"]:
            return False, "Campo obligatorio 'cliente_id' ausente."
        if "datos_financieros" not in payload or not isinstance(payload["datos_financieros"], dict):
            return False, "Campo 'datos_financieros' debe ser un diccionario válido."
        return True, None

    def validar_suficiencia_semantica(self, datos: Dict[str, Any]) -> Tuple[bool, Optional[Dict[str, Any]]]:
        """Nivel 2: Comprobación de ramas disyuntivas."""
        ramas_satisfechas = []
        diagnostico_faltantes = []

        for rama in self.ramas:
            campos_faltantes = []
            for campo in rama.requisitos:
                val = datos.get(campo)
                # Se considera presente si tiene valor real o explícitamente confirmado como no aplica
                if val is None or val == "" or val == EstadoDato.DATO_NO_PROVISTO.value:
                    campos_faltantes.append(campo)

            if not campos_faltantes:
                ramas_satisfechas.append(rama.id_rama)
            else:
                diagnostico_faltantes.append({
                    "rama": rama.id_rama,
                    "descripcion": rama.descripcion,
                    "campos_faltantes": campos_faltantes
                })

        if ramas_satisfechas:
            return True, {"ramas_aprobadas": ramas_satisfechas}
        else:
            return False, {
                "error": "EVIDENCIA_INSUFICIENTE_PARA_DECISION",
                "mensaje": "La solicitud no cumple ninguna de las ramas probatorias mínimas necesarias.",
                "alternativas_para_subsanar": diagnostico_faltantes
            }

# Simulación de ejecución
if __name__ == "__main__":
    # Definición de ramas de suficiencia para evaluación de arriendo vehicular (Wheelwork)
    ramas_wheelwork = [
        RamaEvidencia(
            id_rama="RAMA_DEPENDIENTE",
            descripcion="Acreditación como trabajador dependiente",
            requisitos=["liquidaciones_sueldo", "contrato_trabajo_indefinido"]
        ),
        RamaEvidencia(
            id_rama="RAMA_INDEPENDIENTE_BOLETAS",
            descripcion="Acreditación como profesional independiente",
            requisitos=["informe_boletas_honorarios_anual", "formulario_29_sii"]
        ),
        RamaEvidencia(
            id_rama="RAMA_AVAL_GARANTIA",
            descripcion="Acreditación mediante aval o garantía prendaria",
            requisitos=["rut_aval", "renta_aval", "autorizacion_aval"]
        )
    ]

    validador = ValidadorPreVueloJev(ramas_wheelwork)

    # Caso 1: Caso límite difícil pero VÁLIDO (Independiente que no tiene liquidaciones)
    caso_limite_valido = {
        "cliente_id": "CLI-9901",
        "datos_financieros": {
            "liquidaciones_sueldo": None,  # No tiene, es independiente
            "contrato_trabajo_indefinido": None,
            "informe_boletas_honorarios_anual": {"total_anual": 24000000},
            "formulario_29_sii": {"meses_declarados": 12}
        }
    }

    valido_s1, err_s1 = validador.validar_sintaxis_basica(caso_limite_valido)
    valido_s2, diag_s2 = validador.validar_suficiencia_semantica(caso_limite_valido["datos_financieros"])
    print(f"Caso 1 (Independiente sin Liquidación): ¿Aprobado para Jev? {valido_s2}")
    print(f"Detalle: {diag_s2}\n")

    # Caso 2: Caso INCOMPLETO REAL (No cumple ninguna rama completa)
    caso_incompleto = {
        "cliente_id": "CLI-9902",
        "datos_financieros": {
            "liquidaciones_sueldo": None,
            "contrato_trabajo_indefinido": {"fecha_ingreso": "2024-01-01"},  # Tiene contrato pero no sueldos
            "informe_boletas_honorarios_anual": None,
            "rut_aval": "12.345.678-9"  # Tiene aval pero falta la renta y autorización
        }
    }
    valido_s2_inc, diag_s2_inc = validador.validar_suficiencia_semantica(caso_incompleto["datos_financieros"])
    print(f"Caso 2 (Entrada Parcial Inviable): ¿Aprobado para Jev? {valido_s2_inc}")
    print("Respuesta Diagnóstica (HTTP 422):")
    print(json.dumps(diag_s2_inc, indent=2, ensure_ascii=False))
```

### 5.2. Contraejemplo y Caso Límite: Exclusión Ilegítima de un Usuario Extranjero con Documentación Equivalente

En una plataforma de financiamiento vehicular, un solicitante es de nacionalidad extranjera con residencia en trámite, por lo que carece de cédula de identidad definitiva (`rut_chileno: null`), pero adjunta:
1. Pasaporte vigente oficial (`pasaporte: "AB891234"`).
2. Certificado de Residencia Temporal emitido por el Servicio Nacional de Migraciones.
3. Contrato de trabajo y 6 liquidaciones de sueldo con RUT provisorio.

- **Falla del validador plano**: El esquema clásico exige `rut_chileno: string (required)`. El validador rechaza la solicitud de inmediato con HTTP 400.
- **Manejo correcto por Árbol de Evidencia**: La rama de identidad define `(RUT_Chileno) OR (Pasaporte_Vigente AND Certificado_Migraciones)`. El validador en CPU valida la segunda opción y permite el paso a Jev 1.13, el cual evaluará la solvencia laboral sin descartar discriminatoriamente a un cliente legítimo de alto valor.

## 6. Aplicación a nuestros desarrollos

### 6.1. Hechos verificables en proyectos existentes

1. **Wheelwork (Evaluación de Riesgo de Arrendatarios)**:
   - Recibe solicitudes de conductores de aplicaciones, trabajadores independientes y empresas que postulan a flotas.
   - *Hecho*: Los postulantes poseen estructuras documentales heterogéneas; imponer una validación fija monolítica provocaba que más del 25% de los conductores válidos no pudieran ingresar al embudo de evaluación.

2. **QRT (Calificación de Emisores y Oportunidades de Inversión)**:
   - Analiza prospectos de emisión de bonos y empresas emergentes.
   - *Hecho*: Las startups no disponen de balances de 3 años, pero sí de reportes de retención de clientes (*churn*), métricas de caja (*burn rate*) y rondas de inversión auditadas.

### 6.2. Hipótesis de diseño para Jev

- **Hipótesis 1**: El uso de un validador de ramas de suficiencia en CPU reduce en un 100% las llamadas a Jev con datos insubsanables, reduciendo la factura mensual de tokens en más del 18%.
- **Hipótesis 2**: La tasa de falsos rechazos de casos límite legítimos se reduce en más de un 80% en comparación con validadores estáticos de campos requeridos.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de falla y mitigaciones

| Modo de Falla | Causa Raíz | Detección | Mitigación Arquitectónica |
|---|---|---|---|
| **Explosión Combinatoria de Ramas** | Intentar modelar cientos de excepciones casuísticas en el validador CPU. | Código de validación complejo y difícil de mantener ($> 500$ líneas). | Agrupar los requisitos en ramas abstractas estandarizadas de suficiencia. |
| **Falsa Suficiencia por Datos Vencidos** | El usuario aporta todos los campos, pero los documentos tienen 3 años de antigüedad. | Comprobación de temporalidad y vigencia en CPU (JEV-P04-012 y JEV-P04-019). | Integrar reglas de caducidad en el Nivel 2 del validador previo. |
| **Paso de Datos Ficticios para Engañar al Validador** | El cliente rellena campos con `"asdasd"` o `"0"` para superar la validación. | Verificación de tipos semánticos y entropía mínima en CPU. | Exigir validadores de formato regex o firmas de hash para archivos adjuntos. |

### 7.2. Condiciones de NO uso

- **NO usar Jev para validar la presencia de campos básicos**: Pedirle a Jev *"dime si falta el RUT o la fecha"* es un desperdicio de inferencia y latencia; la verificación de presencia de claves pertenece 100% a la CPU.
- **NO relajar las ramas mínimas de suficiencia por presión comercial sin actualizar el modelo de riesgo**: Permitir que casos sin evidencia mínima lleguen a Jev forzará al modelo a alucinar o producir decisiones descalibradas.

## 8. Validación propuesta

> **Nota**: Validación técnica propuesta, no ejecutada en producción.

### 8.1. Diseño experimental
- **Hipótesis falsable**: El validador previo de dos niveles con ramas de evidencia alcanzará una tasa de rechazo del 100% en cargas sintéticamente corruptas o insuficientes (cero llamadas inútiles a Jev), al tiempo que retendrá una tasa de aprobación del $> 95\%$ en un conjunto de 200 casos límite válidos no tradicionales.
- **Dataset sintético de prueba**: 500 solicitudes simuladas: 200 estándar completas, 150 casos límite heterogéneos pero suficientes, y 150 casos con omisión crítica de evidencia.
- **Métricas y umbrales**:
  - Tasa de Falsos Rechazos en Casos Límite: $< 3.0\%$.
  - Tasa de Fugas de Cargas Incompletas hacia Jev: $0.0\%$.
  - Tiempo de ejecución en CPU: $< 2$ milisegundos por solicitud.
- **Criterio de rechazo**: Si el validador descarta más del 5% de los casos límite válidos o permite el paso de una sola solicitud sin datos causales mínimos, el diseño de ramas se considera fallido y debe reconfigurarse.
- **Presupuesto estimado**: Ejecución puramente local en CPU (Python/pytest) = $0.00 USD.
