# JEV-P06-017: Control de Comparaciones Múltiples y Prevención del Desgaste del Conjunto de Prueba

## 1. Respuesta directa y decisión que permite tomar

Evaluar múltiples formulaciones de prompts, esquemas de taxonomía o variantes de modelos sobre el mismo conjunto de prueba sin control estadístico desencadena la **Explosión de Falsos Descubrimientos (*Multiple Testing Fallacy*)**. Si un equipo de ingeniería prueba $M = 20$ variantes de prompts contra el mismo holdout test con un nivel de significancia nominal de $\alpha = 0.05$, la **Tasa de Error Familiar (Family-Wise Error Rate - FWER)** se dispara a:

$$\text{FWER} = 1 - (1 - 0.05)^{20} \approx 64.15\%$$

Existe casi un **$65\%$ de probabilidad de declarar una "mejora estadísticamente significativa" que en realidad es puro ruido estocástico**. Además, reutilizar iterativamente el conjunto de prueba para guiar el diseño de los prompts convierte al conjunto de prueba en un conjunto de entrenamiento tácito (*Test Set Peeking*), destruyendo su capacidad de predecir el rendimiento en producción.

Para garantizar la integridad científica de las comparaciones en Jev 1.13, la arquitectura de validación debe implementar el **Protocolo de Control de Descubrimientos y Presupuesto de Consultas (PCDPC)**:

1. **Corrección Estadística por Comparaciones Múltiples**:
   - **Procedimiento Benjamini-Hochberg (FDR - False Discovery Rate)**: Cuando se exploran múltiples formulaciones ($M > 5$), controlar la tasa de falsos descubrimientos al nivel $Q = 0.05$, ordenando los $p$-values:
     $$p_{(i)} \le \frac{i}{M} Q$$
   - **Corrección de Bonferroni (Para Decisiones Críticas de Despliegue)**: Para compuertas de liberación final entre $M$ candidatos preseleccionados, exigir $\alpha_{\text{ajustado}} = \frac{\alpha}{M}$.
2. **Arquitectura Escalonada de Conjuntos de Datos (*Ladder of Datasets*)**:
   - **Conjunto de Exploración y Prompt Tuning (40%)**: Consultas ilimitadas para ingeniería de prompts e iteración rápida.
   - **Conjunto de Validación de Esquemas (30%)**: Máximo 10 evaluaciones controladas con Benjamini-Hochberg.
   - **Bóveda Sellada Golden Holdout (30%)**: **Una única evaluación final (*Single-Shot Evaluation*)**. Una vez desencriptada y evaluada, la partición queda "quemada" y debe ser renovada para futuras versiones.
3. **Presupuesto de Consultas con Ruido de Privacidad (*Reusable Holdout*)**: Si el negocio exige reutilizar el holdout, implementar el algoritmo de umbral ruidoso (*Thresholdout*) que solo devuelve retroalimentación si la mejora supera un umbral perturbado por ruido laplaciano.

**Decisión que permite tomar**: Descartar cualquier informe comparativo donde se hayan probado más de 3 variantes de prompt sin ajuste formal de $p$-values; establecer un registro criptográfico que bloquee el acceso al dataset de holdout tras su primera evaluación oficial.

## 4. Explicación técnica verificable

### 4.1. Algoritmo de Control de False Discovery Rate (Benjamini-Hochberg)

Para evaluar $M$ variantes de prompts frente a la línea base:

1. Se calculan los $p$-values individuales $p_1, p_2, \dots, p_M$ mediante pruebas pareadas de McNemar o Wilcoxon.
2. Se ordenan los $p$-values de menor a mayor:
   $$p_{(1)} \le p_{(2)} \le \dots \le p_{(M)}$$
3. Para una tasa de descubrimiento falso objetivo $Q = 0.05$, se encuentra el mayor índice $k$ que satisfaga:
   $$p_{(k)} \le \frac{k}{M} \cdot Q$$
4. Se rechaza la hipótesis nula (se declara mejora significativa) para **todas las variantes $i = 1, 2, \dots, k$**.
5. Si ningún $p_{(i)}$ satisface la condición, se concluye formalmente que **ninguna de las variantes supera a la línea base con significancia controlada**.

### 4.2. El Protocolo de Escalera de Datasets (*Ladder of Datasets*)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      LADDER OF DATASETS (GOBERNANZA)                        │
├─────────────────────────────────────────────────────────────────────────────┤
│ NIVEL 1: DATASET DE EXPLORACIÓN (DEV)                                       │
│ - Acceso: Ilimitado                                                         │
│ - Propósito: Ingeniería de prompts, pruebas sintácticas, depuración de bugs │
├─────────────────────────────────────────────────────────────────────────────┤
│ NIVEL 2: DATASET DE VALIDACIÓN DE CANDIDATOS (VAL)                          │
│ - Acceso: Cuota máxima de 10 ejecuciones                                    │
```

## 5. Ejemplo sintético trabajado y contraejemplo o caso límite

### 5.1. Implementación en Python: Controlador de Comparaciones Múltiples y Presupuesto

```python
# Ejemplo ilustrativo no ejecutado
"""
Módulo de Control de Comparaciones Múltiples y Presupuesto de Holdout para Jev.
Implementa correcciones Bonferroni, Benjamini-Hochberg y contador de desgaste de test.
"""

from typing import List, Dict, Any, Tuple
import numpy as np
import logging

logger = logging.getLogger("MultipleTestingGuard")

class MultipleTestingController:
    def __init__(self, fdr_q_level: float = 0.05, max_test_queries: int = 1):
        self.q = fdr_q_level
        self.max_test_queries = max_test_queries
        self.query_counter = 0

    def apply_benjamini_hochberg(
        self, hypotheses: List[Dict[str, Any]]
    ) -> List[Dict[str, Any]]:
        """
        Aplica el procedimiento Benjamini-Hochberg sobre una lista de hipótesis con sus p-values.
        """
        try:
            M = len(hypotheses)
            if M == 0:
                return []

            # Ordenar por p-value ascendente
            sorted_hypo = sorted(hypotheses, key=lambda x: x["p_value"])

            # Encontrar el mayor k tal que p_(k) <= (k / M) * Q
            max_k = -1
            for k in range(1, M + 1):
                critical_val = (k / float(M)) * self.q
                sorted_hypo[k - 1]["bh_critical_value"] = round(critical_val, 6)
                if sorted_hypo[k - 1]["p_value"] <= critical_val:
                    max_k = k

            # Etiquetar cuáles se rechazan (significativas)
            for idx, h in enumerate(sorted_hypo):
                h["bh_rank"] = idx + 1
                h["statistically_significant_fdr"] = (idx + 1 <= max_k) if max_k != -1 else False
                h["bonferroni_critical_value"] = round(self.q / float(M), 6)
                h["statistically_significant_bonferroni"] = (h["p_value"] <= (self.q / float(M)))

            return sorted_hypo

        except Exception as err:
            logger.error(f"Error en Benjamini-Hochberg: {type(err).__name__} (detalles omitidos por seguridad)")
            return []

    def consume_holdout_budget(self, caller_id: str) -> bool:
        """
        Controla el presupuesto de consultas sobre la bóveda holdout.
        """
        self.query_counter += 1
        if self.query_counter > self.max_test_queries:
            logger.warning(
                f"ALERTA CRÍTICA: Se superó el presupuesto de consultas en el Holdout Test "
                f"(Query #{self.query_counter} por {caller_id}). La partición está quemada."
            )
            return False
        return True


if __name__ == "__main__":
    controller = MultipleTestingController(fdr_q_level=0.05, max_test_queries=1)

    # Simulación de un ingeniero que probó 10 variantes de prompt con Jev
    # La mayoría son ruido (p > 0.05), pero una pareció significativa por azar (p=0.038)
    simulated_tests = [
        {"prompt_id": "Prompt_v1_Simple", "p_value": 0.42},
        {"prompt_id": "Prompt_v2_FewShot", "p_value": 0.12},
        {"prompt_id": "Prompt_v3_NegativeAnchors", "p_value": 0.003},  # Mejora real
        {"prompt_id": "Prompt_v4_Verbose", "p_value": 0.65},
        {"prompt_id": "Prompt_v5_EnglishInput", "p_value": 0.038},    # Falso positivo de azar!
        {"prompt_id": "Prompt_v6_MarkdownTables", "p_value": 0.18},
        {"prompt_id": "Prompt_v7_JsonStrict", "p_value": 0.008},      # Mejora real
        {"prompt_id": "Prompt_v8_Roleplaying", "p_value": 0.55},
        {"prompt_id": "Prompt_v9_ChainOfLogic", "p_value": 0.81},
        {"prompt_id": "Prompt_v10_CleanContext", "p_value": 0.045},   # Falso positivo de azar!
    ]

    results = controller.apply_benjamini_hochberg(simulated_tests)

    print("--- RESULTADO DEL CONTROL DE COMPARACIONES MÚLTIPLES (FDR Q=0.05, M=10) ---")
    for r in results:
        status_fdr = "APROBADO (Significativo)" if r["statistically_significant_fdr"] else "DESCARTADO (Ruido)"
        print(f"Rank #{r['bh_rank']} | {r['prompt_id']}: p={r['p_value']} | Umbral BH={r['bh_critical_value']} | {status_fdr}")

    # Auditoría de Presupuesto Holdout
    print("\n--- Auditoría de Presupuesto Holdout ---")
    print("Consulta 1 (Evaluación Oficial):", "AUTORIZADO" if controller.consume_holdout_budget("CI_Pipeline") else "BLOQUEADO")
    print("Consulta 2 (Intento de Peeking):", "AUTORIZADO" if controller.consume_holdout_budget("Engineer_Peeking") else "BLOQUEADO")
```

### 5.2. Caso Límite / Contraejemplo

Un equipo de optimización probó 40 formulaciones distintas de taxonomía para clasificar tipos de reclamos.
- De las 40 formulaciones, la variante #27 arrojó un **$p$-value de 0.021** frente a la línea base en el test set.
- El equipo redactó un paper interno anunciando: *"El Prompt #27 superó a la línea base con $p < 0.05$"*.
- Desplegaron el Prompt #27 en producción y el rendimiento fue un **desastre idéntico a los otros 39 prompts**.
- **La explicación matemática**: Con 40 pruebas independientes bajo la hipótesis nula, el número esperado de falsos positivos por puro azar al nivel $\alpha=0.05$ es $40 \times 0.05 = \mathbf{2.0}$. El $p=0.021$ era simplemente uno de los dos falsos positivos garantizados por la probabilidad.
- Al aplicar la corrección de Bonferroni ($\alpha_{\text{bonf}} = 0.05 / 40 = \mathbf{0.00125}$), el $p=0.021$ fue rechazado de inmediato.
- **Lección**: Sin corrección por comparaciones múltiples, el optimismo cuantitativo destruye valor en producción.

## 6. Aplicación a nuestros desarrollos

### 6.1. Wheelwork (Ingeniería de Prompts y Rúbricas)
- **Hecho**: Los ingenieros ajustan iterativamente las descripciones de las competencias de los candidatos en el esquema `Choice`.
- **Hipótesis de desarrollo**: Wheelwork debe implementar el **Ladder of Datasets**: todas las iteraciones de redacción deben correr sobre el dataset `DEV` (400 CVs). Cuando se preseleccionen las 3 mejores variantes, se evaluarán en `VAL` aplicando la corrección de Benjamini-Hochberg. Solo la ganadora se evaluará una única vez en `GOLDEN_HOLDOUT` antes de autorizar el release.

### 6.2. QRT (Cuadernos Cuantitativos y Búsqueda de Parámetros)
- **Hecho**: En trading cuantitativo, el *Data Mining Bias* (probar 100 reglas técnicas hasta que una parezca rentable) es el principal motivo de quiebra de fondos algorítmicos.
- **Hipótesis de desarrollo**: QRT debe tratar a Jev con el mismo rigor que a cualquier estrategia cuantitativa: prohibir terminantemente probar múltiples taxonomías contra el mismo histórico de precios. Se exigirá el registro del número total de formulaciones evaluadas ($M$) y la aplicación obligatoria de la **Corrección de Deflated Sharpe Ratio (DSR)** de Bailey & López de Prado para ajustar por comparaciones múltiples.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de Fallo
1. **Ocultamiento de Ensayos Fallidos (*File Drawer Problem*)**: Probar 25 prompts en un Jupyter Notebook local, borrar las celdas de los 24 que fallaron y presentar el ganador como si hubiera sido la única hipótesis planificada.
2. **Holdouts Contaminados por Desgaste**: Mantener el mismo conjunto de prueba durante dos años, evaluándolo semanalmente con cada commit, hasta que el modelo memoriza tácitamente cada caso.

### 7.2. Controles Mandatorios
- **Log Centralizado de Consultas de Inferencia**: Todo script que consulte el dataset de validación debe registrar la llamada en una tabla de auditoría con `run_id`, autor, fecha y hash del prompt.
- **Renovación Semestral del Holdout**: El 100% de la partición de holdout test debe renovarse cada 6 meses con datos nuevos recién etiquetados.

### 7.3. Condiciones de No Uso
- Prohibido autorizar un piloto si el número de variantes exploradas sobre el test set supera el presupuesto de consultas sin ajuste formal de FDR.

## 8. Validación propuesta

### 8.1. Hipótesis Falsable
> **Hipótesis**: La aplicación obligatoria del procedimiento Benjamini-Hochberg (FDR $Q=0.05$) sobre la batería de exploración de prompts en Wheelwork filtrará al menos el **$100\%$ de los falsos descubrimientos espurios** ($p \in [0.01, 0.05]$ bajo la nula), asegurando que solo variantes con una mejora estructural reproducible alcancen la evaluación de Golden Holdout.

### 8.2. Diseño Experimental
- **Tipo**: Propuesta, no ejecutada.
- **Simulación**: Inyectar 10 variantes de prompts sintéticas idénticas en capacidad (A/A testing puro) y medir cuántas arrojan $p < 0.05$ por azar antes y después de aplicar Benjamini-Hochberg.
- **Criterio de Rechazo**: Si el procedimiento permite la aprobación de cualquier variante nula con la corrección activa, el nivel $Q$ se reducirá a 0.01.
- **Presupuesto Supuesto**: Cero coste adicional de infraestructura; 6 horas de modelación estadística ($\approx \text{USD \$300}$).
