# JEV-P06-004: Prevención de Fuga de Datos: Separación Criptográfica por Entidad, Documento y Período Temporal

## 1. Respuesta directa y decisión que permite tomar

La partición aleatoria ingenua (*uniform random split*) en tareas de decisión semántica con modelos fundacionales produce estimaciones de rendimiento groseramente optimistas e inválidas. Esto ocurre debido a tres vías silenciosas de **Fuga de Datos (*Data Leakage*)**: (1) Fuga por Entidad (casos de un mismo cliente o candidato distribuidos entre ajuste y prueba), (2) Fuga por Documento (fragmentos o cláusulas de un mismo contrato dispersos en ambas particiones), y (3) Fuga Temporal o *Lookahead Bias* (usar información del futuro para calibrar decisiones del pasado).

Para erradicar la contaminación y garantizar una evaluación independiente incorruptible, la arquitectura debe implementar la **Partición Criptográfica Jerárquica Tripartita (PCJT)** en CPU:

1. **Aislamiento por Clúster de Entidad y Documento**: La asignación de datos a las particiones se realiza exclusivamente a nivel de **Identificador de Raíz (`entity_root_id` o `document_id`)**, nunca por fila individual o fragmento. Si una entidad pertenece a la partición de prueba, **el 100% de sus transacciones, facturas y registros históricos queda confinado a esa partición**.
2. **Estratificación Temporal Estricta (Out-of-Time Split)**: En dominios financieros o dinámicos, la partición debe ser estrictamente cronológica:
   $$t(\mathcal{D}_{\text{ajuste}}) \le T_1 < t(\mathcal{D}_{\text{calibración}}) \le T_2 < t(\mathcal{D}_{\text{holdout\_test}})$$
   La evaluación final se ejecuta sobre un período temporal posterior a la calibración, midiendo directamente la resiliencia del modelo ante la no estacionariedad.
3. **Bóveda Criptográfica Sellada de Evaluación Final**: La partición de evaluación final (`holdout_test`, 30% del volumen) se cifra y sella con un hash SHA-256. Queda estrictamente prohibido consultar o evaluar repetidamente este conjunto durante la fase exploratoria de ingeniería de prompts; **se ejecuta una sola vez al cierre de la validación**.

**Decisión que permite tomar**: Rechazar de inmediato cualquier benchmark en Wheelwork o QRT que haya utilizado particiones aleatorias simples (`train_test_split` estándar de Scikit-Learn); exigir la auditoría del log de partición criptográfica por entidad y tiempo antes de considerar válidos los resultados de precisión y calibración de Jev.

### 4.1. Diagrama de la Bóveda Criptográfica Tripartita de Partición

```
                       DATASET HISTÓRICO BRUTO (N Casos)
                                       │
        ┌──────────────────────────────┴──────────────────────────────┐
        ▼                                                             ▼
[ FILTRO DE TIEMPO: t <= T_corte ]                  [ EVALUACIÓN OOD / TEMPORAL ]
(Datos Históricos Disponibles)                      (Período Futuro / No Visto)
        │                                                             │
        ▼                                                             ▼
AGRUPACIÓN POR ENTIDAD RAÍZ                                   HOLDOUT TEMPORAL (20%)
hash = SHA-256(entity_id + salt)                              (Sello Criptográfico)
        │
        ├──────────────────────────────┐
        ▼                              ▼
AJUSTE DE PROMPTS (40%)        CALIBRACIÓN EN CPU (40%)
(Desarrollo, Few-shot)         (Ajuste de Temperatura T*,
                                Umbrales y Bayes tau*)
```

### 4.2. Algoritmo de Asignación Determinista Criptográfica

Para evitar almacenar tablas gigantescas de mapeo de particiones y garantizar que la asignación sea 100% determinista e inmune a reordenamientos de datos:

$$\text{score} = \frac{\text{int}(\text{SHA-256}(\text{entity\_id} \,\|\, \text{salt})[:8], 16)}{2^{32} - 1}$$

- Si $\text{score} < 0.40 \implies \mathcal{D}_{\text{ajuste\_prompts}}$
- Si $0.40 \le \text{score} < 0.70 \implies \mathcal{D}_{\text{calibración\_cpu}}$
- Si $\text{score} \ge 0.70 \implies \mathcal{D}_{\text{holdout\_test\_ciego}}$

**Propiedad Matemática**: Cada entidad reside enteramente en un único subconjunto con probabilidad proporcional al tamaño de la partición, garantizando **cero intersección de entidades ($\mathcal{E}_{\text{ajuste}} \cap \mathcal{E}_{\text{test}} = \emptyset$)**.

### 5.1. Implementación en Python: Particionador Criptográfico Anti-Fuga

```python
# Ejemplo ilustrativo no ejecutado
"""
Módulo de Partición Criptográfica y Detección de Fugas de Datos para Jev.
Garantiza el aislamiento absoluto por entidad y ventana temporal.
"""

import hashlib
from typing import List, Dict, Any, Set
import logging

logger = logging.getLogger("DataLeakageGuard")

class CryptographicSplitter:
    def __init__(self, secret_salt: str = "jev_canonical_audit_salt_2026"):
        self.secret_salt = secret_salt

    def assign_partition(self, entity_id: str) -> str:
        """
        Asigna deterministamente una entidad a una partición mediante SHA-256.
        """
        raw_key = f"{entity_id}:{self.secret_salt}".encode("utf-8")
        hash_hex = hashlib.sha256(raw_key).hexdigest()
        # Convertir los primeros 8 caracteres hexadecimales a un float [0.0, 1.0)
        score = int(hash_hex[:8], 16) / float(0xFFFFFFFF)

        if score < 0.40:
            return "DEV_PROMPT_TUNING"
        elif score < 0.70:
            return "CPU_CALIBRATION"
        else:
            return "SEALED_HOLDOUT_TEST"

    def partition_dataset(
        self, records: List[Dict[str, Any]]
    ) -> Dict[str, List[Dict[str, Any]]]:
        """
        Particiona una lista de registros preservando la integridad de la entidad.
        """
        try:
            partitions = {
                "DEV_PROMPT_TUNING": [],
                "CPU_CALIBRATION": [],
                "SEALED_HOLDOUT_TEST": []
            }

            for rec in records:
                ent_id = rec.get("entity_id")
                if not ent_id:
                    raise ValueError(f"Registro sin 'entity_id': {rec}")
                target_part = self.assign_partition(ent_id)
                partitions[target_part].append(rec)

            # Verificación cruzada anti-fuga (Assertion Gate)
            dev_entities = {r["entity_id"] for r in partitions["DEV_PROMPT_TUNING"]}
            cal_entities = {r["entity_id"] for r in partitions["CPU_CALIBRATION"]}
            test_entities = {r["entity_id"] for r in partitions["SEALED_HOLDOUT_TEST"]}

            # Comprobar intersecciones vacías
            assert dev_entities.isdisjoint(cal_entities), "Fuga detectada entre DEV y CAL"
            assert dev_entities.isdisjoint(test_entities), "Fuga detectada entre DEV y TEST"
            assert cal_entities.isdisjoint(test_entities), "Fuga detectada entre CAL y TEST"

            return partitions

        except Exception as err:
            logger.error(f"Error crítico en partición criptográfica: {type(err).__name__} (detalles omitidos por seguridad)")
            raise


if __name__ == "__main__":
    # Simulación con facturas de 5 empresas clientes
```

### 5.2. Caso Límite / Contraejemplo

Un equipo de investigación evaluó la capacidad de Jev para detectar cláusulas abusivas en pólizas de seguro.
- Tenían 50 pólizas completas, que dividieron en 1,500 fragmentos de párrafos.
- Usaron `train_test_split(test_size=0.3, random_state=42)` plano a nivel de párrafo.
- El modelo obtuvo un **F1-Score del 96.5%** en el conjunto de prueba.
- Al desplegar el modelo sobre una nueva aseguradora en producción, el rendimiento cayó en picada a **61.2%**.
- **Causa de la catástrofe**: Los párrafos de una misma póliza estaban mezclados en entrenamiento y prueba. Jev simplemente aprendió el tono, la tipografía y el encabezado de las pólizas de la aseguradora de prueba, memorizando el documento sin aprender a detectar cláusulas abusivas en abstracto.
- **Corrección**: La partición a nivel de `poliza_id` reveló de inmediato el rendimiento real previo al despliegue.

## 6. Aplicación a nuestros desarrollos

### 6.1. Wheelwork (Conciliación y Reclutamiento)
- **Hecho**: En reclutamiento, un candidato puede postular con múltiples versiones de su CV o postular a distintos cargos dentro de la misma empresa cliente.
- **Hipótesis de desarrollo**: La partición de evaluación debe realizarse obligatoriamente a nivel de `RUT_candidato` y `RUT_empresa_cliente`. Si un candidato o cliente aparece en el conjunto de ajuste, queda terminantemente prohibido que cualquiera de sus registros pasados o presentes aparezca en el `holdout_test` de evaluación de Jev.

### 6.2. QRT (Cuadernos de Trading y Macroeconomía)
- **Hecho**: En finanzas cuantitativas, la violación temporal es el pecado capital de la modelación (*Lookahead Bias*).
- **Hipótesis de desarrollo**: QRT debe prohibir cualquier partición aleatoria por hash. La partición de evaluación de Jev para análisis de eventos de mercado debe ser **100% cronológica (Walk-Forward Validation)**:
  - Ajuste: 2018–2022.
  - Calibración de temperatura $T^*$: 2023.
  - Holdout Test ciego: 2024–2026.
  Esto garantiza que el modelo se enfrente a regímenes de tasas e inflación que no existían en su ventana de diseño.

## 7. Fallos, límites, controles y condiciones de no uso

### 7.1. Modos de Fallo
1. **Fuga por Identificador Derivado**: Usar `invoice_id` creyendo que aisla entidades, cuando varias facturas pertenecen al mismo grupo empresarial (e.g., holding o filiales con el mismo departamento contable).
2. **Peeking en el Holdout**: Ajustar los prompts repetidamente después de ver que el modelo falló en el conjunto de prueba holdout, invalidando su condición de test ciego.

### 7.2. Controles Mandatorios
- **Sello Hash del Holdout en Git**: Registrar el hash SHA-256 de los datos del holdout en el repositorio y bloquear su desencriptación hasta la fecha final de auditoría del piloto.
- **Assertion Automática en Pipeline**: Código en CI/CD que lance un error fatal si la intersección de conjuntos de entidades entre particiones no es vacía.

### 7.3. Condiciones de No Uso
- Prohibido publicar o aceptar cualquier informe de rendimiento si se comprueba que el conjunto de prueba contenía documentos o entidades vistas durante el ajuste de los prompts.
